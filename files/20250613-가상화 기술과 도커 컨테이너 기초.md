# I. 가상화
## 1. 가상화(Virtualization) 기술의 이해
> 서버, 스토리지, 네트워크 등 물리적 시스템의 자원을 **추상화**하여 가상의 표현을 생성하는 기술

하나의 물리적 컴퓨터를 여러 논리 자원으로 나누거나, 반대로 여러 개의 물리적 자원을 하나인 것처럼 사용하는 기술을 의미한다. 

### 1.1 가상화의 역사

과거에는 하나의 서버에 하나의 운영체제(OS)만 설치해서 사용했지만 이 방식은 몇 가지 문제점이 존재. 서버 성능은 좋은데 프로그램 하나만 돌리기에는 남는 자원이 너무 많다든지(자원 낭비), 새 서비스를 운영하기 위해 매번 비싼 하드웨어를 새로 사야 한다든지(확장성 부족), 한 프로그램이 에러를 일으켜 OS가 멈추면 다른 서비스까지 모두 중단다든지(격리성 문제)...

#### 가상화의 이점

하드웨어 자원을 최대한 활용해 리소스 효율성을 높일 수 있고, 가상 머신은 파일 형태이므로 IT 인프라를 소프트웨어적으로 제어해 관리에 용이하다. 또한 장애 발생 시 가상 시스템 단위로 빠르게 재해 복구가 가능하다. 예시를 들자면 다음과 같다.
- 낮에 사용량이 많은 '웹 서버'와 밤에 작업이 몰리는 '배치 처리 서버'를 물리 서버 한 대에 몰아넣어, 시간대별로 자원을 나누어 쓰게 한 뒤, 하드웨어 가동률을 70~80% 이상으로 끌어올리기.
- 과거에는 서버 한 대를 추가하려면 장비를 발주하고, 배송받고, 랙에 장착하고 케이블을 연결하는 물리적 과정이 필요했지만, 가상화 환경에서는 미리 만들어둔 이미지(Template)를 복사하기만 하면 클릭 몇 번으로 수 분 내에 새로운 서버를 생성할 수 있음. 심지어 수백 대의 가상 머신(VM)을 하나의 관리 콘솔에서 모니터링하고 제어할 수 있음.
- 물리 서버는 부품 하나만 고장 나도 서비스가 중단되지만, 가상화는 운영체제와 데이터를 하나의 '파일(.vmdk, .vhd 등)' 형태로 관리하기 때문에 복구 방식이 완전히 달라짐. 
  - 스냅샷(Snapshot): 특정 시점의 상태를 '사진 찍듯' 저장해두는 기술. 업데이트 오류나 랜섬웨어 공격을 받아도 장애 발생 직전의 스냅샷으로 즉시 되돌릴(Rollback) 수 있다.

### 1.2 핵심 구성 요소
실제 하드웨어인 호스트 위에 하이퍼바이저라는 관리 소프트웨어를 두어, CPU와 메모리 같은 자원을 쪼개어 여러 개의 독립적인 가상 머신인 게스트에게 나누어 주는 구조.

* **호스트(Host):** 물리적인 하드웨어와 실제 설치된 메인 OS.
* **게스트(Guest):** 가상화 기술을 통해 만들어진 VM과 그 위에서 돌아가는 OS.
* **하이퍼바이저(Hypervisor):** 호스트의 자원을 나누어 각 게스트에게 할당하고 관리하는 중간 관리자.

### 1.3 가상화 종류 (범위 기준)

#### 서버 가상화
가장 기본이 되는 가상화로, 물리적인 CPU, RAM 등을 논리적 단위로 쪼개는 기술. 하이퍼바이저를 이용해 하나의 하드웨어 위에 여러 개의 VM을 띄운다. 각 VM은 서로 독립된 운영체제(Guest OS)를 가진다.
- **AWS의 EC2**가 대표적. 물리적인 거대 서버의 자원을 사용자가 원하는 만큼(t3.medium, m5.large 등) 잘라서 대여해주는 서비스다.
- 하드웨어 가속 기술(Intel VT-x, AMD-V)을 통해 가상화로 인한 성능 저하를 최소화한다.

#### 네트워크 가상화
물리적인 케이블 연결에 구애받지 않고, 소프트웨어로 네트워크를 구성하고 제어하는 기술.
- **SDN(Software Defined Networking)**: 제어부(Control Plane)와 데이터 전송부(Data Plane)를 분리하여, 관리자가 중앙에서 소프트웨어 명령만으로 네트워크 경로를 변경하거나 보안 정책을 적용할 수 있게 한다.
- **NFV(Network Functions Virtualization)**: 방화벽, 로드밸런서 같은 고가의 하드웨어 장비를 범용 서버 위에서 돌아가는 **소프트웨어(가상 장비)**로 대체.
- **AWS VPC**가 대표적. 네트워크 가상화를 통해 물리적 네트워크 장비를 건드리지 않고도 클릭 몇 번으로 서브넷을 나누고, 라우팅 테이블을 설정하고, 보안 그룹(Firewall)을 만든다.

#### 컨테이너 가상화
OS 전체를 가상화하는 기존 방식과 달리, OS의 커널을 공유하면서 애플리케이션 실행에 필요한 환경만 격리하여 담는 기술. **가볍고 빠르며 효율적인데다 어디에든 이식이 가능하다**.
- 게스트 OS가 따로 없기 때문에 GB 단위가 아닌 MB 단위로 **용량이 줄어듦**.
- 부팅 과정이 필요 없어 명령어를 입력하자마자 애플리케이션이 **수초 내 실행**.
- 개발 환경을 그대로 패키징(이미지화)하여 어디서든 똑같이 돌릴 수 있음.
- OS가 차지하는 리소스 낭비가 거의 없어 동일 성능의 물리 서버에서 VM보다 훨씬 많은 컨테이너를 구동할 수 있음.

참고로 하드웨어와 게스트 OS 사이를 중재하던 하이퍼바이저의 역할을, 컨테이너 가상화에서는 **컨테이너 엔진(예: Docker)**이 담당하게 된다.

## 2. 컨테이너 기술과 도커
### 2.1 컨테이너란?
> **OS 커널**을 공유하면서, 프로세스를 격리하여 실행하는 운영체제 수준의 가상화. 하드웨어 전체를 흉내 내는 VM과 달리, 애플리케이션 실행에 필요한 최소한의 요소(바이너리, 라이브러리)만 패키징한다.

### 2.2 가상 머신과의 차이
#### 1) 가상머신(VM)
하드웨어 위에 하이퍼바이저를 두고 그 위에 게스트 OS를 설치하는 방식. 만약 격리하고 싶은 프로그램을 5개 만들어야 한다면, VMware 등으로 5개의 VM을 만들어야 함. 게다가 VM에는 독립 OS가 존재한다. 처음부터 끝까지 새로 설치해야 함. 
- 물론 가상머신도 획기적인 시스템이었다. 대부분 OS 설치와 기본 설정이 완벽하게 끝난 '골든 이미지 (Golden Image)'를 하나 만들고 이를 복제하는 방식으로 사용했다. 또한 스냅샷 기능도 지원하는 편. 나름 좋다.

#### 2) 컨테이너

그럼에도 VM은 문제가 있긴 했다. VM 한 대에 여러 프로그램을 직접 깔면 서로 엉킨다든지, 내 노트북에서는 잘 되다가 정작 서버로 옮기니까 안 된다든지, 자원을 쪼갤 때 단위 상정이 어렵다든지... 이러한 문제를 단번에 해결한 것이 컨테이너. OS 격리가 아닌 프로세스 단위로 격리해서 매번 단독 주택을 짓는게 아닌, 하나의 큰 집에 방음이 잘 되는 개인 방을 따로 만드는 것.

### 2.3 도커의 핵심 요소
#### 이미지(Image)
> 컨테이너 실행에 필요한 파일과 설정의 집합이다. (환경 변화로 인한 오류를 원천 차단하기 위해 **불변 상태를 유지**한다. 이것이 환경 이식성의 핵심)

- **읽기 전용(Read-only) 템플릿**으로, 여러 개의 레이어가 차곡차곡 쌓인 형태다.
  - 쓰기(수정)가 필요한 경우에는 쓰기 가능한 레이어를 따로 올린다. 이건 컨테이너 설명에서 다시.
- 예를 들어 OS 레이어 위에 Python 레이어를 올리고 그 위에 코드 레이어를 쌓는 방식.
  - 앱 코드를 수정해야 한다? 무거운 OS나 Python 레이어는 다시 다운로드할 필요 없이 그냥 재사용하면 된다.
  - 여러 컨테이너가 똑같은 이미지를 기반으로 실행되고 있다면, 무거운 이미지 레이어들은 단 하나만 존재하며 모든 컨테이너가 이를 공유해서 읽는 구조다. 이게 저장 공간을 아끼는 핵심.
- 빌드된 이미지는 Docker Hub 같은 저장소에 올려두고 언제든 내려받아 즉시 사용이 가능하다.

#### 컨테이너(Container)
> 이미지가 "설계도"라면, 컨테이너는 그 설계도를 바탕으로 실제로 지어진 집(프로세스).

- `docker run`을 하는 순간, 읽기 전용인 이미지 레이어 위에 **'쓰기 가능한 레이어(Writable Layer)'**가 한 층 얹어진다. 실제 프로그램은 이 층에서 돌아가며 데이터를 쓰고 읽는 셈.
  - 우리가 컨테이너 안에서 파일을 생성하고, 수정하고, 삭제하는 모든 작업은 오직 이 최상단 레이어에서만 일어난다.
  - 또한 각 컨테이너는 자신만의 전용 '쓰기 레이어'를 가지기 때문에, 컨테이너 A에서 파일을 마구마구 지워도, 같은 이미지를 쓰는 컨테이너 B나 원본 이미지에는 아무런 영향이 없다.
- 휘발성 특징을 가진다. 쓰고 버리는 것이 기본 원칙. 컨테이너를 정지하고 삭제(`rm`)하면, 실행 중에 생성되었던 '쓰기 레이어'의 모든 데이터는 함께 사라진다.

#### 볼륨(Volume)
> 컨테이너의 휘발성 문제를 해결하기 위해, 컨테이너가 삭제되어도 데이터를 영구적으로 보존하기 위한 저장소.

- **마운트**: 호스트 OS의 특정 폴더를 컨테이너 내부의 특정 폴더와 **'연결(Mapping)'**하는 방식. 즉, 컨테이너 안에서 파일을 써도 실제 내 컴퓨터 하드디스크에 저장이 되게 만들 수 있다.
- 애초에 컨테이너 내부 쓰기 레이어에 저장하는 것보다, 물리적인 디스크(볼륨)에 직접 쓰는 것이 입출력(I/O) 성능 면에서 훨씬 유리. 이 부분은 좀 어려울 수 있는데, 컨테이너의 쓰기 레이어는 유니온 파일 시스템(UnionFS)을 사용하기 때문. 

**정리하자면, 이미지는 절대 변하지 않는 게임 CD고, 컨테이너는 현재 실행 중인 게임 화면이다. 볼륨은 메모리 카드(세이브 파일)인 셈.**

## 3. 도커 주요 명령어 체계

### 1) 컨테이너 조작 (Container Commands)
* **run**: 이미지를 다운로드하고 컨테이너를 생성하여 실행한다.
* **start / stop / pause**: 컨테이너를 시작, 정지하거나 일시 정지한다.
* **rm**: 실행이 중지된 컨테이너를 삭제한다.
* **exec**: 동작 중인 컨테이너 내부에서 특정 명령을 수행한다.
* **ls / ps**: 컨테이너 목록을 확인한다.
* **cp**: 호스트와 컨테이너 간에 파일을 복사한다.

### 2) 이미지 관리 (Image Commands)
* **pull**: 도커 허브 등 레지스트리에서 이미지를 내려받는다.
* **build**: 도커파일(Dockerfile)을 기반으로 새로운 이미지를 생성한다.
* **ls / images**: 로컬에 저장된 이미지 목록을 확인한다.
* **rmi**: 사용하지 않는 이미지를 삭제한다.

### 3) 네트워크 및 볼륨 관리
* **network connect/disconnect**: 컨테이너를 도커 네트워크에 연결하거나 해제한다.
* **volume create/inspect**: 데이터를 저장할 볼륨을 생성하고 상세 정보를 확인한다.
* **prune**: 사용 중이지 않은 네트워크나 볼륨을 일괄 삭제하여 자원을 정리한다.

## 4. 기타 고급 기능
* **Swarm 관련**: node, service, stack 등은 여러 대의 도커 호스트를 하나의 클러스터로 관리하는 '도커 스웜'에서 사용되는 명령어다.
* **시스템 확인**: `docker system` 명령을 통해 도커 엔진의 전반적인 상태와 용량을 점검할 수 있다.
