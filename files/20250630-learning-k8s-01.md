# 1. 컨테이너 런타임

[컨테이너](https://prgmd-blog.vercel.app/#post/20250613-learning-docker-01)란 과거 도커 게시물에서도 봤듯 OS 커널을 공유하면서, 프로세스를 격리하여 실행하는 운영체제 수준의 가상화. 이러한 컨테이너들을 관리하는 환경을 '컨테이너 런타임'이라고 부른다.

## 1.1 대표 런타임

* **Docker**: 컨테이너 관리 전반 기능을 제공하는 대표 컨테이너 런타임.
* **Containerd**: 도커에서 개발한 오픈 소스 런타임. 이미지 다운로드, 압축 해제, 실행 및 감독 등 핵심 기능을 제공한다.
* **CRI-O**: Docker를 대체하기 위해 레드햇, 인텔 등이 협력하여 개발한 오픈 소스 런타임이다.

### Docker와 Containerd의 차이

Docker가 모든 기능을 다 모아둔 플랫폼이면 containerd는 그중 컨테이너 실행 및 관리 기능만 따로 뺀 런타임. 초창기 도커는 모든 기능이 하나로 합쳐진 거대한 모놀리식 덩어리였음. 하지만 도커가 너무 유명해지다 보니, 구글 같은 다른 진영에서 '아 다 필요없고 핵심 기능만 쓰고 싶어요'라고 요청. 그래서 핵심 엔진만 떼서 containerd라는 이름으로 오픈소스화했고 현재는 독립된 재단(CNCF)에서 관리 중. 편의 기능은 부족하지만 훨씬 가볍고 빠르다.

# 2. 컨테이너 오케스트레이션

수많은 컨테이너를 지휘하는 지휘자. 실제로 그 교향악단을 뜻하는 '오케스트라'에서 왔다. **컨테이너 런타임이 실행을 담당한다면 오케스트레이션은 운영을 담당.** 런타임이 서버(호스트)의 가장 낮은 위치에서 컨테이너를 실제로 만들고 실행한다면 오케스트레이션은 여러 대 서버에 흩어진 수많은 런타임을 원격에서 조종하고 관리한다. 

## 2.1 대표 오케스트레이션

* **쿠버네티스**: 구글이 내부에서 사용하던 시스템을 오픈소스로 공개한 것으로, 현재 사실상 업계 표준. 강력하고 유연하다. 대규모  서비스 운영에 최적화되어 있으며 어떤 클라우드 서비스에서도 동일하게 동작한다. (다만 너무 공부할 게 많아서 전문가가 필요)
* **Docker Swarm**: 도커(Docker) 서비스 안에 기본적으로 내장되어 있는 오케스트레이션 도구. 세밀한 조정 기능을 부족할지 몰라도 엄청 가볍고 빠르다. 심지어 내장 기능이기에 별도 설치도 필요 없다.

## 2.2 클러스터

여러 대 컴퓨터를 묶어 마치 한 대의 '슈퍼컴퓨터'처럼 작동하게 만드는 것. 개별 컴퓨터를 노드라고 부른다면, 여러 컴퓨터를 묶은 것은 클러스터라고 부른다.

### 클러스터 사용 목적

* **고가용성**: 컴퓨터는 무적이 아니라 언제든 고장 날 수 있음. 일단 클러스터로 묶여 있으면 서버 한 대가 불타버려도, 옆에 있는 다른 서버가 즉시 업무를 대신 수행.
* **병렬 처리 및 성능 향상**: 10시간 걸릴 작업도 10대가 나눠 작업하면 1시간만에 끝냄. 이는 오토 스케일링이라는 개념으로 확장.
* **부하 분산**: 입구에서 지휘자가 특정 서버에 업무가 몰려 과부하가 걸리는 일을 방지함.

### 노드 종류

* **마스터 노드(Master Node)**: 팀의 리더. 전체 클러스터의 상태를 관리하고, 어떤 일을 누가 할지 결정하는 두뇌 역할이다.
* **워커 노드(Worker Node)**: 실제 일을 하는 일꾼들. 컨테이너를 직접 실행하고 데이터를 처리하는 몸통 역할이다.

이 때, 마스터 노드와 워커 노드는 `kubectl`이라는 CLI 도구를 통해 명령을 주고 받는다.

## 2.3 파드

![](https://velog.velcdn.com/images/paramad/post/95e55f3d-5f97-4acb-9597-1d72f3bfcc64/image.png)

영어로 콩꼬투리를 뜻하는 단어. 꼬투리 안에 여러 콩이 들어있는 모습을 떠올리면 된다. 각 콩들이 컨테이너가 되는 셈.

* 파드는 쿠버네티스 세계에서 최소 배포 단위다. 엥 왜요? 걍 개별 컨테이너를 독립적으로 쓴다고 해도 파드 단위로 배포해야 한다. 무조건 파드라는 주머니에 담겨 배포하고 관리되는 셈.
  - 특별한 이유가 없다면 파드 하나에는 컨테이너 하나만 넣는게 원칙이긴 하다. 그래야 스케일 아웃 하기에 효율적이기 때문.
  - 또한 테스트 단에서는 `kubectl run` 등의 명령어를 입력해 직접 파드를 띄우기는 하지만, 실제로는 항상 Deployment를 통해 파드를 관리해야 함. 그래야 파드가 죽었을 때 자동으로 살아나기 때문.
* 즉, 포드 안에 담긴 컨테이너는 목적이 같은 애들끼리 담기고, 동일 워커 노드에 배치되며, 생명 주기를 공유한다. 같이 태어나 같이 죽는다.

### 파드 생성 이유

* **네트워크 공유**: 파드 하나는 고유한 IP 주소 하나를 가진다. 파드 내 컨테이너는 이 IP를 공유하며 서로 `localhost`로 소통.
* **스토리지 공유**: 파드 수준에서 볼륨을 정의해 모든 컨테이너가 해당 볼륨에 접근할 수 있도록 한다.
* **사이드카 패턴**: 메인 컨테이너와 보조 컨테이너를 하나로 묶어 같이 협업하도록 유도. 예를 들어 로그 수집기.

### 파드 생성 방법
쿠버네티스에서 모든 리소스는 YAML 파일로 정의. 파드의 3요소는 다음과 같다. 
- `apiVersion`: 오브젝트를 처리할 API 버전을 명시 (파드는 보통 `v1`)
- `metadata`: 이름, 라벨, 네임스페이스 등 리소스가 가질 신분증 기재
- **`spec`: 어떤 컨테이너 이미지를 쓸지, 포트는 몇 번인지, 메모리는 얼마나 쓸지 상세 설계가 들어가는 파트.** 

### 생명 주기

* **Pending**: 파드 생성 명령을 받고, 이미지를 받는 중이거나 어디로 자대 배치될지 대기하는 중.
* **Running**: 자대(노드)에 배치 받아 모든 컨테이너를 생성해 잘 돌아가고 있는 상태.
* **Succeeded**: 작업이 성공적으로 끝남.
* **Failed**: 에러로 작업 종료된 상태.
* **Terminating**: 삭제 중인 상태.

### 예시
``` yaml
apiVersion: v1
kind: Pod
metadata:
  name: mart-app-pod
  labels:
    app: mart
spec:
  containers:
  - name: web-server
    image: nginx:1.21
    ports:
    - containerPort: 80
  - name: log-agent      # 보조 컨테이너 (사이드카)
    image: log-collector:v1
```

## 2.4 상태 비저장 / 상태 저장
### Stateless(상태 비저장)
각 요청이 독립적이고, 데이터는 파드 내부가 아닌 외부 DB, 스토리지에 저장하는 구조. 파드가 죽고 새로 생겨도 데이터 유실 걱정이 없다. Deployment를 사용해 개수를 맞게 하면 장땡.
- 예시: Nginx, API 서버 컨테이너

### Stateful(상태 저장)
DB처럼 데이터 연속성이 생명인 앱. 파드가 재생성되어도 이전 데이터와 고유한 이름(ID)이 유지되어야 하며, 순서대로 하나씩 늘리고 줄여야 한다. 전용 볼륨(PV)이 필수 결합되어야 한다. (예를 들어 0번이 죽으면, 새로 생성된 파드 이름이 0번으로 부여받는 식. 이렇게 되면 0번이 갖고 있던 전용 볼륨으로 다시 연결된다) 
- DB(MySQL, MongoDB), Kafka, Redis 컨테이너
