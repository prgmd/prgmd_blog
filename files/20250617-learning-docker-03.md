# I. 도커 볼륨(Docker Volume)
## 1. 데이터 영속성
도커 컨테이너가 삭제되어도 데이터가 날아가지 않게 하는 방법은 크게 두 가지. 도커 볼륨과 볼륨 마운트 방식이다.

### 1.1 도커 볼륨(Docker Volumes)
도커 엔진이 자체 관리하는 저장소. 일종의 도커를 위한 전용 창고라 보면 된다.

#### 특징
- **호스트 독립성**: 호스트의 OS나 파일 구조를 몰라도 **이름만으로 관리가 가능하기 때문에 이식성이 뛰어나다.**
- **성능 및 보안**: 도커가 직접 관리한다는 뜻은, 호스트의 다른 프로세스가 함부로 접근을 못하게 막는다는 뜻. 파일 시스템 성능도 나름 최적화된 편이다.
- **백업 및 이동**: `docker save` 명령어로 딸깍 가능.

#### 주요 명령어
- 생성: `docker volume create [명칭]`
- 연결: `docker run -v [명칭]:[컨테이너_경로] [이미지]`
- 조회: `docker volume ls`
- 상세 정보: `docker volume inspect [명칭]`

### 1.2 바인드 마운트(Bind Mounts)
호스트 시스템의 특정 폴더를 컨테이너에 직통으로 연결하는 방식. **양방향 실시간 동기화** 개념이라 보면 된다.

#### 특징
- **실시간 반영(Hot Reload)**: **개발 환경에서 소스 코드 수정시 컨테이너 재시작 없이 즉시 반영된다**.
- **도커 바깥과의 통신**: 호스트 특정 설정 파일(`nginx.conf`)나 로그 파일을 직접 확인해야 할 때 유용하다.
  - 다만, 컨테이너 내부 프로세스가 호스트의 중요 파일을 건드리거나 삭제할 위험 또한 존재하다.

#### 주요 명령어
- 연결: `docker run -v /[호스트_절대경로]:[컨테이너_경로] [이미지]`
  - 이 때 반드시 **절대 경로**를 사용해야 함.

### 1.3 대표 Q&A
`-v`말고 `--mount`가 있던데요?
> 볼륨 옵션보다 더 명확하고 상세하게 저장소를 연결하기 위해 도입된 최신 방식. 과거에는 `-v`를 많이 사용했으나, 요즘은 공식 문서까지 `--mount`를 권장하는 편이다. 전자의 경우 경로 오타가 나면 **자동으로 새 폴더를 만들어주기 때문에** 디버깅이 어렵다. 하지만 `--mount`는 에러를 뱉어주기 때문에 실수를 방지할 수 있다.

최초 연결시 동기화 문제는 어떻게 되나요?
> 볼륨(`-v`)의 경우 도커가 관리하기 때문에 **최초 연결 시 일종의 데이터 보호 기능**을 지원한다. 비어있는 볼륨을 연결하면 컨테이너 내부 파일들이 볼륨에 복사된다.
>
> 바인드 마운트의 경우 서로 똑같은 파일 저장소를 양쪽에서 동시에 바라보고 있는 개념이고, 호스트가 우선이다. 호스트 내용이 컨테이너 내용을 완전히 가려버린다. (**참고로 삭제된 게 아니다! 포스트잇처럼 호스트 폴더에 가려져서 안 보이게 되는 것**) 만약 호스트 폴더가 비어있다면 컨테이너 내용도 안 보이게 되니 주의할 것.
>
> 참고로 병합 기능은 따로 제공하지 않는다.

| 단계 | 컨테이너 상태 | 볼륨(호스트) 상태 | 결과 |
| :--- | :--- | :--- | :--- |
| **1. 연결 전** | 파일 **A** 보유 | 비어 있음 | - |
| **2. 최초 연결 (`-v`)** | 파일 **A** | **A** (컨테이너에서 복사됨) | 양쪽 다 **A** 보임 |
| **3. 컨테이너에서 수정** | **A $\rightarrow$ C** | **A $\rightarrow$ C** (실시간 반영) | 양쪽 다 **C** 보임 |
| **4. 컨테이너 삭제** | (삭제됨) | **C** (데이터 보존됨) | **C**가 안전하게 남음 |
| **5. 새 컨테이너 연결** | 파일 **D** (이미지 원본) | **C** (기존 볼륨 데이터) | 양쪽 다 **C** 보임 (D가 가려짐) |

# II. MySQL를 이용한 DB 영속성 관리
이러한 '볼륨'이 가장 빛을 발하는 곳은 결국 데이터베이스.   이번에는 MySQL 역시 도커 컨테이너로 띄우고, 컨테이너끼리 연결해서 데이터를 저장하는 구조를 구현하는 방식을 간단히 설명해보겠다. 도커 명령만으로 격리된 DB 환경을 구축해보자.

## 1.1 MySQL 컨테이너 실행 및 볼륨 연결

``` bash
# 1. 전용 볼륨 생성
docker volume create mysql-data-vol

# 2. 볼륨 마운트 및 환경 변수 설정과 함께 실행
docker run -dit --name=mysql-vtest \
  -e MYSQL_ROOT_PASSWORD=your_password \
  -e MYSQL_DATABASE=db \
  -v mysql-data-vol:/var/lib/mysql mysql
```

`mysql-data-val`이 처음 연결되면 MySQL 이미지 내부 초기 설정 파일들이 볼륨으로 복사된다. 이후 컨테이너를 삭제하고 다시 띄워도 이 볼륨만 연결하면 데이터가 그대로 유지되는 식.

## 1.2 컨테이너 간 네트워크 연동
DB를 띄웠으니 이제 DB를 사용할 애플리케이션을 연결해보자. 이 때 **사용자 정의 네트워크(Bridge)**를 활용해 IP가 아닌 컨테이너 이름으로 편리하게 통신할 수 있다.

``` bash
# 1. 컨테이너 간 통신을 위한 전용 네트워크 생성
# 이 네트워크 안에서는 컨테이너 '이름'이 곧 '도메인 주소'가 됩니다.
docker network create redmine-net

# 2. MySQL 컨테이너 실행 (데이터베이스)
# --net: 생성한 네트워크에 소속
# -v: 생성한 볼륨을 MySQL 데이터 경로(/var/lib/mysql)에 연결
# -e: 초기 루트 비밀번호 및 사용할 DB 이름 설정
docker run -d --name mysql-db \
  --net redmine-net \
  -v mysql-data-vol:/var/lib/mysql \
  -e MYSQL_ROOT_PASSWORD=password \
  -e MYSQL_DATABASE=redmine \
  mysql:8.0

# 3. Redmine 컨테이너 실행 (애플리케이션)
# -p: 호스트의 8080 포트를 컨테이너의 3000 포트와 연결
# -e REDMINE_DB_MYSQL: DB 주소로 위에서 정한 컨테이너 이름(mysql-db)을 입력
# -e REDMINE_DB_PASSWORD: 위에서 설정한 DB 비밀번호와 일치시켜 연결
docker run -d --name redmine-app \
  --net redmine-net \
  -p 8080:3000 \
  -e REDMINE_DB_MYSQL=mysql-db \
  -e REDMINE_DB_PASSWORD=password \
  redmine

# 4. 실행 확인
# 브라우저에서 http://localhost:8080 접속 시 Redmine 화면이 나오면 성공!
docker ps
```

`redmine-app`이 실행되면서 환경 변수로 받은 `mysql-db`라는 이름을 도커 네트워크에 물어보고, 도커 내장 DNS가 이를 실제 DB 컨테이너의 IP로 연결. 이후 `docker stop` → `docker rm`으로 컨테이너를 모두 지워도 `mysql-data-val` 볼륨에 데이터가 남아있게 된다.
