## 1. 쿠버네티스 클러스터 구성 방법
환경과 목적에 따라 로컬 구축 도구, 직접 설치 도구, 관리형 서비스 중 적절한 방식을 선택하여 클러스터를 구성한다.

### 1) 로컬 쿠버네티스 구축 도구
* **Minikube**: 단일 혹은 다중 노드 클러스터를 가상 환경에 쉽게 구축하는 도구다. SIG(Special Interest Group)에서 관리하며, Docker나 VirtualBox 등 다양한 하이퍼바이저를 지원한다.
* **Kind (Kubernetes IN Docker)**: 도커 컨테이너를 노드로 활용하여 클러스터를 구축하는 도구로, 로컬 환경에서 다중 노드 구성을 테스트할 때 효율적이다.
* **k3s**: 메모리 점유율을 낮춘 경량화된 쿠버네티스로 설치가 간편하여 저사양 환경에 적합하다.

### 2) 다중 머신 클러스터 구축 도구
* **kubeadm**: 가장 표준적인 구축 도구로 세부 설정 변경이 다양하지만 학습 곡선이 다소 높다.
* **kubespray**: Ansible 기반의 자동화 도구로 온프레미스와 클라우드 모두에서 범용적으로 사용된다.
* **kops**: 클라우드 환경(AWS 등)에서 클러스터를 구축하고 관리하는 데 최적화되어 있다.

## 2. 쿠버네티스 사용 및 환경 설정

### 1) 네임스페이스 (Namespace)
물리적인 하나의 클러스터를 가상으로 나누어 사용하는 기능이다. 팀별 혹은 환경별(개발/운영)로 자원을 분리할 때 유용하다.
* **기본 네임스페이스**:
    - `default`: 기본 작업 공간.
    - `kube-system`: 쿠버네티스 시스템 핵심 구성 요소가 배치되는 공간.
    - `kube-public`: 모든 사용자가 접근 가능한 공용 자원 공간.
* **보안 연계**: RBAC(역할 기반 접근 제어)나 네트워크 정책을 적용하여 네임스페이스 간의 보안 경계를 강화할 수 있다.

### 2) kubectl과 인증 관리
* **kubectl**: 쿠버네티스 마스터의 API 서버에 명령을 전달하는 커맨드라인 도구다.
* **Kubeconfig**: `~/.kube/config` 파일에 클러스터 주소, 사용자 인증 정보, 컨텍스트(클러스터와 사용자 매핑)를 정의하여 관리한다. `kubectl config` 명령어로 현재 활성화된 컨텍스트를 확인하거나 변경할 수 있다.

## 3. 리소스 생성 및 관리 기술

### 1) 명령어 기반 생성 (Imperative)
* **kubectl run**: 특정 이미지를 기반으로 포드(Pod)를 즉시 생성한다. 테스트 용도로 적합하지만 상세 설정 이력이 남지 않아 재사용성이 떨어진다.
* **kubectl create**: 특정 리소스를 생성할 때 사용하며, 이미 해당 이름의 리소스가 존재하면 에러를 반환한다.

### 2) 선언적 관리 기반 생성 (Declarative)
* **kubectl apply**: YAML 파일에 정의된 '바람직한 상태'를 클러스터에 적용한다. 리소스가 없으면 생성하고, 있으면 변경된 부분만 업데이트한다.
* **장점**: 자동화 및 CI/CD 환경에서 조건 분기 없이 동일한 명령어로 상태를 동기화할 수 있어 권장되는 방식이다.

### 3) 리소스 삭제 및 강제 종료
* **일반 삭제**: `kubectl delete` 명령은 비동기적으로 처리되어 상태 확인이 필요할 수 있다. `--wait` 옵션으로 처리 완료를 기다릴 수 있다.
* **강제 삭제**: 응답이 없는 리소스는 `--force --grace-period 0` 옵션을 사용하여 즉시 제거한다.

## 4. 고급 리소스 제어 및 실습

### 1) 롤아웃 재시작 (Rollout Restart)
* `kubectl rollout restart deployment [이름]` 명령을 사용하여 배포된 포드들을 순차적으로 재기동한다. 환경 변수 변경이나 시크릿 갱신 내용을 반영할 때 주로 사용된다. 단, 리소스에 연결되지 않은 단독 포드에는 적용할 수 없다.

### 2) 리소스 이름의 유연성 (generateName)
* 리소스 정의 파일에 `name` 대신 `generateName`을 사용하면 리소스 생성 시 이름 뒤에 임의의 난수가 붙어 고유한 이름을 자동으로 할당할 수 있다. 이는 주로 테스트나 동일한 스펙의 리소스를 여러 개 만들 때 중복을 피하기 위해 활용된다.
