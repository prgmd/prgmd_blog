# 1. MongoDB

## 1.1 MongoDB의 역사

2007년, 기존 RDBMS의 확장성 한계를 극복하기 위해 10gen(현재의 MongoDB Inc.)에 의해 개발된 DB. 초당 수십만 건 광고를 처리하기에 기존 RDBMS는 한계가 너무 명확했고, 확장성과 속도를 고려한 DB를 새로 만들기로 결정. '엄청나게 큰'이라는 뜻의 'Humongous' 단어에서 따왔다고 한다. 2009년 오픈소스로 공개되면서 JSON 기반 친숙한 데이터 모델 덕분에 전 세계에서 가장 많이 사용되는 NoSQL DB로 자리잡음.

초기에는 트랜잭션을 지원하지 않아 금융권에서는 사용이 제한되어 있었으나 4.0 버전부터 다중 문서 트랜잭션을 지원하게 되면서 어느 정도 열렸다는듯.

## 1.2 개요 및 특징

> 일명 **스키마가 없는(Schema-less) 도큐먼트 지향(Document-Oriented) NoSQL 데이터베이스**.

* 고정된 스키마가 없다. 데이터 구조 변경 시 `ALTER TABLE` 같이 무거운 작업을 할 필요가 없음.
* C++ 기반 엔진을 사용하기 때문에 조회가 상당히 빠름.

  * BSON(Binary JSON) 형식을 채택해 기계가 읽는 속도와 데이터 압축 효율을 극대화했다.
* Double, String, Object, Array, Binary, Boolean, Date, Null 등 프로그래밍 언어에서 사용하는 대부분의 타입을 그대로 호환.
* ObjectID를 통한 고유 식별자 제공. 생성 시간과 프로세스 ID, 카운터를 조합해 분산 환경에서도 중복 없는 ID를 보장함.

### NoSQL이란?

> Not Only SQL의 약자. 전통적인 RDBMS의 한계를 극복하고자 만들어진 뉴타입 데이터베이스. 과거에는 데이터가 대체로 정형화되어 있었지만 현대 서비스는 SNS, Log, IoT 등 데이터 형태가 제각각인데다 양이 엄청나게 많음. 이런 상황에 최적화된 SQL들을 말한다.

* 미리 테이블을 짜지 않아도 데이터를 바로 저장할 수 있고(**유연성**), 저렴한 서버 여러 대를 연결해 성능을 올리기 쉽다(**확장성**). 또한 비정형 데이터(텍스트, 영상, 이미지, 로그 등)를 담기에 좋다.

### 도큐먼트 지향이란?

NoSQL의 여러 종류 중 하나로, 데이터를 문서로 관리하는 방식. JSON 같은 형식의 데이터를 말한다. 간단하게 말하면 포스트잇과 같다. 어떤 포스트잇에는 이름만 적고, 어떤 포스트잇에는 이름 나이 취미 특기 등등... 을 적어 상자(Collection)에 던져 넣는 식.

## 1.3 물리적/논리적 구조

계층 구조는 다음과 같다.

1. Database: 물리적 저장 단위
2. Collection: RDBMS의 Table
3. Document: RDBMS의 Row

다만 RDBMS와의 차이점도 분명히 존재.

* Collection은 Table과 달리 내부 Document들이 각자 다른 필드를 가질 수 있다!
* Join이 없으므로 데이터를 한 컬렉션에 모으는 Embedding 작업이 성능상 유리함. 다만 데이터가 16MB를 초과하지 않도록 설계할 것.

## 1.4 핵심 관리 명령어

## 2.1 CREATE

* `_id` 필드는 생략해도 상관 없음. 자동으로 생성되고, 생성 순서대로 정렬된다.
* `insertOne`: 데이터 하나 삽입.
* `insertMany`: 여러 데이터를 배열로 묶어 한꺼번에 삽입. 대량 로그 데이터에 사용됨.
* ~~`save`: 동일 `_id` 있으면 덮어쓰고 없으면 새로 삽입~~. 하지만 최신 드라이버에서는 권장하지 않는 기능.

### 멀티 스레드 옵션

* 여러 데이터 삽입시 `ordered` 옵션으로 처리 방식 정할 수 있음.

  * `true`: 하나라도 에러 나면 멈춤 → 데이터 무결성이 중요할 때 체크
  * `false`: 에러 나도 일단 나머지 다 집어넣음 → 로그처럼 누락보다 수집이 더 중요할 때

### 데이터 유실 방지

* `writeConcern`: 메모리에 먼저 작업한 후 나중에 저장 장치에 반영하는 옵션. 갑작스러운 서버 장애 시 발생 가능한 데이터 손실을 방지한다.

## 2.2 READ

* 원하는 데이터를 정교하게 걸러내기 위해 커서와 연산자를 활용.

  * 커서란? 질의 결과에 하나씩 접근할 수 있게 해주는 포인터. `toArray()`를 호출해 전체 결과를 배열로 바꿀 수도 있다.
    * `toArray`는 다만 데이터가 10,000건만 넘어가도 메모리 과부하로 앱이 뻗음. `limit()`과 `skip()`을 활용한 페이징 처리를 꼭 해주자.
  * `.` 연산자를 통해 객체 내부 속성이나 배열의 특정 순서를 지정해 조회할 수도 있다.
    * 혹여나 `db.col.find({ address.city: "Seoul" })`으로 쓰지 말자. `db.col.find({ "address.city": "Seoul" })`가 맞는 표현. 따옴표를 놓치지 말 것.

### 페이징 처리란?
데이터를 책 페이지처럼 나눠 보여주는 기술. 구글 검색 시 수억 건의 문서를 페이지 별로 보여주는 개념과 같다. MongoDB에서는 `limit`(이것만 가져와라)과 `skip`(이것까지는 넘겨라)이 그 역할을 해줌. 다만 `skip`은 뒤로 갈수록 느려진다. 앞 데이터를 다 읽어서 버린 다음에 그 다음 데이터를 가져오기 때문. 이 경우에는 **커서 기반 페이징** 기법을 사용한다. 지난번으로 본 마지막 데이터의 ID(인덱스)를 기억한 뒤 `_id`가 n 이상인 것부터 10개 달라고 하는 식.

### 기본 문법

```sql
// 기본 문법
find(query, projection)
```

* `query`: 찾는 조건. (`'name':'bear' 같이 작성함)
* `projection`: 보고 싶은 필드. 1은 노출, 0은 숨김.

### 예시

```sql
db.users.find({ age: 25 }, { name: 1, _id: 0 })
// 25살인 유저를 찾는 쿼리. 이 때 필요한 필드만 1로 켜주면 메모리를 아낄 수 있다.
// 참고로 find는 데이터를 다 가져오는 게 아니라 데이터로 가는 길을 열 때 사용한다고 알아두자. toArray는 꼭 필요한 상황에서만 쓸 것. 데이터가 적으면 괜춘.

db.orders.find({ "address.city": "Seoul" })
//중첩된 도큐먼트 내부 파고들 때는 도트 연산자 사용.
```

## 2.3 UPDATE
* `replaceOne`: Document 전체를 새 내용으로 교체 (`_id`는 유지됨)

### 수정 연산자
* `$set`: 특정 필드 값만 변경
* `$inc`, `$mul`: 값을 증가시키거나 곱함

  * 조회 후 더하는 게 아니라 DB 단에서 바로 숫자를 올리기 때문에 조회-수정 사이 오차를 방지할 수 있다.

### 배열 연산자

* `$push`: 추가
* `$pop`: 제거
* `$addToSet`: 중복 없이 추가 (Python의 Set라 보면 됨)

## 2.4 DELETE
* `updateMany`: 조건에 맞는 모든 데이터를 수정
* `deleteMany`: 조건에 부합하는 모든 Document 삭제
