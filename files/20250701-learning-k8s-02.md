# 1. 컨트롤러

파드는 언제든 죽을 수 있기 때문에 (앞서 말했듯 무적이 아니다) 이를 계속해서 관리해줄 친구들이 필요하다. 컨트롤러는 쿠버네티스의 핵심 철학인 '선언적 제어'를 수행해주는 중요한 친구. 제어 루프(관찰-비교-조정)를 돌며 파드를 관리해 준다.

* 관찰: 현재 클러스터 상태 지켜봄
* 비교: 사용자가 미리 입력해둔 원하는 상태랑 비교
* 조정: 두 상태가 다르네? → 원하는 상태로 강제 수정

## 1.1 종류

컨트롤러 종류가 많은데 대부분 90%는 다음 세 가지로 쓰임.

* **ReplicaSet**: 파드 개수 유지
* **Deployment**: ReplicaSet의 관리자. 그냥 '애플리케이션 배포 및 업데이트' 총괄임.
  * **롤링 업데이트**: 서비스 중단 없이 파드를 하나씩 새 버전으로 교체.
  * **롤백**: 새로 배포한 버전이 이상하면 즉시 이전 버전으로 되돌림.
* **DaemonSet**: 모든 노드에 하나씩 배포할 때 사용. (Fluentd 같은 로그 수집기, Prometheus 같은 서버 모니터링 에이전트처럼 서버마다 무조건 하나씩 돌아가야 하는 프로그램 관리시 필수)
  - 업데이트 전략으로는 파드 수동 삭제 혹은 노드 재기동 시에만 새 버전이 반영되는 `OnDelete`, Deployment와 유사한 `RollingUpdate`를 주로 사용.
  - 단, DaemonSet은 파드 당 하나씩 들어가기 때문에 아래에서 나오는 maxSurge 같은 설정은 불가능.
* **StatefulSet**: DB처럼 이름과 순서가 바뀌면 안되는 앱 관리시 사용 (파드 이름이 고정된다. 원래는 무작위 해시값이 붙음)
  - `volumeClaimTemplate`을 통해 각 파드 별 독립적인 영구 볼륨 클레임(PVC)을 자동으로 할당. 리소스를 삭제해도 이때 생성된 영구 볼륨은 삭제되지 않는다. 최고.
  - DaemonSet과 비슷하게 `OnDelete`, `RollingUpdate` 지원. 롤링 업데이트 시 인덱스가 높은 파드부터 하나씩 순차적 진행.
* **Job / CronJob**: 한 번 실행하고 끝나는 작업 or 특정 시간마다 반복되는 예약 작업(배치 작업) 관리용

## 1.2 Deployment

### 작동 방식

* YAML 파일에 `kind: Deployment`라 적고 선언
* 쿠버네티스를 자동으로 그 아래에 `ReplicaSet`을 만들고, 만들어진 `ReplicaSet`가 다시 `Pod`를 만든다.

> 이렇게 하는 이유: 롤링 업데이트 때문. 신버전 ReplicaSet을 만듦과 동시에 구버전 ReplicaSet를 하나씩 줄여나가는 방식으로 업데이트가 진행된다!

### 변경 이력 관리 및 롤백

* `kubectl rollout history` 명령어로 리비전 번호와 변경 내역을 확인할 수 있고, 변경 사유까지 체크하고 싶다면 생성할 때 `--record` 옵션을 키면 된다.
* 이전 버전(리비전)으로 돌리고 싶다면 `kubectl rollout undo`로 복구.
* 하지만 실운영 단에서는 그냥 기존 안정적으로 작동하던 매니페스트 파일을 다시 `kubectl apply`하는 식을 더 선호.

### 주요 업데이트 전략

* Recreate(재생성); 기존 버전 파드 모두 종료 → 새 버전 파드 일괄 생성.

  * 업데이트 속도는 빠르지만 일시적인 서비스 중단(다운타임)이 발생한다.
* **Rolling Update**: 서비스 중단은 없지만 전체 완료까지 시간이 다소 소요.

  * maxSurge: 업데이트 중 의도한 레플리카 수보다 초과해 생성 가능한 파드의 최대 개수를 설정
  * maxUnavailable: 업데이트 중 사용할 수 없는 상태가 되어도 무방한 파드의 최대 개수를 설정
* Blue/Green: 이전 버전과 새 버전을 동시에 모두 띄우고 트래픽을 한꺼번에 전환. 복구는 빠르지만 자원 소모가 두 배로 발생한다.
* Canary: 새 버전에 트래픽 일부만 먼저 흘려보내 테스트를 거침. 이후 점진적으로 트래픽을 늘려감. 

### Label

컨트롤러는 라벨(Label)을 보고 자신이 관리할 파드를 찾음. 만약 파드 라벨을 새걸로 바꾸면 '엥 내 파드 어디감?' 하면서 이전 버전 파드를 또 만드니 유의할 것.

#### 리소스 삭제

명시적으로 이름을 지정한 뒤 파일 `-f` 옵션을 지정해 제거. 만약 디플로이먼트를 삭제하면 속한 레플리카셋과 파드도 함께 삭제됨을 유의하자.

## 1.4 Job
- 작업이 성공적으로 완료되면 상태가 `Running`이 아닌 `Completed`로 표시되며, 장애가 발생하더라도 지정된 횟수만큼 재시도해 작업 성공 보장률을 높여준다.
- 하나 이상 파드를 동시에 실행해 대량의 데이터를 처리할 수 있다.

### 재시작 정책(restartPolicy)
- Never: 파드 내 컨테이너 장애시 새로운 파드를 생성해 작업을 재시도
- OnFailure: 파드 유지한 채 내부 컨테이너만 다시 시작
- backoffLimit: 작업 실패시 최대 재시도 횟수 설정

## 1.5 CronJob
정해진 스케줄에 따라 반복적으로 Job을 생성하고 실행.
- 리눅스의 `crontab`과 동일 형식을 사용한다.
- 또한 이전 작업이 완료되지 않았을 때 다음 작업을 실행할지 여부(Allow, Forbid, Replace)를 결정할 수 있다.
