# Docker Swarm

> 여러 도커 호스트(서버)를 묶어 하나의 거대 가상 도커 서버처럼 관리하게 해주는 **도커 전용** 오케스트레이션 도구. Kubernetes 같은 거다.

## 1. 핵심 개념

* **노드**: 스웜 클러스터에 들어가는 각각 도커 서버

  * **매니저 노드**: 클러스터 상태 관리 + 어떤 서버에 컨테이너 띄울지 결정
  * **워커 노드**: 실제 서비스(컨테이너)가 구동되는 일꾼들
* **서비스**: 스웜에서 컨테이너 실행하는 기본 단위. 매니저에게 떨어지는 '명령 하나' ex) "야 이미지 3개 띄워봐" → 이 묶음 자체가 서비스임
* **태스크**: 서비스에 의해 생성된 개별 컨테이너 = **매니저가 워커 노드에게 할당하는 실행 단위다.**

## 2. 사용 이유

* **고가용성**: 특정 노드가 고장날 경우 매니저가 알아서 다시 살려줌.
* **롤링 업데이트** 탑재
* **로드 밸런싱**: 여러 대 컨테이너에 트래픽을 골고루 분산해줌. (Ingress Mesh 네트워크)
* **스케일링**: 명령어 하나로 컨테이너 개수를 자유롭게 늘리거나 줄일 수 있음.

### 2.1 만약 매니저가 다운될 경우
실무에서는 이를 방지하고자 매니저 노드를 홀수로 구성함. (당연히 1대는 아니고)
- Raft 합의 알고리즘을 이용한 리더 선출 + 의사 결정
  - 매니저 노드 사이에는 리더가 존재하는데, 만약 리더가 다운되면 나머지 매니저끼리 투표를 해서 새 리더를 뽑느다.
- 과반수 원칙
  - 클러스터가 정상 작동하려면 매니저 노드 과반수가 살아있어야 함. (매니저 3대일 경우에는 2대가 살아있어야 함. 만약 과반수가 깨지면 클러스터는 읽기 전용 상태로 변함)

그리고 매니저 노드가 죽는다고 해서 워커 노드가 죽는 것도 아니다. 다만 자동 복구 기능이 작동을 안할 뿐... 서비스가 끊긴다는 건 아님.

### 2.2 Ingress Mesh
도커의 내장 로드 밸런싱 시스템. 클러스터 어떤 노드로 접속하더라도 해당 서비스가 실행 중인 노드로 트래픽을 자동 라우팅해준다. 참고로 **컨테이너를 중심으로 로드 밸런싱이 됨** (입구 노드에 도달한 패킷은 IPVS를 거쳐 라운드 로빈 방식으로 돌면서 해당 서비스가 실행 중인 노드를 찾음)

- 라우팅 메시: 스웜 클러스터 내 모든 노드는 특정 서비스 포트를 공유한다. (예를 들어  Nginx 서비스를 80번 포트로 열었다면 컨테이너가 떠 있지 않은 워커 노드 2번으로 접속해서 스웜 엔진이 알아서 실행 중인 워커 노드 1번으로 트래픽을 넘겨줌)
- 내부 로드 밸런싱(IPVS): 트래픽이 특정 노드에 도착하면 이번에는 도커 엔진 내부 IP Virtual Server가 동작. 현대 가동 중인 여러 개 컨테이너 중 어떤 게 한가한지 판단해 트래픽을 골고루 분산시킨다. 

#### 왜 노드 단위 로드 밸런싱이 아닌가요?
만약 노드 단위로 로드 밸런싱을 하게 된다면 비효율이 발생. 노드 A에 컨테이너가 5개 떠있고 노드 B에 1개만 떠있다고 가정해보자. 전체 트래픽이 100이 들어왔고, 각각 50씩 분배했다. 이렇게 되면 노드 A는 컨테이너가 각각 10씩 부하를 맡지만, 노드 B의 컨테이너는 홀로 50을 떠안고 과부하에 걸린다. 도커 스웜의 Ingress Mesh는 전체 컨테이너 개수를 기준으로 트래픽을 나눔. **어떤 노드로 트래픽이 들어오든 각 컨테이너에 똑같이 16.6만큼 일을 시키는 것.**

또한 컨테이너는 수시로 죽고 살아나는데, 노드 IP만 바라보면 실제 서비스 생존 여부를 즉각 반영하기 어렵다.

노드 단위 밸런싱은 이제 별도 L4 장비나 AWS ELB를 둬 노드 간 접속을 분산하다고 보면 된다. Ingress Mesh는 **노드 위치와 상관없이 살아있는 컨테이너들에게 골고루 전달하는 역할**

## 3. 장단점
### 3.1 장점
- 학습 곡선이 낮음 (도커를 잘 알고 있다면)
- 별도 설치가 필요 없음
- 쿠버네티스에 비해 설치나 운영 리소스가 적게 든다
- `docker-compose.yml`과 문법이 유사함

### 3.2 단점
- 당근 쿠버네티스에 비하면 세밀한 제어가 힘들다
  - 그래서 소규모, 중규모 프로젝트나 빠른 배포와 단순 운영이 필요할 때만 사용.
- 또한 커뮤니티 지원이나 플러그인도 상대적으로 적음. 생태계가 작다는 뜻.
