# 들어가며

CJ ENM의 계약직으로 근무하면서 수동 수집 업무를 개선하기 위해 BeautifulSoup과 Selenium을 활용한 크롤러를 직접 설계했던 경험이 있는데, 이 만들어둔 크롤링 로직을 좀 더 개선해서 평소 관심 있는 영역에 적용해 원하는 정보만 볼 수 있는 프로그램을 만들어보면 어떨까, 생각을 했고 처음 digem을 구상하게 됐다. 당시 정적 페이지(빌보드, 써클차트)는 BeautifulSoup으로, 자바스크립트 기반 동적 페이지(멜론, 스포티파이 등)는 Selenium으로 수집하는 이원화 구조로 제작했는데, 여기에 AI 데이터 가공 단을 붙여 원본 데이터를 AI가 알아서 가공하는 파이프라인을 구성하고, 동시에 이를 AWS 상으로 배포해 실제 서비스로 운영하는 것이 일차 목표였다. 엔드 투 엔드 사이클 전체를 경험해보고 싶었던 것도 있고, 동시에 '클라우드 부트캠프'를 다니면서 배운 개념을 직접 적용해보는 과정이 필요하다고 생각했다.

# 서비스 소개

**[dig-em.com](https://dig-em.com)** — 음악 메타데이터 수집 및 아카이빙 서비스.

Pitchfork 같은 해외 음악 전문 매체의 평론을 자동으로 수집하고, Gemini API로 번역 및 요약해 아카이빙한다. (초기에는 요약한 데이터를 제공했으나, 현재는 보다 매끄러운 내용 파악을 위해 전문 번역을 베이스로 수정하고, 동시에 어려운 단어나 용어를 풀어 해석하는 방향으로 수정했다) 수집 방식은 매일 오전 9시 자동으로 사이트를 순회하며 수집하고, 가공된 데이터를 저장소(DB)에 적재하는 시스템을 기본으로 한다. 파이프라인을 한 번 세팅해두면 사람이 개입하지 않아도 데이터가 꾸준히 쌓이는 구조를 목표로 했다.

초기 구조는 다음과 같다.

- 크롤러 (Lambda, VPC Private Subnet)
- NAT Gateway (외부 인터넷 접근을 위한 관문)
- 외부 사이트 (크롤링 대상)
- EC2 (수집 데이터 저장)

그리고 현재 운영 중인 기술 스택은 다음과 같다.

- **프론트엔드:** Next.js (Vercel)
- **DB / 인증:** Supabase (PostgreSQL)
- **크롤링 / 자동화:** Vercel Cron Jobs
- **AI 번역:** Gemini API
- **도메인:** AWS Route 53 (유지)

---

# Step 1 — VPC Isolation 기반 초기 설계

## 구조

처음 설계는 보안을 최우선으로 생각했다. Lambda 함수를 VPC(Virtual Private Cloud)의 Private Subnet 안에 배치하고, EC2를 스토리지로 사용하는 구조였다.

```
크롤러 (Lambda, VPC Private Subnet)
    ↓
NAT Gateway (외부 인터넷 접근을 위한 관문)
    ↓
외부 사이트 (크롤링 대상)
    ↓
EC2 (수집 데이터 저장)
```

VPC는 AWS 안에 격리된 가상 네트워크다. Private Subnet에 Lambda를 두면 외부 인터넷에서 직접 접근할 수 없어 보안상 안전하다. 여기까지는 좋은 설계처럼 보였다.

## 문제 발생 — NAT Gateway 비용 폭탄

그런데 청구서를 확인하고 당황했다. 예상보다 훨씬 많은 비용이 나오고 있었다.

원인은 NAT Gateway였다. VPC Private Subnet 안의 Lambda가 외부 인터넷에 접근하려면 반드시 NAT Gateway를 거쳐야 하는데, 요금 구조가 두 가지로 구성된다.

- **시간당 고정 요금**: NAT Gateway가 켜져 있는 시간만큼 고정으로 부과
- **데이터 전송 요금**: 오가는 데이터 양에 비례해 부과

크롤링은 외부 사이트에 요청을 보내고 대량의 HTML을 받아오는 작업이라, 일반적인 웹 서비스와 달리 외부 트래픽이 많다. 이 특성 때문에 데이터 전송 요금이 빠르게 쌓였다.

설계할 때 보안만 생각하고 비용 구조를 제대로 안 따진 게 문제였다. **크롤링처럼 외부 트래픽이 많은 워크로드에 VPC + NAT Gateway 조합은 맞지 않는다.** Lambda를 VPC 밖으로 꺼내는 것이 비용과 구조 모두에서 더 나은 선택이라는 결론을 내렸다.

# Step 2 — Public Lambda + S3, 그리고 Blue-Green 배포

## 무엇을 바꿨나

NAT Gateway 비용 문제를 해결하기 위해 두 가지를 바꾸기로 했다.

- **Lambda를 VPC 밖으로 꺼낸다.** VPC 안에 있을 이유가 없으니 Public 환경으로 이동해 NAT Gateway를 제거한다.
- **EC2 스토리지를 S3로 교체한다.** EC2는 켜져 있는 내내 비용이 발생하지만, S3는 저장된 용량과 요청 수에 따라만 요금이 부과되어 훨씬 저렴하다.

## 이미 서비스가 운영 중이었다

구조를 바꾸는 것 자체는 어렵지 않다. 문제는 이 시점에 이미 실제 사용자가 있는 서비스가 운영 중이었다는 것이다. 인프라를 교체하는 동안 서비스가 다운되면 안 됐다. 이때 적용한 게 **Blue-Green 배포** 전략이다.

## Blue-Green 배포란?

기존 환경(Blue)을 유지한 채로 새로운 환경(Green)을 별도로 구축하고, 준비가 완료되면 트래픽을 전환하는 방식이다. 언제든 Blue로 되돌릴 수 있어 리스크가 낮다.

```
[전환 전]
사용자 → Route 53 → Blue (VPC Lambda + EC2)   100%
                   Green (Public Lambda + S3)    0%

[단계적 전환]
사용자 → Route 53 → Blue   70%
                   Green   30%

[전환 완료]
사용자 → Route 53 → Blue    0%
                   Green  100%
```

**1단계 — Green 환경 구축 및 검증**

기존 Blue 환경(VPC Lambda + EC2)을 건드리지 않은 채로 새로운 Public Lambda + S3 환경을 별도로 만들었다. 크롤링이 정상 동작하는지, 데이터가 S3에 제대로 쌓이는지 충분히 검증했다.

**2단계 — Route 53 가중치 라우팅으로 단계적 전환**

Route 53의 가중치(Weighted) 라우팅 기능을 활용했다. 같은 도메인에 Blue와 Green 두 개의 레코드를 등록하고, 가중치 비율을 조정해 트래픽을 조금씩 옮기는 방식이다. Blue 90 / Green 10으로 시작해 문제가 없으면 50/50, 최종적으로 0/100으로 완전 전환. 문제가 생기면 가중치만 되돌리면 즉시 롤백된다.

**3단계 — Blue 환경 정리**

Green으로 완전히 전환하고 안정화를 확인한 뒤, Blue 환경이었던 VPC, NAT Gateway, EC2를 제거했다.

인프라를 크게 바꾸는 게 처음에는 두려웠는데, Blue-Green 방식은 언제든 되돌릴 수 있다는 안전망을 만들어줘서 훨씬 과감하게 변경할 수 있었다.

# Step 3 — Supabase + Vercel, 운영비 0원

## 왜 또 바꿨나

Step 2에서 NAT Gateway 비용 문제는 해결했지만, AWS Lambda와 S3도 사용량이 쌓이면 비용이 발생한다. Free Tier 한도를 넘으면 조금씩이라도 청구가 되는 구조다. 개인 프로젝트를 장기적으로 운영하려면 비용 부담이 없어야 한다는 결론을 내렸다. 목표는 단순했다. **월 운영비 0원.**

## Supabase + Vercel 조합

**Supabase**

PostgreSQL 기반의 BaaS(Backend as a Service)로, AWS RDS처럼 관계형 DB를 쓸 수 있으면서 사용자 인증(Auth) 기능까지 내장되어 있다. Free Tier에서 500MB DB와 월 50,000 MAU까지 무료다. 기존에 S3에 파일 형태로 저장하던 데이터를 PostgreSQL로 옮겼더니 조회와 필터링이 훨씬 편해졌다.

**Vercel**

Next.js 프론트엔드 배포에 최적화된 플랫폼이다. GitHub에 푸시하면 자동으로 빌드·배포되고, Serverless Functions와 Cron Jobs도 Free Tier에서 쓸 수 있다. 기존에 AWS EventBridge + Lambda로 처리하던 크롤링 스케줄링을 Vercel Cron Jobs로 대체했다.

**AWS Route 53**

도메인(dig-em.com) 관리는 Route 53을 계속 사용한다. 도메인 비용은 연간 고정이라 월별 추가 비용이 없다.

## 전환 결과

| 항목 | Step 2 | Step 3 |
|---|---|---|
| DB | S3 (파일 저장) | Supabase (PostgreSQL) |
| 프론트엔드 | - | Vercel (Next.js) |
| 크롤링 스케줄러 | AWS EventBridge | Vercel Cron Jobs |
| 월 운영비 | 소액 발생 | **0원** |

이 과정에서 배운 건 **"AWS가 항상 정답이 아니다"** 라는 것. Route 53처럼 AWS가 잘하는 영역은 유지하고, DB와 배포처럼 Free Tier가 충분한 영역은 전문 플랫폼에 위임하는 하이브리드 전략이 개인 프로젝트에서는 훨씬 실용적이었다.

# AI 로컬라이징 파이프라인

## 왜 이게 필요했나

Pitchfork, Resident Advisor 같은 해외 음악 매체의 평론은 국내에서 접근하기 쉽지 않다. 영어로 작성되어 있고 음악 전문 용어와 비유적 표현이 많아, 일반 번역기로는 문맥이 깨지는 경우가 많다.

이 서비스의 핵심 가치는 두 가지다.

- 전문 용어가 많은 음악 평론을 **문맥을 유지한 채** 한국어로 아카이빙한다.
- 그 과정이 **사람 손 없이 자동으로** 이루어진다.

## 파이프라인 구조

```
[스케줄러] Vercel Cron Jobs (주기적 실행)
    ↓
[크롤링] Vercel Serverless Function / AWS Lambda
    ↓ 영문 원문 수집
[번역·요약] Gemini API
    ↓ 한국어 번역 + 요약
[저장] Supabase (PostgreSQL)
    ↓
[서비스] dig-em.com (Next.js)
```

각 단계가 독립적으로 동작하며, 특정 단계에서 오류가 생겨도 다음 실행 사이클에서 재처리할 수 있는 구조다.

## Gemini API — 프롬프트 설계가 핵심

단순히 번역 API를 붙이는 것과는 다르게 접근했다. 음악 평론은 장르 용어, 아티스트명, 악기명, 비유적 표현이 뒤섞여 있어 프롬프트를 어떻게 설계하느냐가 결과 품질을 결정한다.

신경 쓴 부분들은 다음과 같다.

- **고유 명사는 원문 유지:** 장르명(Shoegaze, Bossa Nova 등), 아티스트명, 악기명은 번역하지 않고 그대로 사용
- **직역보다 의미 전달 우선:** 문장 구조를 그대로 옮기기보다 한국어 독자가 자연스럽게 읽을 수 있도록 재구성
- **평론 문체 유지:** 주관적 표현, 감상적 서술 등 평론 특유의 어조를 살리도록 지시

이런 방향으로 프롬프트를 다듬은 결과, 단순 번역보다 훨씬 자연스러운 한국어 평론이 나왔다.

## 향후 계획

지금까지는 데이터를 모으는 데 집중했다면, 다음 단계는 쌓인 데이터를 활용하는 것이다. 유저별 청취 이력과 평론 데이터를 결합해 취향에 맞는 음악 평론을 추천하는 알고리즘을 도입할 계획이다.

# 마치며

**아키텍처는 처음부터 완벽할 수 없다.** Step 1에서 Step 3까지 세 번 구조를 바꿨는데, 처음 설계가 틀렸던 게 아니라 운영하면서 발견한 문제를 고쳐나간 결과다. 설계-배포-운영-개선 사이클을 반복하는 게 실제 서비스 개발의 모습이라는 걸 몸으로 경험했다.

**안전망이 있으면 과감하게 변경할 수 있다.** Blue-Green 배포처럼 언제든 되돌릴 수 있는 구조를 만들어두면, 인프라를 통째로 교체하는 것도 두렵지 않다.

**AI API는 붙이는 것보다 프롬프트 설계가 더 중요하다.** Gemini API 연결 자체는 어렵지 않다. 음악 평론이라는 도메인 특성을 반영해 프롬프트를 설계했을 때 비로소 쓸 만한 결과물이 나왔다.

엔드 투 엔드 사이클을 직접 경험하고, 현재도 실제 유저가 쓰는 서비스로 운영 중이라는 점이 이 프로젝트에서 가장 의미 있는 부분이다.
