# 들어가며

CJ ENM에서 아르바이트를 하면서 음악 메타데이터를 수집하고 정리하는 일을 했습니다. 매일 반복되는 크롤링 작업을 보면서 "이걸 자동화하면 어떨까?"라는 생각이 계속 들었습니다. 그 경험이 이 프로젝트의 출발점입니다.

단순히 "돌아가는 것"을 목표로 하지 않았습니다. 아이디어를 구상하고, 설계하고, 직접 배포해 실제 서비스로 운영하고, 문제가 생기면 고치는 엔드 투 엔드(End-to-End) 사이클 전체를 경험해보고 싶었습니다.

---

# 서비스 소개

**[dig-em.com](https://dig-em.com)** — 음악 메타데이터 수집 및 아카이빙 서비스입니다.

Pitchfork 같은 해외 음악 전문 매체의 평론을 자동으로 수집하고, Gemini API로 번역·요약해서 아카이빙합니다. 한 번 파이프라인을 세팅해두면 사람이 개입하지 않아도 데이터가 꾸준히 쌓이는 구조입니다.

핵심 기술 스택은 아래와 같습니다.

- **프론트엔드:** Next.js (Vercel)
- **DB / 인증:** Supabase (PostgreSQL)
- **크롤링 / 자동화:** AWS Lambda, Vercel Cron Jobs
- **AI 번역:** Gemini API
- **도메인:** AWS Route 53

# 아키텍처가 세 번 바뀌었습니다

이 프로젝트에서 가장 많이 배운 부분이 여기입니다. 처음 설계한 구조가 정답이 아니었고, 운영하면서 문제를 발견하고, 고치고, 다시 개선하는 과정을 반복했습니다.

---

# Step 1 — VPC Isolation 기반 초기 설계

## 구조

처음 설계는 보안을 최우선으로 생각했습니다. Lambda 함수를 VPC(Virtual Private Cloud)의 Private Subnet 안에 배치하고, EC2를 스토리지로 사용하는 구조였습니다.

```
크롤러 (Lambda, VPC Private Subnet)
    ↓
NAT Gateway (외부 인터넷 접근을 위한 관문)
    ↓
외부 사이트 (크롤링 대상)
    ↓
EC2 (수집 데이터 저장)
```

VPC는 AWS 안에 격리된 가상 네트워크입니다. Private Subnet에 Lambda를 두면 외부 인터넷에서 직접 접근할 수 없어 보안상 안전합니다. 여기까지는 좋은 설계처럼 보였습니다.

## 문제 발생 — NAT Gateway 비용 폭탄

그런데 청구서를 확인하고 당황했습니다. 예상보다 훨씬 많은 비용이 나오고 있었습니다.

원인은 NAT Gateway였습니다. VPC Private Subnet 안에 있는 Lambda가 외부 인터넷(크롤링 대상 사이트)에 접근하려면 반드시 NAT Gateway를 거쳐야 합니다. NAT Gateway의 요금 구조는 두 가지로 구성됩니다.

- **시간당 고정 요금**: NAT Gateway가 켜져 있는 시간만큼 고정으로 부과
- **데이터 전송 요금**: NAT Gateway를 통해 오가는 데이터 양에 비례해 부과

크롤링은 외부 사이트에 요청을 보내고 대량의 HTML/데이터를 받아오는 작업입니다. 일반적인 웹 서비스와 달리 외부로 나가는 트래픽이 많고, 받아오는 데이터 양도 상당합니다. 이 특성 때문에 데이터 전송 요금이 빠르게 쌓였습니다.

설계할 때 보안 측면만 생각하고 비용 구조를 제대로 따져보지 않은 것이 문제였습니다. **크롤링처럼 외부 트래픽이 많은 워크로드에 VPC + NAT Gateway 조합은 맞지 않습니다.** Lambda를 VPC 밖으로 꺼내는 것이 비용과 구조 모두에서 더 나은 선택이라는 결론을 내렸습니다.

# Step 2 — Public Lambda + S3, 그리고 Blue-Green 배포

## 무엇을 바꿨나

NAT Gateway 비용 문제를 해결하기 위해 두 가지를 변경하기로 했습니다.

- **Lambda를 VPC 밖으로 꺼낸다.** VPC 안에 있을 이유가 없으니 Public 환경으로 이동해 NAT Gateway를 제거합니다.
- **EC2 스토리지를 S3로 교체한다.** EC2는 인스턴스가 켜져 있는 내내 비용이 발생하지만, S3는 저장된 용량과 요청 수에 따라만 요금이 부과되어 훨씬 저렴합니다.

## 이미 서비스가 운영 중이었다

구조를 바꾸는 것 자체는 어렵지 않습니다. 문제는 이 시점에 이미 실제 사용자가 있는 서비스가 운영 중이었다는 것입니다. 인프라를 교체하는 동안 서비스가 다운되면 안 됐습니다. 이때 적용한 것이 **Blue-Green 배포** 전략입니다.

## Blue-Green 배포란?

Blue-Green 배포는 기존 환경(Blue)을 유지한 채로 새로운 환경(Green)을 별도로 구축하고, 준비가 완료되면 트래픽을 전환하는 방식입니다. 언제든 Blue로 되돌릴 수 있어 리스크가 낮습니다.

```
[전환 전]
사용자 → Route 53 → Blue (VPC Lambda + EC2)   100%
                   Green (Public Lambda + S3)    0%

[단계적 전환]
사용자 → Route 53 → Blue   70%
                   Green   30%

[전환 완료]
사용자 → Route 53 → Blue    0%
                   Green  100%
```

**1단계 — Green 환경 구축 및 검증**

기존 Blue 환경(VPC Lambda + EC2)을 건드리지 않은 채로, 새로운 Public Lambda + S3 환경을 별도로 만들었습니다. 크롤링이 정상 동작하는지, 데이터가 S3에 제대로 쌓이는지 충분히 검증했습니다.

**2단계 — Route 53 가중치 라우팅으로 단계적 전환**

Route 53의 가중치(Weighted) 라우팅 기능을 활용했습니다. 같은 도메인에 Blue와 Green 두 개의 레코드를 등록하고, 가중치 비율을 조정해 트래픽을 조금씩 옮기는 방식입니다. Blue 90 / Green 10으로 시작해 문제가 없으면 50/50, 최종적으로 0/100으로 완전 전환했습니다. 문제가 생기면 가중치를 원래대로 되돌리기만 하면 즉시 롤백됩니다.

**3단계 — Blue 환경 정리**

Green으로 완전히 전환하고 안정화를 확인한 뒤, Blue 환경이었던 VPC, NAT Gateway, EC2를 제거했습니다.

인프라를 크게 바꾸는 것이 처음에는 두려웠습니다. Blue-Green 방식은 언제든 되돌릴 수 있다는 안전망을 만들어줘서, 훨씬 과감하게 변경할 수 있었습니다.

# Step 3 — Supabase + Vercel, 운영비 0원

## 왜 또 바꿨나

Step 2에서 NAT Gateway 비용 문제는 해결했지만, AWS Lambda와 S3도 사용량이 쌓이면 비용이 발생합니다. Free Tier 한도를 넘으면 조금씩이라도 청구가 되는 구조입니다. 개인 프로젝트를 장기적으로 운영하려면 비용 부담이 없어야 한다는 결론을 내렸습니다. 목표는 단순했습니다. **월 운영비 0원.**

## Supabase + Vercel 조합

**Supabase**

Supabase는 PostgreSQL 기반의 BaaS(Backend as a Service)입니다. AWS RDS처럼 관계형 DB를 사용할 수 있으면서, 사용자 인증(Auth) 기능까지 내장되어 있습니다. Free Tier에서 500MB DB와 월 50,000 MAU까지 무료로 제공합니다. 기존에 S3에 파일 형태로 저장하던 데이터를 Supabase PostgreSQL로 옮겼더니, 데이터 조회와 필터링이 훨씬 편리해졌습니다.

**Vercel**

Vercel은 Next.js 프론트엔드를 배포하기에 최적화된 플랫폼입니다. GitHub에 코드를 푸시하면 자동으로 빌드·배포되고, Serverless Functions와 Cron Jobs도 Free Tier에서 사용할 수 있습니다. 기존에 AWS EventBridge + Lambda로 처리하던 크롤링 스케줄링을 Vercel Cron Jobs로 대체했습니다.

**AWS Route 53**

도메인(dig-em.com) 관리는 Route 53을 계속 사용합니다. 도메인 비용은 연간 고정이라 월별 추가 비용이 발생하지 않습니다.

## 전환 결과

| 항목 | Step 2 | Step 3 |
|---|---|---|
| DB | S3 (파일 저장) | Supabase (PostgreSQL) |
| 프론트엔드 | - | Vercel (Next.js) |
| 크롤링 스케줄러 | AWS EventBridge | Vercel Cron Jobs |
| 월 운영비 | 소액 발생 | **0원** |

이 과정에서 배운 것은 **"AWS가 항상 정답이 아니다"** 라는 것입니다. Route 53처럼 AWS가 잘하는 영역은 유지하고, DB와 배포처럼 Free Tier가 충분한 영역은 전문 플랫폼에 위임하는 하이브리드 전략이 개인 프로젝트에서는 훨씬 실용적이었습니다.

# AI 로컬라이징 파이프라인

## 왜 이게 필요했나

Pitchfork, Resident Advisor 같은 해외 음악 매체의 평론은 국내에서 접근하기 쉽지 않습니다. 영어로 작성되어 있고, 음악 전문 용어와 비유적 표현이 많아 일반 번역기로는 문맥이 깨지는 경우가 많습니다.

이 서비스의 핵심 가치는 두 가지입니다.

- 전문 용어가 많은 음악 평론을 **문맥을 유지한 채** 한국어로 아카이빙한다.
- 그 과정이 **사람 손 없이 자동으로** 이루어진다.

## 파이프라인 구조

```
[스케줄러] Vercel Cron Jobs (주기적 실행)
    ↓
[크롤링] Vercel Serverless Function / AWS Lambda
    ↓ 영문 원문 수집
[번역·요약] Gemini API
    ↓ 한국어 번역 + 요약
[저장] Supabase (PostgreSQL)
    ↓
[서비스] dig-em.com (Next.js)
```

각 단계가 독립적으로 동작하며, 특정 단계에서 오류가 생겨도 다음 실행 사이클에서 재처리할 수 있는 구조입니다.

## Gemini API 활용 — 프롬프트 설계가 핵심

단순히 번역 API를 붙이는 것과는 다르게 접근했습니다. 음악 평론은 장르 용어, 아티스트명, 악기명, 비유적 표현이 뒤섞여 있어 프롬프트를 어떻게 설계하느냐가 결과 품질을 결정합니다.

프롬프트 설계 시 신경 쓴 부분들입니다.

- **고유 명사는 원문 유지:** 장르명(Shoegaze, Bossa Nova 등), 아티스트명, 악기명은 번역하지 않고 그대로 사용
- **직역보다 의미 전달 우선:** 문장 구조를 그대로 옮기는 것보다 한국어 독자가 자연스럽게 읽을 수 있는 문장으로 재구성
- **평론 문체 유지:** 주관적 표현, 감상적 서술 등 평론 특유의 어조를 살리도록 지시

이런 방향으로 프롬프트를 다듬은 결과, 단순 번역보다 훨씬 자연스러운 한국어 평론이 나왔습니다.

## 향후 계획

지금까지는 데이터를 모으는 데 집중했다면, 다음 단계는 쌓인 데이터를 활용하는 것입니다. 유저별 청취 이력과 평론 데이터를 결합해 취향에 맞는 음악 평론을 추천하는 알고리즘을 도입할 계획입니다.

# 마치며

**아키텍처는 처음부터 완벽할 수 없습니다.** Step 1에서 Step 3까지 세 번 구조를 바꿨습니다. 처음 설계가 틀렸던 게 아니라, 운영하면서 발견한 문제를 고쳐나간 결과입니다. 설계-배포-운영-개선의 사이클을 반복하는 것이 실제 서비스 개발의 모습이라는 것을 몸으로 경험했습니다.

**안전망이 있으면 과감하게 변경할 수 있습니다.** Blue-Green 배포처럼 언제든 되돌릴 수 있는 구조를 만들어두면, 인프라를 통째로 교체하는 것도 두렵지 않습니다.

**AI API는 붙이는 것보다 프롬프트 설계가 더 중요합니다.** Gemini API를 단순히 연결하는 것은 어렵지 않습니다. 음악 평론이라는 도메인 특성을 반영해 프롬프트를 설계했을 때 비로소 쓸 만한 결과물이 나왔습니다.

엔드 투 엔드 사이클을 직접 경험하고, 현재도 실제 사용자가 이용하는 서비스로 운영되고 있다는 점이 이 프로젝트에서 가장 의미 있는 부분입니다.
