# Step 2 — Public Lambda + S3로의 전환

## 무엇을 바꿨나

NAT Gateway 비용 문제를 해결하기 위해 두 가지를 변경하기로 했습니다.

- **Lambda를 VPC 밖으로 꺼낸다.** VPC 안에 있을 이유가 없으니, Public 환경으로 이동해 NAT Gateway를 제거합니다.
- **EC2 스토리지를 S3로 교체한다.** EC2는 인스턴스가 켜져 있는 내내 비용이 발생하지만, S3는 저장된 용량과 요청 수에 따라만 요금이 부과되어 훨씬 저렴합니다.

## 문제: 이미 서비스가 운영 중이었다

구조를 바꾸는 것 자체는 어렵지 않습니다. 문제는 이 시점에 이미 실제 사용자가 있는 서비스가 운영 중이었다는 것입니다. 인프라를 교체하는 동안 서비스가 다운되면 안 됐습니다.

이때 적용한 것이 **Blue-Green 배포** 전략입니다.

## Blue-Green 배포란?

Blue-Green 배포는 기존 환경(Blue)을 유지한 채로 새로운 환경(Green)을 별도로 구축하고, 준비가 완료되면 트래픽을 전환하는 방식입니다. 언제든 Blue로 되돌릴 수 있어 리스크가 낮습니다.

```
[전환 전]
사용자 → Route 53 → Blue (VPC Lambda + EC2)   100%
                   Green (Public Lambda + S3)    0%

[단계적 전환]
사용자 → Route 53 → Blue   70%
                   Green   30%

[전환 완료]
사용자 → Route 53 → Blue    0%
                   Green  100%
```

## 진행 순서

**1단계 — Green 환경 구축 및 검증**

기존 Blue 환경(VPC Lambda + EC2)을 건드리지 않은 채로, 새로운 Public Lambda + S3 환경을 별도로 만들었습니다. 크롤링이 정상 동작하는지, 데이터가 S3에 제대로 쌓이는지 충분히 검증했습니다.

**2단계 — Route 53 가중치 라우팅으로 단계적 전환**

Route 53의 가중치(Weighted) 라우팅 기능을 활용했습니다. 같은 도메인에 Blue와 Green 두 개의 레코드를 등록하고, 가중치 비율을 조정해 트래픽을 조금씩 옮기는 방식입니다.

예를 들어 가중치를 Blue 90 / Green 10으로 설정하면 전체 트래픽의 10%만 Green으로 흘러갑니다. 문제가 없으면 50/50으로 조정하고, 최종적으로 0/100으로 완전 전환합니다. 문제가 생기면 가중치를 원래대로 되돌리기만 하면 즉시 롤백됩니다.

**3단계 — Blue 환경 정리**

Green으로 완전히 전환하고 안정화를 확인한 뒤, Blue 환경이었던 VPC, NAT Gateway, EC2를 제거했습니다.

## 결과

- NAT Gateway 제거로 비용 대폭 절감
- 전환 과정에서 서비스 중단 시간 0초 (Zero Downtime)
- S3 Data Lake로 데이터 관리가 유연해짐

## 느낀 점

인프라를 크게 바꾸는 것이 처음에는 두려웠습니다. "잘못되면 서비스가 다운된다"는 걱정이 있었기 때문입니다. Blue-Green 방식은 그 두려움을 없애줍니다. 언제든 되돌릴 수 있다는 안전망이 있으면, 훨씬 과감하게 변경할 수 있습니다.
