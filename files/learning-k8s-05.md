## 1. 디플로이먼트(Deployment) 업데이트 전략
애플리케이션의 변경 사항을 반영할 때 서비스 중단을 최소화하기 위해 다양한 배포 전략을 사용한다.

### 1) 주요 배포 방식
* **Recreate (재생성)**: 기존 버전의 파드를 모두 종료한 후 새 버전의 파드를 일괄 생성하는 방식이다. 업데이트 속도는 빠르지만 일시적인 서비스 중단(다운타임)이 발생한다.
* **RollingUpdate (롤링 업데이트)**: 쿠버네티스의 기본 전략으로, 새 파드를 하나씩 늘리고 기존 파드를 하나씩 줄여가며 배포한다. 서비스 중단 없이 안정적이지만 전체 완료까지 시간이 다소 소요된다.
    - **maxSurge**: 업데이트 중 의도한 레플리카 수보다 초과하여 생성할 수 있는 파드의 최대 개수를 설정한다.
    - **maxUnavailable**: 업데이트 중 사용할 수 없는 상태가 되어도 무방한 파드의 최대 개수를 설정한다.
* **Blue/Green (블루/그린)**: 이전 버전(Blue)과 새 버전(Green)을 동시에 모두 띄워놓고 트래픽을 한꺼번에 전환하는 방식이다. 빠른 복구가 가능하지만 자원 소모가 두 배로 발생한다.
* **Canary (카나리)**: 새 버전에 트래픽의 일부(예: 10%)만 먼저 흘려보내 테스트를 거친 후 점진적으로 트래픽을 늘려가는 방식이다. 사용자 반응을 살피며 배포할 수 있다.

### 2) 업데이트 상세 파라미터
* **minReadySeconds**: 파드가 Ready 상태가 된 후 기동 완료로 판단하기까지 기다리는 최소 시간이다.
* **revisionHistoryLimit**: 롤백을 위해 유지할 이전 레플리카셋의 기록 개수를 지정한다.
* **progressDeadlineSeconds**: 업데이트 진행 시 타임아웃 시간을 설정하며, 시간 내 완료되지 않으면 자동으로 실패 처리된다.

## 2. 데몬셋 (DaemonSet)
클러스터 내의 모든(혹은 특정) 노드에 파드를 하나씩 배치하여 실행하는 리소스다.

* **주요 용도**: 각 노드의 로그를 수집하는 Fluentd나 리소스 상태를 모니터링하는 Prometheus Exporter 등에 주로 활용된다.
* **업데이트 전략**:
    - **OnDelete**: 매니페스트가 수정되어도 기존 파드는 유지되며, 파드가 수동으로 삭제되거나 노드 재기동 시에만 새 버전이 반영된다.
    - **RollingUpdate**: 디플로이먼트와 유사하게 점진적으로 업데이트를 수행한다. 단, 노드당 파드가 하나뿐이므로 `maxSurge` 설정은 사용할 수 없다.

## 3. 스테이트풀셋 (StatefulSet)
데이터베이스와 같이 상태를 보존해야 하는(Stateful) 애플리케이션 관리에 최적화된 리소스다.

* **특징**:
    - **고유 식별자**: 파드 이름 뒤에 임의의 해시값이 아닌 0, 1, 2와 같은 순차적인 인덱스가 부여되며, 재생성 시에도 이름이 유지된다.
    - **순차적 관리**: 파드의 생성과 삭제가 지정된 순서대로 엄격하게 진행된다.
* **영구 볼륨 관리 (Storage)**:
    - `volumeClaimTemplates`를 통해 각 파드마다 독립적인 영구 볼륨 클레임(PVC)을 자동으로 할당한다.
    - 스테이트풀셋 리소스를 삭제하더라도 데이터 보호를 위해 생성된 영구 볼륨(PV)은 자동으로 삭제되지 않으므로 수동 관리가 필요하다.
* **업데이트 방식**: 디플로이먼트와 마찬가지로 `OnDelete`와 `RollingUpdate`를 지원하며, 롤링 업데이트 시에는 인덱스가 높은 파드부터 하나씩 순차적으로 진행된다.

## 4. 잡 (Job) 및 크론잡 (CronJob)
* **Job**: 특정 작업을 수행하고 완료되면 종료되는 일회성 리소스다. 지정된 횟수만큼 성공적으로 실행되는 것을 보장한다.
* **CronJob**: 정해진 시간에 주기적으로 잡을 실행할 때 사용하며, 데이터 백업이나 정기적인 알림 발송 업무에 적합하다.
