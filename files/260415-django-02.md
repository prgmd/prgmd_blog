# Template System

## 1. Django Template System

### 1.1 Django Template System이란?
> 파이썬 데이터(Context)를 HTML(Template)과 결합해 동적인 웹페이지를 만드는 도구.

핵심은 **'로직(Python)'과 '표현(HTML)'을 분리**한다는 개념이다. 개발자는 데이터만 잘 넘겨주고, 디자이너는 화면만 잘 만들어두면 Django가 알아서 둘을 합쳐주는 식. 네이버 뉴스를 떠올려보자. 모든 기사 페이지는 헤더, 폰트, 광고 위치가 똑같지만(이게 **Template**), 기사마다 제목, 내용, 기자가 다 다르다(이게 **Context**). 이렇게 나누는 이유는 간단하다. 이게 훨씬 효율적이기 때문. 페이지 틀에 데이터를 동적으로 결합해 수만 개 페이지를 단 몇 개만으로 해결할 수 있다.

#### View에서 데이터 보내기 (`views.py`)

`render` 함수의 세 번째 인자 `context`를 활용.

```python
# views.py
def index(request):
    # 딕셔너리 형태로 데이터를 담는다
    context = {
        'name': 'Jane', 
    }
    return render(request, 'articles/index.html', context)
```

(해당 HTML에서 활용할 데이터를 Dict 형태로 넘겨준다. 반대로 말하면 아무것도 넘겨주지 않으면 해당 HTML은 데이터를 사용하지 못함)

#### Template에서 데이터 받기 (`index.html`)

Django 템플릿 언어(DTL)의 변수 출력 문법은 **`{{ }}`** (중괄호 두 개)다.

```html
<body>
  <h1>Hello, {{ name }}!</h1>
</body>
```

이렇게 하면 웹 브라우저에서 원하는 이름으로 마음껏 바꿔서 출력이 가능하다. 즉, 템플릿은 냅두고 데이터에 따라 다르게 출력이 가능. 동적 웹페이지가 된 셈이다.

## 2. DTL (Django Template Language)

하지만 HTML은 Python을 모르기 때문에 DTL 언어를 맞춰줘야 한다. DTL이 있으면 템플릿에서도 **조건, 반복, 변수와 같은 프로그래밍적 기능을 가능케 해준다**. (물론 복잡한 계산은 불가능. 사실 웬만해서는 View 단에서 모두 가공을 마친 뒤 결과값만 Template에 보내주는 것이 Django의 철학이다) 실제로 DTl의 종류는 엄청나게 많다. 필요할 때마다 [Django 공식 문서](https://docs.djangoproject.com/en/5.2/ref/templates/builtins/)를 검색해서 보는 습관을 추천.

| 종류 | 문법 | 용도 |
| :--- | :--- | :--- |
| **Variable** | `{{ variable }}` | 데이터를 화면에 출력 |
| **Filters** | `{{ var\|filter }}` | 데이터를 가공하여 출력 |
| **Tags** | `{% tag %}` | 조건문, 반복문 등 로직 실행 |
| **Comments** | `{# #}` 또는 `{% comment %}` | 주석 처리 (화면에 안 보임) |

※ 주석의 경우 화면에 보이지 않지만, 브라우저 소스를 보면 전부 보이므로 이 부분 알아둘 것.

### 2.1 Variable (변수)
`render` 함수의 딕셔너리 `key` 값 = 템플릿 변수명

* **기본 출력:** `{{ name }}`
* **속성 접근:** `{{ user.name }}` 처럼 `dot(.)`을 사용하여 객체의 속성이나 딕셔너리의 키에 접근할 수 있다. (참고로 파이썬의 `user['name']` 대신 점을 찍는다는 점에 유의하라.)

### 2.2 Filters (필터)
데이터를 출력하기 전에 살짝 변형. `|`를 사용하며, 안에 띄어쓰기가 들어가면 오류 발생.

* **예시:** `{{ picked|length }}` (글자 수나 리스트 길이를 잰다)
* **체이닝:** `{{ name|lower|truncatewords:30 }}` 처럼 여러 개를 이어 붙일 수도 있다.

### 2.3 Tags (태그)
반복문, 조건문 같은 제어 흐름을 설정. 일부 태그는 **시작 태그와 종료 태그(`end...`)가 필요하다.**

#### **반복문 (for)**
```html
<ul>
  {% for food in foods %}
    <li>{{ food }}</li>
  {% endfor %}
</ul>
```

#### **조건문 (if)**
```html
{% if foods|length == 0 %} # 조건문이 참이면
  <p>메뉴가 소진되었습니다.</p>
{% else %} # 조건문이 거짓이면
  <p>아직 메뉴가 남았습니다.</p>
{% endif %}
```

### 2.4 실전 예제

슬라이드에 나온 국밥 예제를 코드로 정리했다. 실무에서는 이런 식으로 **URL -> View -> Template**의 흐름이 완성된다.

> **urls.py** : `path('dinner/', views.dinner),`
> **views.py** : `random.choice(foods)`로 하나를 뽑아 `context`에 담아 보낸다.
> **template** : 뽑힌 메뉴(`picked`)와 전체 리스트(`foods`)를 요리조리 보여준다.

```python
# views.py (핵심 로직)
import random

def dinner(request):
    foods = ['국밥', '국수', '카레', '탕수육']
    picked = random.choice(foods)
    context = {
        'foods': foods,
        'picked': picked,
    }
    return render(request, 'articles/dinner.html', context)
```

## 3. 템플릿 상속

웹사이트를 만들다 보면 모든 페이지에 공통으로 들어가는 것들이 있는데, 상단 네비게이션 바, 푸터, **Bootstrap CDN** 등이 그렇다. 만약 페이지가 100개라 가정했을 때 모든 페이지에 부트스트랩 링크를 일일이 복사해서 넣어야 한다면 유지보수가 매우 피곤해질 것.

### 3.1 템플릿 상속(Template Inheritance)이란?

> 여러 템플릿이 **공통 요소**를 공유하고, 각 페이지마다 달라지는 부분만 **재정의(Override)** 할 수 있게 해주는 기능.

* **부모 템플릿:** 전체적인 뼈대(Skeleton)를 담당한다.
* **자식 템플릿:** 부모의 뼈대를 그대로 물려받고, 특정 '블록'만 자신의 내용으로 채운다.

### 3.2 상속의 핵심 DTL 태그

상속 구현에는 두 가지를 기억해야 한다.

1. **`{% extends '...' %}`**
    * **"부모 템플릿"**을 선언하는 태그다. (일종의 어디 출신인지 알리는 셈)
    * 반드시 자식 템플릿의 **최상단**에 위치해야 한다. 두 개 이상 사용은 불가하다.
      * 만약 그 위에 다른 코드를 작성하면 상속 요청이 무시됨.

2. **`{% block ... %}` & `{% endblock %}`**
    * 부모에서는 **"여기 내용 바뀔 수 있어"**라고 자리를 비워두는 용도.
    * 자식에서는 **"이 빈자리를 내 내용으로 채울게"**라고 재정의하는 용도.

### 3.3 실전 예제

#### 부모 뼈대 만들기 (`base.html`)
모든 페이지의 공통 규격을 만드는 파일. 파일명이 꼭 `base.html`일 필요는 없지만, 관례적으로 이렇게 부른다.

```html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <title>My Django App</title>
  </head>
<body>
  <nav>공통 네비게이션 바</nav>

  {% block content %}
    {% endblock content %}

  <footer>공통 푸터</footer>
</body>
</html>
```

#### 자식 템플릿에서 상속받기 (`index.html`)
이제 자식은 잡다한 HTML 태그를 다 버리고, 자기한테 필요한 알맹이만 챙기면 된다. (부모 측에서 `content`라고 이름 붙였으므로, 틀리지 않게 가져오는 것이 중요하다)

```html
{% extends 'articles/base.html' %}

{% block content %}
  <h1>여기는 메인 페이지입니다.</h1>
  <p>부모의 뼈대를 그대로 쓰고 알맹이만 바꿉니다.</p>
{% endblock content %}
```

## 4. HTML form / 데이터 전송

지금까지 서버가 클라이언트에게 데이터를 일방적으로 보여주는 법만 배웠다면, 이 파트는 사용자의 데이터를 입력받고 다루는 법. 그 수단이 바로 **HTML 'form' element**다. 여기서 form이란? 사용자 입력을 묶어 보내는 HTML 태그라고 보면 된다. 예를 들어 로그인을 할 때 우리가 아이디 따로, 비밀번호 따로 보내지 않듯 같이 사용되는 데이터를 묶어주는 것. 심지어 구글의 검색창도 단일 데이터처럼 보이지만 form으로 되어 있다. 아니 그냥 사용자 요청은 대개 form으로 감싸져 있다!

``` html
<form action="/login-process" method="POST">
  
  <div>
    <label for="userId">아이디:</label>
    <input type="text" id="userId" name="username" placeholder="아이디를 입력하세요">
  </div>

  <div>
    <label for="userPw">비밀번호:</label>
    <input type="password" id="userPw" name="password" placeholder="비밀번호를 입력하세요">
  </div>

  <button type="submit">로그인</button>

</form>
```

### 4.1 클라이언트-서버 구조

웹은 기본적으로 **Request(요청)**와 **Response(응답)**의 핑퐁 게임이다.
* **Client:** 나 이거 검색한다 (Request)
* **Server:** ㅇㅋ 여기 결과 드림 (Response)

이때 HTTP 요청을 서버에 보내는 가장 편리하고 대중적인 방법이 바로 **form**이다. 구글 검색창이나 네이버 로그인 화면도 거대한 form 태그 덩어리로 이뤄져 있다.

### 4.2 'form' Element
`form` 태그는 사용자로부터 할당된 데이터를 서버로 전송하는 운반책이다.

* **주요 속성:**
  * `action`: 데이터를 어디로 보낼 건지? (목적지 URL)
  * `method`: 어떤 방식으로 보낼 건지? (GET, POST 등)
* **내부 요소:** `input` 태그를 통해 텍스트, 패스워드, 체크박스 등 다양한 입력을 받는다.

### 4.3 실전 예제
네이버 검색창을 만들어보자. 네이버가 지정해둔 규격에 맞춰 데이터를 쏴주기만 하면 된다.

#### URL & View 설정
```python
# urls.py
path('search/', views.search),

# views.py
def search(request):
    return render(request, 'articles/search.html')
```

#### 검색창 만들기 (`search.html`)
네이버 검색 파라미터의 핵심 키값은 **`query`**다. 이 이름을 정확히 맞춰야 네이버가 알아듣는다. `id` 속성은 CSS나 자바스크립트가 식별하기 위한 용도고, 정말 중요한 건 `name` 속성. Django(혹은 네이버)는 `input`의 **`name`** 속성값을 키(Key)로 사용해 데이터를 식별한다. 만약 `name="query"`라고 적혀 있다면, 서버 주소창에는 `?query=검색어`라는 꼬리표가 붙게 된다. 만약 name이 없다면 값이 전달되지 않는다.

```html
{% extends 'articles/base.html' %}

{% block content %}
  <form action="https://search.naver.com/search.naver" method="GET">
    <label for="message">검색어 : </label>
    <input type="text" name="query" id="message">
    <input type="submit" value="Naver 검색">
  </form>
{% endblock content %}
```

만약 input에 `hello`라고 데이터를 입력하면 `http://127.0.0.1:8000/search?query=hello`가 된다.

![](https://velog.velcdn.com/images/paramad/post/23f12d2f-ad1c-460e-930f-b82b80df1154/image.png)

네이버에 hello을 입력한 경우

![](https://velog.velcdn.com/images/paramad/post/8c43153f-12bb-4788-afa3-8a8d48b34db9/image.png)

뭐가 다닥다닥 붙어있긴 한데, 기본적으로 `https://search.naver.com/search.naver?query=hello`와 같다. 

※ 지금은 `method="GET"` 방식을 사용했지만, 이 경우 주소창(Query String)에 데이터가 노출된다. 보안이 중요한 로그인 정보 같은 데이터는 나중에 배울 **POST** 방식을 사용해야 한다. GET은 내용이 보이는 한 장짜리 엽서고, POST는 봉투에 담긴 편지라고 보면 된다.

### 4.4 HTML form 핵심 속성

단순히 `form` 태그를 만드는 것보다 중요한 것은, 그 안에 들어가는 **속성(Attribute)**들을 정확히 이해하는 것. 속성을 잘 맞춰야 데이터를 원하는 곳으로 보낼 수 있다. 3가지 속성을 잘 알아야 한다 (목적지, 방식, 이름표라 보면 된다)

#### `action` & `method`

'어디로 어떻게 보낼지'에 대한 설정. `form` 태그의 가장 근본적인 속성이다.

* **`action` (목적지):**
  * 입력 데이터가 전송될 **URL을 지정**한다. 
  * 만약 이 값을 비워두면(`action=""`), 데이터는 **현재 페이지의 URL**로 다시 돌아온다.

* **`method` (전송 방식):**
    * 데이터를 어떤 HTTP 방식으로 보낼지 정의한다. 
    * 주요 방식으로는 **GET**과 **POST**가 있다.

#### `name` Attribute

많은 이들이 `id`와 `name`을 헷갈려 하지만, 서버 입장에서 중요한 것은 오직 **`name`**뿐이다. `id`는 문서(HTML) 내부에서 해당 요소를 찾기 위한 고유 주소로, 서버에 전송되지 않는다. 

* **역할:** 사용자가 입력한 데이터에 붙이는 **이름표(Key)**다.
* **중요성:** 서버는 `name` 속성에 설정된 값을 통해서만 사용자가 입력한 데이터에 접근할 수 있다. 
* **예시:** `<input name="query">`라고 적고 'hello'를 입력하면, 서버는 `"query라는 가방에 hello가 들어있군!"`이라고 인식한다.

#### Query String Parameters

사용자의 입력 데이터를 URL 주소에 파라미터를 통해 서버로 보내는 방법이다. 주로 GET 방식에서 사용된다.

* **구조:** `기본 URL?key=value&key=value`
* **구분자:**
  * **물음표(`?`):** 기본 URL과 데이터의 시작을 구분한다.
  * **앰퍼샌드(`&`):** 여러 개의 데이터(key=value 쌍)를 연결할 때 사용한다.

> **현실 예시:** `http://host:port/search?query=iphone&page=1`
> 서버는 이 주소를 보고 "iphone을 검색하고 싶어 하는군. 1페이지를 보여줘야겠다"라고 판단한다.

## 5. Throw, Catch 로직

위 실습에서 네이버로 데이터를 던져봤다면, 이제는 **장고 서버**로 직접 데이터를 받아 볼 차례다. 크게 두 단계로 나뉜다. 데이터를 던지는 `throw` 로직과, 그걸 받아서 처리하는 `catch` 로직이다.

### 5.1 Throw 로직
사용자가 데이터를 입력할 수 있는 페이지를 만드는 과정이다.

* **`urls.py`**: `path('throw/', views.throw),` 등록
* **`views.py`**: `throw.html`을 렌더링하는 단순 함수 작성
* **`throw.html`**: 핵심은 `form` 태그의 속성이다.
  * `action="/catch/"`: 데이터의 목적지를 우리가 만들 `catch` 주소로 설정한다.
  * `method="GET"`: 주소창을 통해 데이터를 실어 보낸다.
  * `<input name="message">`: 서버가 낚아챌 때 사용할 **이름표**를 붙인다.

### 5.2 Catch 로직
`throw`에서 던진 데이터를 받아서 화면에 보여주는 과정. 여기서 **`request` 객체**가 등장한다.

#### **HTTP request 객체란?**
Django 뷰 함수의 첫 번째 인자로 전달되는 이 객체에는 클라이언트가 보낸 모든 정보가 담겨 있다. `print(request.GET)`를 해보면 사용자가 보낸 데이터가 `QueryDict` 형태로 예쁘게 담겨 있는 것을 볼 수 있다. QueryDict는 유사 딕셔너리. 딕셔너리는 아니지만 비슷하게 사용할 수 있도록 Django에서 지원하는 타입이다.

#### **데이터 추출 및 처리 (views.py)**
```python
def catch(request):
    message = request.GET.get('message') # request.GET에서 'message'라는 이름표를 가진 데이터를 쏙 빼온다   
    context = { # 그걸 다시 context에 쏙 넣어줌
        'message': message,
    }
    return render(request, 'articles/catch.html', context)
```

`request.GET['message']`라고 직접 접근할 수도 있지만, 만약 해당 키가 없으면 장고는 에러를 출력. 이때 `get()` 메서드를 사용하면 `None`을 반환하며 대처할 수 있다. 

#### Throw - Catch 요청과 응답 흐름 정리

이 일련의 과정이 어떻게 돌아가는지 머릿속에 시뮬레이션을 돌려보자.

1.  **Throw 요청**: 사용자가 `/throw/` 주소로 접속하면 Django가 `throw` 뷰를 호출해 입력 폼을 보여준다.
2.  **데이터 제출**: 사용자가 폼에 "안녕!"이라고 적고 제출 버튼을 누른다.
3.  **Catch 요청**: 브라우저는 `/catch/?message=안녕!` 이라는 주소로 서버에 다시 요청을 보낸다.
4.  **데이터 처리**: `catch` 뷰 함수는 `request.GET.get('message')`를 통해 "안녕!"을 낚아챈다.
5.  **최종 응답**: 낚아챈 데이터를 담아 `catch.html`을 사용자에게 보여준다.

## 6. App URL mapping

프로젝트 초기에 앱이 하나일 때는 프로젝트의 `urls.py`에서 모든 것을 처리해도 문제가 없었지만, 앱이 2개, 3개 늘어나고 그 안에 기능이 여러개 생기다보니 이름도 겹치게 되고, `import views as article_views` 같은 괴상한 코드를 짜게 되거나, URL 패턴이 섞여 관리하기가 매우 까다롭다는 문제가 생김. 그래서 URL을 각자 앱에서 관리하자는 결론에 도달하게 됐다고 한다.

이해가 안 된다면, [브런치](https://brunch.co.kr/)에 누군가 글을 200개 올렸다고 가정하자. 브런치는 `https://brunch.co.kr/@계정명/게시글수`와 같은 URL을 사용하는데, 그러면 개발자가 이를 지켜보고 있다가 글이 올라옴녀 200개를 일일이 `urlpatterns = []`에 적어두고 있는걸까? 당연히 아닐 것이다!

### 6.1 URL Dispatcher

기존에는 프로젝트의 `urls.py`가 모든 요청을 일일이 분류. 하지만 변경된 구조에서는 프로젝트가 요청의 '앞부분'만 보고 해당 앱의 `urls.py`로 토스해 주는 방식을 취한다.

### 6.2 Variable Routing
URL의 일부에 변수를 포함시키는 기술. 값을 **View 함수의 인자(Argument)**로 전달해 로직에 사용된다.

#### Path Converter
URL 패턴에 다음과 같은 형식으로 작성.
> **`<path_converter:variable_name>`**

* **`path_converter`**: 변수 타입 지정. (str, int 등 5가지 지원)
* **`variable_name`**: 뷰 함수에서 받을 매개변수 이름.

#### 실전 예제

주소창에 `hello/john/`이라고 치면 "John님 안녕하세요!"라고 출력되도록 만들어보자.

먼저 `urls.py`에 문자열 변수를 받기 위해 `str` 컨버터를 사용.
```python
# urls.py
urlpatterns = [
    # <str:name> 자리에 들어오는 문자열이 name이라는 변수에 담긴다
    path('hello/<str:name>/', views.greeting),
]
```

그러면 views.py에서 이를 처리. **이 때, Path Converter에 쓴 변수명과 View 함수의 파라미터 이름은 반드시 일치해야 함.**

```python
# views.py
def greeting(request, name): # URL에서 넘어온 name을 인자로 받음
    context = {
        'name': name,
    }
    return render(request, 'articles/greeting.html', context)
```

또한 컨버터의 데이터 타입도 같아야 한다. 만약 `<int:num>`이라 저장했는데 `articles/abc/`라 입력하면 바로 **404 Page Not Found**가 출력됨.

* `127.0.0.1:8000/hello/John/` -> **"John님 안녕하세요!"**
* `127.0.0.1:8000/hello/Jane/` -> **"Jane님 안녕하세요!"**

이렇게 **단 하나의 URL 패턴으로 무한대의 이름에 응답할 수 있게 됐다.**

### 6.2 `include()` 함수
프로젝트 메인 `urls.py`에서 특정 앱의 URL 설정을 참조할 수 있도록 매핑하는 함수.

* **동작 원리:** URL의 일치하는 부분까지 잘라내고, **남은 문자열 부분**은 후속 처리를 위해 `include`된 앱의 `urls.py`로 전달.
* 내가 큰 분류는 해줄테니, 나머지는 앱 네가 직접 알아서 처리하도록. (앱 내 기능가지 전부 메인 `urls.py`가 관리하기는 불편하니)

#### 실전 예제

앱 폴더(`articles/`) 내부에 직접 `urls.py` 파일을 만듦. (자동으로 생성되지 않으니 직접 만들어야 한다!)

```python
# articles/urls.py
from django.urls import path
from . import views  # 현재 폴더(.)에서 views를 가져옴

urlpatterns = [
    path('index/', views.index),
    path('dinner/', views.dinner),
    # ... 나머지 articles 관련 URL들
]
```

#### 프로젝트 `urls.py`에 포함
메인 프로젝트 폴더(`firstpjt/`)의 `urls.py`를 수정.

```python
# firstpjt/urls.py
from django.contrib import admin
from django.urls import path, include  # include를 꼭 import 할 것

urlpatterns = [
    path('admin/', admin.site.urls),
    # 'articles/'로 시작하는 모든 요청은 articles 앱의 urls.py로 보낸다
    path('articles/', include('articles.urls')),
    # 'pages/'로 시작하는 모든 요청은 pages 앱의 urls.py로 보낸다
    path('pages/', include('pages.urls')),
]
```

1. 브라우저가 `/articles/index/` 요청을 보냄.
2. 프로젝트 `urls.py`가 앞에 붙은 `articles/`를 보고 `articles.urls` 담당이구나 하고 판단.
3. `articles/`를 떼어낸 나머지 **`index/`**만 앱의 `urls.py`로 넘김.
4. 앱의 `urls.py`에서 `index/` 패턴을 찾아 매칭되는 뷰 함수를 실행함.

## 7. Naming URL patterns

그러다보니... 기존 방식의 하드코딩된 주소를 사용하던 옛날에는 그래도 불편이 있었다. 만약 기껏 만든 서비스의 주소를 `/articles/`에서 `/blog/`로 바꾸려면 그 주소를 링크로 걸어둔 모든 HTML 파일을 찾아가 일일이 수정해야 했다. 그래서 URL에 이름을 지어주고, 그 이름만 기억하자는 것이 Naming URL의 철학.

### 7.1 Naming URL patterns
`path` 함수의 세 번째 인자로 **`name`** 키워드 인자를 사용하여 정의.

```python
# articles/urls.py
urlpatterns = [
    # 이제 이 경로는 'index'라는 이름으로 불린다.
    path('index/', views.index, name='index'),
    path('dinner/', views.dinner, name='dinner'),
    path('search/', views.search, name='search'),
]
```

### 7.2 DTL `url` tag
템플릿(HTML)에서 하드코딩된 주소 대신, 설정한 이름을 사용하여 실제 주소를 동적으로 생성.

* **문법:** `{% url 'url_name' arg1 arg2 %}`
* **특징:** 주어진 이름과 일치하는 **절대 경로 주소**를 반환한다. 이때, 태그 내 이름과 인자 사이에는 **쉼표를 쓰지 않는다.**

#### HTML 표기 변화
* **과거 (위험):** `<a href="/articles/dinner/">dinner</a>`
* **현재 (안전):** `<a href="{% url 'dinner' %}">dinner</a>`

이제 `urls.py`에서 주소를 `/lunch/`로 바꿔도, 템플릿은 이름(`'dinner'`)만 보고 바뀐 주소를 알아서 찾아간다.

#### Variable Routing이 포함된 경우
URL에 변수가 있다면 이름 뒤에 한 칸 띄우고 인자를 넘겨주면 된다.

* **urls.py:** `path('<int:num>/', views.detail, name='detail')`
* **Template:** `<a href="{% url 'detail' 1 %}">Article 1</a>`
    * 결과: `/articles/1/` 주소가 생성됨.

### 7.3 URL 이름 공간

다만 URL에 이름을 붙여 관리한다고 해도, `articles` 앱에도 `index`가 있고, `pages` 앱에도 `index`가 있다면 어디로 가야할지 정해줘야 함. 그래서 이름 앞에 **'이름 공간(Namespace)'**이라는 성씨를 붙여 구분. 코드의 유지보수성과 명확성을 챙길 수 있다.

#### `app_name`
각 앱의 `urls.py`에 **`app_name`** 변수를 설정하여 해당 앱만의 이름 공간을 지정.

```python
# articles/urls.py
app_name = 'articles' # 성씨 등록
urlpatterns = [
    path('index/', views.index, name='index'), # 이름은 여전히 index
]

# pages/urls.py
app_name = 'pages' # 다른 성씨 등록
urlpatterns = [
    path('index/', views.index, name='index'), # 이름이 겹쳐도 상관없다
]
```

`app_name`이 추가되면 DTL의 `url` 태그에서도 이를 반영해야 한다. 마치 "김철수", "이철수"라고 부르는 것과 같다. `:`(colon)을 사용해줄 것.

* **문법:** `{% url 'app_name:path_name' %}`
* **비유:** `성씨:이름` 구조로 호출.

#### HTML 반영 예시
```html
<a href="{% url 'index' %}">Home</a> 

<a href="{% url 'articles:index' %}">Home</a>
<a href="{% url 'articles:dinner' %}">Dinner</a>
```

#### 최종 링크 확인

이렇게 `app_name`을 쓰고 `url` 태그를 수정해도, 실제 브라우저에서 렌더링된 결과(`href="/articles/index/"`)는 변하지 않는다. 


## 8. 그 외 팁
### 8.1 추가 템플릿 경로 (DIRS) 설정
기본적으로 Django는 각 앱 폴더 내부의 `templates/` 폴더만 찾아본다. 다만 여러 앱이 공통으로 사용하는 `base.html` 같은 파일은 프로젝트 최상단(`BASE_DIR`)에 두고 싶을 때가 있음. 이럴때는 `settings.py`를 수정하면 된다. 다음과 같이 설정하면 앱 폴더 내부뿐만 아니라, 우리가 지정한 최상단 `templates/` 폴더에서도 파일을 찾는다.

* **설정 방법 (`settings.py`):**
```python
TEMPLATES = [
    {
        ...,
        'DIRS': [BASE_DIR / 'templates'], # 최상단 templates 폴더를 검색 경로에 추가
        'APP_DIRS': True,
        ...,
    },
]
```

> BASE_DIR이 뭔가요? `settings.py`에서 경로 지정을 편하게 하기 위해 최상단 지점을 지정해 둔 변수. `Path(__file__).resolve().parent.parent`로 주로 쓰여 있는데, `resolve()`는 경로를 가져오는 함수고, 여기에 부모 폴더로 두 번 이동한 것. 그렇게 되면 `manage.py`가 포함된 가장 루트 폴더가 나온다. 평소에는 이를 가리킨다.

### 8.2 DTL 사용 시 반드시 명심할 주의사항
DTL(Django Template Language)은 Python처럼 생겼을 뿐 Python이 아님. 템플릿의 목적은 '어떻게 보여줄 것인지'에 대해서고, 복잡한 계산은 반드시 View에서 처리하고 결과값만 넘겨주도록 하자.

### 8.3 URL의 Trailing Slashes (후행 슬래시)
HTTP 표준에서 `foo.com/bar`와 `foo.com/bar/`는 엄밀히 서로 다른 URL. 검색 엔진이나 트래픽 분석 도구는 이를 별개의 페이지로 인식하기도 한다. 그래서 혼동을 방지하기 위해 무조건 슬래시를 붙인다는 원칙을 고수한다. 만약 사용자가 슬래시 없이 요청을 보내도 장고는 똑똑하게 슬래시를 붙여서 다시 안내해주기는 하지만, 모든 프레임워크가 이렇지는 않으므로 다른 도구를 쓸 때는 해당 도구의 관례를 확인해야 한다.
