# Cookie & Session

## 1. HTTP 프로토콜의 기술적 배경과 설계 철학

### 1.1. HTTP의 정의와 역할
HTTP(HyperText Transfer Protocol)는 웹 브라우저와 서버가 리소스를 주고받기 위해 사용하는 애플리케이션 계층의 통신 규약이다. 모든 데이터 교환의 기초가 되며, 단순한 문서 전송을 넘어 REST API 통신, 멀티미디어 스트리밍, 실시간 데이터 교환의 표준으로 자리 잡았다.

### 1.2. 비 연결 지향 (Connectionless)

#### 설계 목적 및 동작 원리
서버는 클라이언트의 요청에 대해 응답을 보낸 후 즉시 물리적/논리적 연결을 끊는다. 이는 수많은 사용자가 동시에 접속하는 현대 웹 환경에서 서버의 메모리 점유와 네트워크 대역폭 자원을 효율적으로 관리하기 위함이다.

#### 기술적 파급 효과와 한계
- 장점: 연결 유지에 필요한 리소스를 절약하여 더 많은 동시 요청을 처리할 수 있는 고가용성을 확보한다.
- 단점: 매 요청마다 TCP 연결 수립 과정(3-Way Handshake)이 반복되어 통신 지연(Latency)이 발생할 수 있다. 이를 보완하기 위해 현대 웹에서는 Keep-Alive 헤더를 사용하여 일정 시간 동안 연결을 재사용하는 기술을 병행한다.

### 1.3. 무상태성 (Stateless)

#### 정의 및 기술적 의미
연결이 끊기는 순간 서버와 클라이언트 간의 통신이 종료되며, 이전 상태 정보를 서버가 전혀 저장하지 않는 특성이다. 각 요청은 독립적인 트랜잭션으로 취급된다.

#### 상태 유지 부재의 실무적 문제
- 사용자 식별 불가: 페이지를 이동할 때마다 서버는 사용자가 이전에 로그인했는지, 어떤 상품을 장바구니에 담았는지 알 수 없다.
- 연속성 결여: 동적인 웹 서비스 구현을 위해서는 사용자의 이전 활동 맥락(Context)을 파악하는 것이 필수적이나, HTTP 자체로는 이를 해결할 수 없다.

#### 전략적 이점과 확장성

서버가 클라이언트의 상태를 기억하지 않음으로써 '수평적 확장(Scale-out)'이 매우 용이해진다. 로드 밸런서 뒤에 위치한 수십 대의 서버 중 어떤 서버가 요청을 받더라도 이전 상태를 알 필요가 없으므로 아키텍처가 단순해지고 가용성이 극대화된다.

## 2. Cookie (쿠키) 기술 명세 및 보안

### 2.1. 정의 및 저장 구조

서버가 브라우저에 전송하는 작은 데이터 조각이다. 브라우저는 이를 로컬 저장소에 KEY-VALUE 형식의 문자열로 저장하며, 이후 동일 서버로의 재요청 시 HTTP 요청 헤더의 Cookie 필드에 담아 자동으로 전송한다.

### 2.2. 쿠키의 상세 동작 및 생명 주기

1. 클라이언트가 페이지 요청(Request)을 보낸다.
2. 서버는 응답 시 Set-Cookie 헤더를 통해 저장할 데이터를 전달한다.
3. 브라우저는 수신한 쿠키를 속성(만료 시간, 도메인, 경로 등)과 함께 로컬 저장소에 기록한다.
4. 재요청 시 브라우저는 저장된 쿠키 중 해당 도메인과 경로에 부합하는 항목을 선별하여 서버에 전송한다.
5. 서버는 쿠키 내부의 식별 정보를 확인하여 사용자의 개인화된 설정이나 인증 상태를 복구한다.

### 2.3. 쿠키 종류 및 수명 관리
- Session cookie: 만료 시간을 설정하지 않은 경우 생성되며, 브라우저 종료 시 메모리에서 즉시 삭제된다.
- Persistent cookies: Expires 또는 Max-Age 속성을 지정하여 하드 디스크에 파일 형태로 저장된다. 브라우저를 종료하거나 컴퓨터를 재부팅해도 지정된 기간까지 유지된다.

### 2.4. 보안 장치 및 규제 준수
- HttpOnly: 자바스크립트(document.cookie)를 통한 접근을 차단하여 XSS(Cross-Site Scripting) 공격으로부터 쿠키 탈취를 방지한다.
- Secure: HTTPS 프로토콜 환경에서 암호화된 채널을 통해서만 쿠키가 전송되도록 강제한다.
- SameSite: CSRF(Cross-Site Request Forgery) 공격을 방지하기 위해 제3자 사이트에서의 쿠키 전송 범위를 제한한다.

## 3. Session (세션) 관리 매커니즘과 서버 부하

### 3.1. 정의와 보안적 가치

사용자의 민감한 정보(인증 상태, 개인 데이터 등)를 클라이언트가 아닌 서버 측 저장소에 보관하는 방식이다. 클라이언트에게는 데이터 자체가 아닌, 해당 데이터에 접근할 수 있는 무작위 문자열인 '세션 ID'만 제공하여 데이터 노출 위험을 원천 차단한다.

### 3.2. 세션 기반 인증의 7단계 프로세스

1. 클라이언트가 로그인 정보(ID/PW)를 서버에 제출한다.
2. 서버는 DB 대조를 통해 인증에 성공하면 새로운 세션 데이터를 생성하고 저장소(DB, Memory 등)에 저장한다.
3. 해당 세션 데이터의 유일한 식별자인 세션 ID를 생성한다.
4. 생성된 세션 ID를 응답 헤더의 쿠키(Set-Cookie)에 담아 클라이언트에 전달한다.
5. 브라우저는 전달받은 세션 ID를 쿠키 저장소에 안전하게 보관한다.
6. 이후 모든 요청마다 브라우저는 세션 ID가 담긴 쿠키를 서버로 자동 전송한다.
7. 서버는 수신한 ID를 세션 저장소에서 조회하여 일치할 경우 해당 사용자를 식별하고 요청을 처리한다.

### 3.3. Django의 세션 저장 아키텍처

Django는 기본적으로 django_session 테이블을 사용하는 DB 기반 세션 방식을 채택한다.
- session_key: 쿠키에 저장되는 32글자의 무작위 문자열.
- session_data: 실제 정보가 암호화/인코딩되어 저장되는 텍스트 필드.
- expire_date: 세션의 만료 기한.
- 설정에 따라 Redis나 Memcached 같은 인메모리 저장소를 사용하여 성능을 극대화할 수도 있다.

## 4. Django 인증 시스템 구조 및 객체 지향적 접근

### 4.1. 인증(Authentication)과 권한(Authorization)의 분리

- 인증: 사용자가 시스템에 주장하는 신원이 실제와 일치하는지 확인하는 과정이다. (예: 로그인 성공 여부)
- 권한: 인증된 사용자가 특정 자원에 접근하거나 행동을 수행할 자격이 있는지 결정하는 과정이다. (예: 관리자 페이지 접근 권한)

### 4.2. User 모델 추상 클래스 상세 비교

| 구분 | AbstractBaseUser | AbstractUser |
| :--- | :--- | :--- |
| **제공 필드** | `password`, `last_login` 등 최소 인증 필드만 제공 | `username`, `email`, `name`, `is_staff` 등 모든 기본 필드 포함 |
| **확장성** | 로그인 아이디(`username`) 자체를 바꾸는 등 완전한 재정의 가능 | 기존 인증 체계를 유지하면서 단순 정보 필드만 추가 가능 |
| **구현 난이도** | 유저 모델 관리자(`Manager`)부터 모든 것을 직접 구현해야 함 | Django의 기본 기능을 모두 사용하므로 구현이 매우 빠름 |
| **비유** | 도우만 준비된 상태의 피자 (커스터마이징 극대화) | 이미 토핑이 다 올라간 콤비네이션 피자 (빠른 서빙) |

## 5. Custom User 모델 대체 전략 및 DB 영속성

### 5.1. 대체(Substitution)의 필요성과 전략적 선택

Django의 기본 유저 모델은 기능이 강력하지만, 실제 비즈니스 환경에서는 이메일로 로그인하거나 나이, 주소, 프로필 이미지 등 추가 정보가 필요하다. 프로젝트 초기 단계에서 커스텀 모델로 대체하지 않으면, 추후 수천 건의 사용자 데이터가 쌓인 상태에서 DB 구조를 바꾸는 것은 거의 불가능에 가까운 기술 부채가 된다.

### 5.2. 기술적 구현 및 주의사항

AbstractUser를 상속받아 프로젝트의 성격에 맞는 모델을 정의한다.

```
# accounts/models.py
from django.contrib.auth.models import AbstractUser
class User(AbstractUser):
    # 비즈니스 로직에 필요한 추가 필드 기술
    point = models.IntegerField(default=0)
    address = models.CharField(max_length=200, blank=True)
```

settings.py에 AUTH_USER_MODEL = 'accounts.User'를 등록하여 프레임워크 전반의 참조 대상을 변경한다.

프로젝트의 첫 migrate를 실행하기 전에 이 설정을 마쳐야 한다. 만약 이미 기본 모델로 마이그레이션이 진행되었다면, DB를 초기화하고 모든 마이그레이션 파일을 삭제한 뒤 재시작해야 한다.

## 6. 로그인/로그아웃 기능의 내부 로직

### 6.1. Login 기능과 세션 결합

- AuthenticationForm: DB 모델과 직접 연결되지 않은 일반 Form이다. 이는 정보를 '생성'하는 것이 아니라 입력값과 DB 값을 '비교'하는 용도이기 때문이다.
- get_user(): 폼의 유효성 검사가 성공한 후, 인증된 사용자 인스턴스를 안전하게 반환받기 위해 사용한다.
- auth_login(request, user): 이 함수가 호출되는 시점에 비로소 서버 측 세션 데이터가 생성되고 세션 ID 쿠키가 브라우저로 전송된다.

### 6.2. Logout 기능과 데이터 파기

- 프로세스: 로그아웃은 단순히 상태를 바꾸는 것이 아니라, 해당 세션 데이터를 서버 저장소에서 영구적으로 삭제(Delete)하는 행위이다.
- 결과: 클라이언트가 보관하던 세션 ID 쿠키는 더 이상 유효하지 않게 되어, 이후 요청 시 서버는 해당 요청을 '로그인하지 않은 사용자'로 처리한다.

## 7. 회원가입 및 정보 수정 폼의 아키텍처적 이해

### 7.1. UserCreationForm 커스터마이징의 당위성

내장된 UserCreationForm은 내부적으로 from django.contrib.auth.models import User와 같이 기본 유저 모델을 직접 참조하도록 설계되어 있다. 우리가 커스텀 모델을 사용하더라도 이 폼은 여전히 과거의 기본 모델을 찾으려 하므로, 상속을 통해 Meta.model을 재정의하는 과정이 필수적이다.

### 7.2. 정보 수정 보안 (UserChangeForm)

UserChangeForm을 그대로 사용하면 일반 사용자가 자신의 권한(is_superuser)이나 접근 가능한 그룹 정보를 임의로 수정할 수 있는 심각한 보안 취약점이 발생한다. 따라서 반드시 상속 후 fields 속성을 통해 수정 가능한 필드를 제한해야 한다.

```
# accounts/forms.py 예시
class CustomUserChangeForm(UserChangeForm):
    class Meta:
        model = get_user_model()
        fields = ('email', 'first_name', 'last_name',) # 안전한 필드만 노출
```

## 8. 유저 모델 참조 체계의 엄격한 구분

### 8.1. settings.AUTH_USER_MODEL (모델 정의 시점)

- 형태: 'accounts.User'와 같은 문자열 형식이다.
- 사용처: models.py 내부의 외래키(ForeignKey) 설정 등 모델 정의 단계에서 사용한다.
- 이유: Django가 구동될 때 모델들 간의 로드 순서가 꼬이는 '순환 참조(Circular Import)' 에러를 방지하기 위해 클래스 객체 대신 문자열 경로를 전달하는 방식을 취한다.

### 8.2. get_user_model() (실행 시점)

- 형태: 실제 유저 모델 클래스 객체를 반환하는 함수이다.
- 사용처: views.py, forms.py, serializers.py 등 모델이 이미 로드된 이후의 로직에서 사용한다.
- 이유: 현재 프로젝트에서 활성화된 유저 모델을 동적으로 찾아오므로, 코드의 재사용성과 유연성을 확보할 수 있다.

## 9. 템플릿 레이어의 인증 데이터 통합

### 9.1. Context Processors의 백그라운드 동작

Django는 매 요청마다 모든 템플릿에 인증 정보를 주입하는 context_processors.auth 미들웨어를 실행한다. 개발자가 수동으로 context에 유저 정보를 담지 않아도 모든 HTML 파일에서 user 변수를 사용할 수 있는 기술적 근거이다.

### 9.2. 객체 기반 조건부 렌더링 (Logic)

- user.is_authenticated: 로그인 여부를 Boolean 값으로 반환하여 메뉴 구성을 변경할 때 사용한다.
- user.is_staff: 관리자 페이지 접근 권한 유무를 판단한다.
- user.username: 현재 접속 중인 사용자의 식별명을 안전하게 출력한다.

```
<!-- 템플릿 활용 예시 -->
{% if user.is_authenticated %}
    <span>{{ user.username }}님 환영합니다.</span>
    <a href="{% url 'accounts:update' %}">정보수정</a>
{% else %}
    <a href="{% url 'accounts:login' %}">로그인</a>
{% endif %}
```
