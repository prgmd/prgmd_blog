# 1. 객체 지향
인간이 현실 세계를 바라보는 방식을 소프트웨어 설계에 투영하려는 철학적 시도에서 시작. 프로그램을 단순히 '명령어의 나열'로 보는 것이 아니라, 데이터와 그 데이터를 처리하는 동작을 하나로 묶은 '객체'들의 모임으로 파악하는 방식을 의미한다.

## 1-1. 객체 지향의 역사
### 절차 지향 (Procedural Programming)
프로그램이 처음부터 끝까지 순서대로 실행되는 결과물에 초점을 맞추고, 로직 중심이기에 데이터의 재사용성보다는 실행 순서가 더 중요.

다만 이러한 절차 지향 방식은 코드가 길어지면 꼬인 실타래처럼 수정하기가 매우 힘들었고, 1960년대부터 객체라는 개념이 등장하기 시작했다. 1983년 등장한 C++이 기존 절차 지향 언어였던 C에 객체 지향을 도입한 언어.

### 객제 지향 (Object-Oriented Programming)
이후 1990년대에 접어들면서 소프트웨어의 규모는 개인이 감당할 수 없을 정도로 거대해졌고, 개발자들은 어떻게 하면 이 복잡한 코드를 망가뜨리지 않고 거대한 성처럼 쌓아 올릴 수 있을지 고민하기 시작. '한 번 쓰고 어디서든 실행한다(Write Once, Run Anywhere)'는 철학과 함께 등장한 Java는 이 시기의 주인공이 됐다. 운영체제에 상관없이 동작하고, 메모리를 개발자가 일일이 관리하지 않아도 되는 '가비지 컬렉션' 기능을 도입해 혁명적인 효율성을 가져온 것.

1994년 'GoF의 디자인 패턴'이라는 책이 출간되면서, 객체 지향으로 문제를 해결하는 '모범 답안'들이 공식화되기 시작했고, 복잡한 설계를 그림으로 소통하기 위한 표준 언어인 UML이 등장하며, 객체 지향은 단순히 코딩 기법을 넘어 소프트웨어 공학의 거대한 표준으로 자리 잡았다.

현대에 이르러 객체 지향은 훨씬 유연하고 실용적인 형태로 진화했다. Python이나 JavaScript 같은 언어들은 객체 지향의 구조를 갖추고 있으면서도, 필요할 때는 매우 간결하고 자유로운 문법을 허용하고, Kotlin이나 Swift, Rust 같은 현대적 언어들은 객체 지향의 핵심인 '상속'보다는 '구성'이나 '인터페이스'를 더 강조하며, 데이터의 안전성과 코드의 간결함을 동시에 잡으려 노력하고 있다.

### 주의사항
절차 지향과 객체 지향은 서로 반대되는 개념이 아님. 객체 지향은 절차 지향의 기본 토대 위에 상속, 코드 재사용, 유지보수성 등의 개념을 더해 보완하고 발전시킨 것.

## 1-2. 객체란?
> 객체란, 단순히 코드의 묶음이 아니라, 상태와 행위를 하나로 합친 추상적 실체.

### 객체 지향의 4대 측징
* **캡슐화(Encapsulation):** 객체의 내부 구현을 외부에서 알지 못하게 감추는 것. 내부 데이터를 보호하여 예기치 못한 수정을 방지하며 보안과 독립성을 갖추도록 한다.
* **상속(Inheritance):** 이미 검증된 클래스의 기능을 그대로 이어받아 쓰는 것. 중복 코드를 줄이고 개발 속도를 획기적으로 높여준다.
* **다형성(Polymorphism):** 똑같은 이름의 명령이라도 어떤 객체가 실행하느냐에 따라 다르게 반응하는 특징. 덕분에 코드를 수정하지 않고도 새로운 객체를 쉽게 교체하거나 추가할 수 있어 유연한 설계가 가능해진다.
* **추상화 (Abstraction):** 현실의 복잡한 실체를 프로그래밍에 필요한 핵심만 뽑아내는 과정. 복잡한 문제를 단순하게 바라보는 자세.

### 핵심 용어
| 용어 | 설명 |
| :--- | :--- |
| **객체(Object)** | 프로그래밍에서 사용되는 모든 실체 |
| **클래스(Class)** | 객체를 만들기 위한 묶음(설계도) |
| **인스턴스(Instance)** | 설계도를 바탕으로 메모리에 실제 구현된 실례 |
| **메서드(Method)** | 클래스 내부에 정의된 기능(함수) |
| **속성(Attribute)** | 클래스 내부에 저장된 데이터(변수) |

스마트폰을 만든다고 가정할 경우, 스마트폰 설계도(**클래스**)가 필요함. 이 설계도에는 스마트폰이 가져야 할 정보(**속성**; 모델명, 배터리 용량 등...)와 수행할 기능(**메서드**; 전화 기능, 촬영 기능 등...)을 미리 정의. 이 설계도를 바탕으로 실제 제품을 찍어내면 실물 스마트폰이 탄생함. 메모리 공간에 실제 구현된 결과물을 **인스턴스**라고 부르며, 이 인스턴스를 포함해 프로그램 내 독립적으로 존재하며 제 역할을 수행하는 모든 실체를 통칭해 **객체**라고 부름.

## 1-3. 객체의 3요소
1.  **속성 (Attribute):** 객체가 가진 데이터 (상태)
2.  **메서드 (Method):** 객체가 할 수 있는 동작 (함수)
3.  **고유성 (Identity):** 각 객체는 서로 구분되는 고유한 주소값을 가짐

# 2. 클래스(Class)와 인스턴스(Instance)
## 2-1. 클래스
> 객체를 만들기 위한 **설계도**. 파이썬에서 새로운 **타입(Type)**을 정의하는 방법. 공통된 특성(데이터)과 기능(동작)을 가진 '틀'을 만드는 과정이다.

## 2-2. 인스턴스
> 클래스라는 설계도를 바탕으로 메모리에 실제 구현된 **결과물(객체)**.

### 파이썬 철학
> 대표적으로, 파이썬에서 "모든 것은 객체." 변수에 할당되는 값(문자열, 숫자 등) 모두가 특정 클래스의 인스턴스다. 심지어 함수도 객체다.

숫자 `1`이나 문자열 `hello` 모두 객체의 일부. `'hello'.upper()`를 실행할 수 있는 이유 역시 클래스 내부 미리 정의된 메서드와 속성을 가지고 있기 때문에 `.`으로 기능을 호출할 수 있는 것.

또한 함수도 메모리상 존재하는 객체인데, 함수를 변수에 대입하거나, 다른 함수의 인자로 넘기거나, 리스트에 담을 수 있다. `def my_func(): pass`를 선언하면 파이썬은 내부적으로 `function` 클래스의 인스턴스를 생성한다. 함수 객체 역시 `__name__ `같은 속성을 가지고 있어 자신의 이름을 기억할 수 있다.

## 2-3. 변수의 종류
| 구분 | 정의 방법 | 접근 방법 | 특징 |
| :--- | :--- | :--- | :--- |
| **인스턴스 변수** | `self.변수명` | `인스턴스.변수명` | 각 인스턴스별로 가지는 **고유한** 값 |
| **클래스 변수** | 클래스 내부 직접 정의 | `클래스이름.변수명` | 모든 인스턴스가 **공유**하는 값 |

### 속성 탐색 순서
`인스턴스.속성` 접근 시, **인스턴스 변수**를 먼저 찾고 없으면 **클래스 변수**를 찾는다. 클래스 변수와 동일한 이름으로 인스턴스 변수를 생성하면, 해당 인스턴스는 인스턴스 변수를 우선 참조합니다.

## 2-4. 메서드의 종류
### ① 생성자 메서드 (`__init__`)
* 새 객체를 만들 때 호출되어 초기값을 설정.
* `self.name = name` 처럼 인스턴스 변수를 선언하고 초기화한다.

### ② 인스턴스 메서드
* **특징:** 인스턴스의 상태를 조작하거나 동작을 수행한다.
* **매개변수:** 첫 번째 인자로 반드시 **`self`**(나 자신)를 받는다.
* **원리:** `'hello'.upper()`는 내부적으로 `str.upper('hello')`와 같이 동작한다. 즉, 클래스가 메서드를 호출하면서 첫 번째 인자로 인스턴스 자신을 넘겨주는 구조.

### ③ 클래스 메서드 (`@classmethod`)
* **특징:** 클래스 전체에 영향을 미치는 속성을 변경하거나 접근할 때 사용.
* **매개변수:** 클래스 자체를 가리키는 **`cls`**를 첫 번째 인자로 받는다.

### ④ 스태틱 메서드 (`@staticmethod`)
* **특징:** 클래스나 인스턴스의 상태와 상관없이 독립적으로 동작하는 '도우미 함수'.
* **매개변수:** `self`나 `cls`를 받지 않는다.

```python
class Person:
    job = '학생'          # 클래스 변수
    population = 0      # 클래스 변수

    def __init__(self, name, age):
        self.name = name  # 인스턴스 변수
        self.age = age
        Person.increase_population() # 생성 시 인구수 증가 로직 추가 가능

    def introduce(self):
        print(self.name, self.age)
    
    @classmethod
    def increase_population(cls):
        cls.population += 1 # 클래스 변수에 접근
    
    @staticmethod
    def print_test(word):
        return 'test :' + word

# 실행 및 결과 확인
p1 = Person('Alice', 25)
p2 = Person('Bob', 28)

# 체크: Person.populatio (오타) -> Person.population
print(Person.population) # 결과: 2

# 인스턴스 변수 생성 시 우선순위
p1.job = '쉬었음청년' # p1에게만 'job'이라는 인스턴스 변수 생성
print(p1.job)         # '쉬었음청년' (인스턴스 변수 우선)
print(Person.job)     # '학생' (클래스 변수는 그대로)
print(p2.job)         # '학생' (p2는 인스턴스 변수가 없으므로 클래스 변수 참조)
```

# 3. 속성
데이터 보호를 위해 클래스 외부에서 속성에 직접 접근하는 것은 피해야 함. 우리 내장이 몸 밖에 나와 있으면 안되니까, 피부로 감싸고 있는 셈.

## 3-1. 속성 분류와 접근 범위
데이터의 성격에 따라 정의 위치와 접근 권한을 다르게 설정.

| 구분 | 정의 위치 | 공유 범위 | 특징 |
| :--- | :--- | :--- | :--- |
| **클래스 속성** | 메서드 밖 | **모든 인스턴스** | 모든 객체가 공통으로 사용하는 데이터를 저장. |
| **인스턴스 속성** | `__init__` 등 메서드 안 | **해당 인스턴스만** | `self.변수명` 형태로 각 객체의 고유 데이터를 저장. |

## 3-2. Private 멤버
클래스 내부의 민감한 정보를 외부에서 함부로 수정하지 못하도록 차단하는 기술. 신체를 비유로 들면 '피부'에 가깝다. 변수명 앞에 언더바 두 개(`__`)를 붙인다. (예: `self.__balance`) 

이렇게 설정하게 되면, 밖에서 `p1.__age = 20`라고 변수 수정을 시도해도 에러를 낸다. (네임 맹글링 보호 조치) 객체의 무결성(Integrity) 유지. 즉, 데이터가 오염되는 것을 방지하는 셈이다.

## 3-3. 접근자 메서드
> 이렇게 직접 수정이 불가능하지만, 외부와 아예 소통하는 건 아니다. 입으로 음식물을 섭취하듯이, 접근자를 이용해 데이터를 주고받음. 데이터를 직접 노출하지 않고, **안전한 통로**를 통해서만 주고받는 방식.

### ① Getter (획득자)
* **역할:** Private 속성값을 외부로 전달 = 현재 상태가 어떤지 안전하게 읽어옴.
* **형식:** `get_속성명()`
* **장점:** 데이터를 그대로 주지 않고, 필요한 형태로 가공해서 전달 가능한다. (예시: `age`에 20이라 저장된 자료를 `20세`로 가공해서 가져옴)

### ② Setter (설정자)
* **역할:** 외부에서 들어온 값을 검사한 후 Private 속성에 할당 = 잘못된 데이터가 들어오는 것을 막음.
* **형식:** `set_속성명(value)`
* **장점:** **유효성 검사(Validation)** 로직을 넣어 잘못된 데이터 삽입을 원천 차단할 수 있다. 예를 들어 나이에 음수값(`-5살`)이 들어오면 할당을 거부하고 에러 메시지 출력하는 식.

### 속성 접근 주의사항 (Shadowing)
파이썬은 인스턴스에서 클래스 순으로 속성을 탐색하기 때문에(내 방에 있는지 먼저 확인하고 없으면 밖으로 나가서 찾아보는 식), 만약 클래스 속성과 동일한 이름으로 인스턴스 변수를 생성(대입)하면 클래스 속성이 가려지는 'Shadowing' 현상이 발생한다. 

쉽게 말하면, 아파트 단지 공용 게시판에 '내일 분리수거일'이라고 공지가 적혀있는데(`Person.day = 'recycle'`), 누가 101호 주민 집 현관문에 '내일 파티하는 날'이라고 쪽지를 붙여둔 것. (`p1.day = 'party'`) 이제부터 101호한테 내일 무슨 날인지 물어보면 '파티하는 날'이라고 대답하게 된다. 

따라서 클래스 공통 데이터를 수정할 때는 반드시 **`클래스명.변수명`**으로 접근해야 함. `Person`의 인스턴스인 `p1`에서 `p1.day = 'party'`이라 클래스 속성을 바꿔봤자 큰 의미 없고 `Person.day = 'party'`로 전체 내용을 바꿔줘야 한다.

# 4. 메모리 관리
## 4-1. 가비지 컬렉션
> 프로그램이 실행되면서 생성된 객체들 중, 더 이상 사용되지 않는 '쓰레기(Garbage)'를 찾아내어 메모리에서 자동으로 해제하는 과정. 개발자가 직접 메모리를 비우지 않아도 되므로 메모리 누수(Memory Leak)를 방지한다.

### 레퍼런스 카운팅 (Reference Counting)
파이썬 메모리 관리의 핵심 매커니즘. 특정 객체를 가리키고(참조하고) 있는 변수나 요소의 개수를 세는 방식이다.

- 객체가 생성되거나 변수에 할당될 때: Count + 1
- 변수가 다른 값을 가리키게 되거나, 변수가 삭제(del)될 때: Count - 1
- Count == 0이 되는 순간: 해당 객체는 즉시 메모리에서 제거

### 순환 참조(Circular Reference) 문제
하지만 레퍼런스 카운팅 방식에는 치명적인 약점이 하나 있음. 바로 **두 객체가 서로를 가리키고 있을 때**. 두 객체를 사용하는 외부 변수를 모두 삭제해도, 서로를 참조하는 횟수가 1로 남아있어 절대 0이 되지 않는다. 이를 두고, 메모리 좀비 상태라고 한다.

파이썬은 이를 해결하기 위해 별도의 **'세대별 가비지 컬렉터'**를 운영. 주기적으로 순환 참조를 찾아내어 강제로 비워낸다.

## 4-2. 세대별 가비지 컬렉션
컴퓨터 공학에는 **"대부분의 객체는 생성된 후 아주 짧은 시간 안에 쓸모없어진다"**는 통계적 경험칙(Weak Generational Hypothesis)이 있음. 예를 들어 함수 안에서 잠깐 계산하고 버려지는 숫자, 리스트는 90% 확률로 잠깐 쓰는 애들이고, 프로그램이 끝날 때까지 유지되는 설정값, 전역 변수는 오래 쓰는 애들로 체크. 모든 객체를 매번 똑같이 검사하면 힘드니까 각각 검사 주기를 다르게 가져가는 것.

### 세대 구조
| 세대 | 대상 | 검사 빈도 | 설명 |
| :--- | :--- | :--- | :--- |
| **0세대** | 방금 막 생성된 객체 | **매우 자주** | 가장 먼저 쓰레기가 될 후보들 |
| **1세대** | 0세대 검사에서 살아남은 객체 | 보통 | 어느 정도 쓸모가 입증된 객체 |
| **2세대** | 1세대 검사에서도 살아남은 객체 | **드물게** | 프로그램 종료 시까지 살 가능성이 높은 객체 |

### 작동 원리
가비지 컬렉터는 다음과 같은 단계로 메모리를 청소한다.

1.  **임계값(Threshold) 도달:** 0세대 객체가 일정 개수 이상 쌓이면 청소를 시작함.
2.  **순환 참조 탐색:** 레퍼런스 카운트가 0은 아니지만, 자기들끼리 참조하고 있는 '순환 참조' 객체들을 찾아내서 지움.
3.  **승급(Promotion):** 청소 후에도 **살아남은 객체는 다음 세대로 이동**시킵니다. (0세대 → 1세대 → 2세대)
4.  **상위 세대 청소:** 0세대 청소가 여러 번 반복되면 1세대를 청소하고, 1세대 청소가 또 여러 번 반복되면 그제야 2세대를 청소한다.

### 장점
* **성능 최적화:** 모든 객체를 매번 전수조사하지 않아도 됨. 2세대에 있는 '장수 객체'들은 검사 대상에서 자주 제외되므로 CPU 소모를 줄일 수 있다.
* **순환 참조 해결:** 레퍼런스 카운팅(단순 숫자 세기)만으로는 못 잡는 '서로 가리키는 좀비 객체'들을 이 세대별 검사 과정에서 확실히 잡아낸다.

## 4-3. 메모리 관리 팁
### 큰 데이터는 사용 후 `del` 키워드로 참조를 끊어주는 게 좋다.
참고로 `del`은 메모리에서 객체를 즉시 삭제하는 명령이 아니라, 참조 카운트를 줄여주는 명령어. 리스트 내용물만 싹 지우고 싶을 때는 `list.clear()`를 쓰는 것이 객체 자체를 새로 만드는 것보다 메모리 재할당 측면에서 유리하다.

### `__slots__`를 사용하여 메모리 아끼기.
- 기본적으로 파이썬 클래스의 인스턴스는 속성을 저장하기 위해 `__dict__`라는 딕셔너리를 사용. 하지만 딕셔너리는 은근 메모리를 꽤 많이 차지한다.
- 클래스 내부에 `__slots__ = ['name', 'age']`와 같이 사용할 속성 이름을 미리 등록하고 사용하면, 딕셔너리를 생성하지 않고 정해진 공간만 사용한다. (대신 미리 정의한 속성 외에는 추가할 수 없다) 수만 개의 객체를 생성할 때 메모리 사용량을 **최대 40~50% 이상** 줄일 수 있다고.

### 대용량 데이터는 제너레이터(Generator) 활용.
리스트에 모든 데이터를 한꺼번에 담으면 그만큼의 메모리가 즉시 점유된다. `[x for x in range(1000000)]` 대신 `(x for x in range(1000000))` 처럼 소괄호를 사용하거나 `yield` 키워드를 사용. 데이터를 한꺼번에 메모리에 올리지 않고, **필요할 때 하나씩 생성**해서 쓰기 때문에 메모리 효율이 압도적으로 좋아진다.

``` python
import sys
list_data = [x for x in range(1000000)] # 약 8MB 점유
gen_data = (x for x in range(1000000))  # 약 112Byte 점유
```

### 문자열 합치기 시 `+` 연산 피하기
파이썬의 문자열은 **불변(Immutable)** 객체. `'a' + 'b' + 'c'`를 하면 매번 새로운 문자열 객체가 메모리에 생성되고 이전 객체는 버려진다. 즉, 리스트에 담아두었다가 `''.join(['a', 'b', 'c'])` 방식을 사용하는 것이 메모리와 속도 면에서 훨씬 유리하다.

### 약한 참조(Weak Reference) 사용하기
순환 참조가 걱정되지만 서로를 알고 있어야 하는 경우에 사용. `weakref` 모듈을 사용하면 레퍼런스 카운트를 올리지 않으면서 객체를 가리킬 수 있습니다. 즉, 대상을 가리키고는 있지만 **가비지 컬렉터가 수거해가는 것을 방해하지 않는다.**

### `gc.collect()` 수동 호출 (주의해서 사용)
파이썬이 알아서 청소해주지만, 대규모 작업 직후에 명시적으로 청소 명령을 내릴 수 있긴 하다. `import gc; gc.collect()`. 다만 가비지 컬렉션 과정 자체가 CPU를 사용하므로 너무 자주 호출하면 오히려 프로그램이 느려질 수 있고, 정말 큰 데이터를 `del`한 직후에만 제한적으로 사용하는 것을 권한다.

# 5. 상속과 추상화

## 5-1. 상속 (Inheritance)
> 기존 클래스(부모)의 모든 속성과 메서드를 그대로 물려받아 새로운 클래스(자식)를 만드는 것. 중복되는 코드를 줄이고, 계층적 구조화를 통해 유지보수 용이성을 확보한다.

### 다중 상속
파이썬은 여러 부모로부터 상속받는 다중 상속을 지원한다. 이때 발생하는 충돌은 MRO(Method Resolution Order, 메서드 탐색 순서) 규칙에 따라 해결

#### MRO(Method Resolution Order)
Linearization(선형화) 알고리즘 적용해 다음 원칙으로 순서 결정
- 부모보다는 자식 먼저
- 왼쪽 부모 먼저 (리스트 나열 순서)
- 중복 방문 방지 (공통 부모 클래스는 모든 자식 클래스 탐색이 끝난 뒤 단 한 번만 탐색)

### 메서드 오버라이딩 (Method Overriding)
> 부모에게 물려받은 메서드를 자식의 입맛에 맞게 **'재정의'**.

* **`super()`를 활용하는 방법:** 부모의 기능을 완전히 버리는 것이 아니라, **부모의 기능을 먼저 수행하고(확장)** 자식만의 기능을 덧붙일 때 사용. 예를 들어, 부모가 '공격' 기능을 가졌다면, 자식은 `super().공격()`으로 기본 대미지를 입히고 '추가 독 데미지' 로직만 따로 작성하는 식.
* 메서드 이름과 매개변수 형식을 부모와 동일하게 맞춰야만 이러한 다형성을 제대로 활용할 수 있다.

※ `super()` : MRO에 따라 현재 클래스의 부모 메서드나 속성에 접근하게 해주는 내장 함수

### 합성 (Composition)
무조건 상속을 쓰는 게 정답은 X. 'Is-a'(부모와 자식) 관계가 확실할 때만 상속을 써야 하며, 만약 'Has-a'(객체가 다른 객체를 포함) 관계일 경우 합성을 사용해야 함. 예를 들어 자동차는 엔진을 상속받는 게 아니라, 자동차 객체 내부에 엔진 객체를 **속성**으로 가짐. (`self.engine = Engine()`)

## 5-2. 추상 클래스 (Abstract Class)
> 상속받을 자식 클래스들이 반드시 구현해야 할 **'표준 규격(인터페이스)'**을 정의하는 클래스.

* `from abc import ABC, abstractmethod`를 사용해 구현한다.
* 특징
    1.  **인스턴스화 불가:** `Animal`이라는 추상 클래스가 있다면 `a = Animal()`처럼 직접 객체를 만들 수 없다. (추상적인 개념이기 때문)
    2.  **구현 강제:** `@abstractmethod`가 붙은 메서드는 자식 클래스에서 **반드시 오버라이딩**해야 한다. 안 하면 자식 클래스도 객체를 만들 수 없다.
* **비유:** '리모컨'이라는 추상 클래스에 '전원 버튼' 메서드가 있다면, 삼성 리모컨이든 LG 리모컨이든 반드시 '전원 버튼' 기능을 실제로 만들어 넣어야 하는 것과 같다.

## 5-3. 예시
백종원의 빽다방 본사는 홍대(**부모 클래스**)에 있지만, 강남(**자식 클래스**) 에 분점을 냄. 본사 시스템을 그대로 가져와 지점을 낸 셈이다. 근데 강남 입맛에는 조금 싱거웠던지, 레시피를 살짝 수정. 본사의 `만들기()` 메서드를 가져와 자식 클래스 단에서 내용을 덮어씌운다(**메서드 오버라이딩**). 만약 본사 레시피를 존중하면서 우리 집 비법만 살짝 추가하고 싶다면 **`super()`**를 이용. 본사에서 브랜드 가맹점을 내려면 간판과 결제 시스템만큼은 무조건 있어야 한다고 규칙을 정했다고 가정하자(**추상 클래스**). 이건 가맹점들이 꼭 지켜야 할 최소한의 규칙이 되는 셈. 이때 가맹점 손님들은 주방 소스가 어떻게 만들어지는지 전혀 알 필요가 없고, 키오스크의 주문하기만 누르면 음료를 마실 수 있다(**추상화**)
