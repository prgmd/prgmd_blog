# 2. 서비스

## 2.1 서비스란?
파드 집합에 접근할 수 있는 고정된 네트워크 엔드포인트를 제공하는 리소스. 파드에 고정된 가상 IP(ClusterIP)를 부여해, 클라이언트가 파드의 IP 변화는 무시하고 안정적으로 통신하게 도와주는 역할을 수행한다.
- 참고로 파드는 생성될 때마다 IP가 바뀌는 일회용 자원이다. 만약 원활하게 통신하기 위해서는 이를 묶어줄 고정 IP가 필요하고, 서비스가 바로 그 고정 IP 역할이 되는 셈.
- 그냥 쿠버네티스 안에서는 무조건 서비스로 통신한다고 알아두면 좋다. (쿠버네티스 내부 DNS가 이름을 IP로 바꿔준다. 우리가 평소 인터넷 사용할 때 도메인으로 접속하는 것과 마찬가지)

### Selector
서비스는 레이블 셀렉터를 사용해 트래픽을 전달할 파드를 식별한다. 파드가 Label을 붙여 서로를 식별한다면, Selector는 서비스나 컨트롤러가 "Label 같은 애들 전부 모이셈"이라 외치는 검색 조건.
- 마트에 수만 개 상품이 있다고 할 때, 모든 상품의 위치를 외울 수 없으니 식품, 가전 같은 라벨을 붙여두고 같은 라벨끼리 코너에 모아두는 것. 만약 손님이 식품 코너 어디냐고 물어보면 그 방향 가리키면 된다.
- 셀렉터의 연결 방식을 '느슨한 연결'이라고도 함. 파드와 서비스는 서로 존재를 몰라도 된다. 그냥 라벨만 맞으면 연결됨.
- 셀렉터를 여러 개 적을 수도 있다.

``` yaml
apiVersion: v1
kind: Service
metadata:
  name: mart-service
spec:
  selector:    # <--- "여기서부터 내가 관리할 애들을 찾겠다!"
    app: mart  # "app이라는 라벨의 값이 mart인 파드만 골라라"
  ports:
  - protocol: TCP
    port: 80
    targetPort: 8080
# 이렇게 설정하면 쿠버네티스가 클러스터 전체를 뒤져서 `app:mart` 라벨이 붙은 파드들을 실시간으로 찾아 연결해준다.
```

## 2.2 클러스터 내부 통신
파드는 서로 다른 노드에 흩어져 있어도 마치 같은 네트워크 대역에 있는 것처럼 대화한다. 어떻게? 바로 Cluster IP를 이용.
- 클러스터 IP는 내부 소통용. 클러스터 안에 있는 파드끼리 서로를 찾을 때 사용한다.
  - 만약 서비스 타입을 따로 지정하지 않으면 쿠버네티스는 자동으로 ClusterIP를 할당한다.
* A 파드가 B 서비스 IP로 데이터를 보내면 각 노드에 있는 `kube-proxy`가 이를 감지해 살아있는 B 파드 중 하나로 전달한다.
* 리눅스 커널의 `iptables`는 주소를 바꿔치기 하는 녀석. 워커 노드의 리눅스 커널에 설치되어 있던 `iptables`가 패킷을 읽고 목적지 주소를 파드 IP 중 하나로 바꿔준다. (DNAT; Destination Network Address Translation) 
  - `iptables`는 일종의 장부고 실시간 비서가 `kube-proxy`다. 만약 파드가 새로 생기면 kube-proxy가 장부에 새 주소를 추가하고, 그 반대 케이스라면 장부에서 그 주소를 지워버림.
  - 이해가 어렵다면 그냥 조건문 덩어리라고 생각하자. 만약 목적지가 서비스 IP다? → 그러면 내가 가진 살아있든 파드 IP 중 하나 드립니다.

#### FQDN(Fully Qualified Domain Name)

클러스터 내부에서는 굳이 IP를 몰라도 서비스 이름이 곧 도메인이 되기 때문에 `http://서비스이름`만 쳐도 접속이 된다.

## 2.2 클러스터 외부 통신

* 클러스터 바깥(인터넷)에서 내부에 접속하거나, 반대로 내부에서 밖으로 나갈 때(구글 API 호출, 외부 DB 사용 등...) 사용하는 외부 통신 방식

### Inbound(외부 → 내부)

| 방식                | 설명                             | 실무 비유                               |
| ----------------- | ------------------------------ | ----------------------------------- |
| **NodePort**      | 모든 노드의 특정 포트(30000~32767)를 개방  | 아파트 단지 모든 동의 '비상문'을 열어두는 것          |
| **Load Balancer** | 클라우드(AWS 등)의 외부 IP를 할당받음       | 아파트 정문에 정식 '안내 데스크'를 설치하는 것         |
| **Ingress**       | **(가장 권장)** URL 경로에 따라 트래픽을 분산 | 중앙 현관에서 "메일은 1층, 블로그는 2층"이라고 안내하는 것 |

### Oubound(내부 → 외부)

보통은 그냥 자유롭게 나가기는 한데, 보안이 엄격한 곳에서만 Egress Network Policy를 설정해 허용된 주소로만 나갈 수 있도록 제한한 편.

## 2.3 NodePort
> 모든 노드의 특정 포트를 열어 내부와 연결하는 방식. 

간편하지만 보안에 취약할 수 있다. 사용자가 모든 노드 IP를 알고 있거나 별도 외부 로드 밸런서를 앞에 둬야 한다. 주로 테스트 환경에서 사용.

## 2.4 Load Balancer
> 클라우드 표준 방식으로, AWS, GCP, Azure 등이 제공하는 외부 로드 밸런스를 사용해 고정된 외부 IP를 할당받는 방식이다. 4계층에서 작동.

서비스 생성시 클라우드 업체가 외부 IP를 하나 던져주고, 이 IP로 들어오는 트래픽이 클라우드 인프라를 타고 안전하게 내부 서비스로 전달되는 식이다. 
- 일종의 클라우드 업체가 제공하는 아파트 정문 데스크. 방문객은 그냥 이 정문 주소만 알고 찾아오면 된다. 

가장 안정적이다. 
- 물론 클라우드 리소스를 사용하므로 비용이 발생하는 편. 
- 서비스 1개당 외부 IP가 1개씩 필요하다. (서비스가 100개라면...?)

## 2.5 Ingress
> 여러 서비스를 하나의 외부 IP(혹은 도메인)로 묶어서 경로에 따라 교통정리를 해주는 7계층 규칙 모음.

예를 들어 하나의 입구를 두고 들어오는 URL 주소나 경로에 따라 목적지 서비스를 나누는 식이다.
- `mart.com/apple` → 사과 코너로
- mart.com/beer → 맥주 코너로

가장 권장되는 방식으로, 외부 IP 하나로 수많은 서비스를 운영할 수 있어 비용이 절약될 뿐더러 SSL/TLS 인증을 입구에서 한꺼번에 처리할 수 있기에 관리도 매우 편하다.

## 2.6 ExternalName
보통 서비스는 트래픽을 클러스 내부 파드로 보내려고 만들지만, 얘는 트래픽을 클러스터 외부 주소로 돌릴 때 사용. 
- 상황: 마트 시스템을 운영하는데, 결제 기능은 외부 업체인 `toss.com`의 API를 써야 할 경우!
  - 개발자가 코드에 직접 `https://toss.com`이라고 적어두면, 나중에 결제 업체가 바뀌었을 때 소스 코드를 다 고치고 다시 빌드해서 배포해야 한다.
  - 그래서 쿠버네티스 내부에 `payment-service`라는 이름의 `ExternalName` 서비스를 만들고, 이 별명이 `toss.com`을 가리키도록 설정.
- 즉, 개발자는 코드에 `http://payment-service`라고만 적으면 된다. 

ExternalName은 IP를 따로 쓰는게 게 아니라 **오직 도메인 이름으로만 작동하며 DNS CNAME 레코드를 활용하는 방식**. 파드가 `http://payment-service`로 접속을 시도하면 쿠버네티스 내부 DNS가 실제 토스 주소로 바꿔주고, 파드가 그 주소를 받아 클러스터 밖 API를 사용하게 되는 식이다.
