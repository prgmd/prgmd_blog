# 1. 프로젝트 개요 및 배경

사고가 났을 때 블랙박스 기기가 파손되거나, 범인이 증거를 없애기 위해 기기를 가져가버리면 영상을 확보할 수 없다. 이 문제에서 출발했다.

영상을 클라우드에 실시간으로 저장하면 어떨까? 기기가 파손되더라도 영상은 클라우드에 살아있고, 용량 걱정 없이 언제 어디서든 확인할 수 있다. **NEVES-BOX**는 그 아이디어를 서비스로 구현한 결과물이다.

- 실시간 저장으로 데이터 손실 방지
- 클라우드를 통해 어디서든 영상 재생 가능
- 영상 보관 기한 증가

# 2. 내 역할 및 기여

> **Web App 팀 — 유저 서버 / 메일 서버 / 재생 서버 개발 + IaC·DevOps 환경 구축 담당**

## 담당 서버 개발

**유저 서버 (Django)**

회원가입, 로그인, JWT 발급·인증 로직을 담당했다. 파드를 스케일 아웃했을 때 사용자 요청이 랜덤으로 로드 밸런싱되면서 기존 세션을 찾지 못해 이메일 인증이 간헐적으로 실패하는 문제가 있었다. 동일 IP의 요청은 항상 동일 파드로 향하도록 Session Affinity를 적용해 해결했다.

**메일 서버 (FastAPI)**

Gmail SMTP 기반으로 인증 메일과 사고 알림 메일을 전송하는 서버를 구현했다. Jaeger로 API 처리 시간을 모니터링하던 중 메일 전송에 비정상적으로 긴 시간이 소요되는 걸 발견했다. 메일을 보낼 때마다 SMTP SSL 연결과 로그인을 반복하는 구조가 원인이었고, 이 중복 인증 로직을 최적화해 전송 시간을 3초대에서 1초대 중반으로 단축했다.

**재생 서버 (FastAPI)**

S3 비공개 버킷을 직접 노출하지 않고, 일정 시간이 지나면 만료되는 Signed URL을 생성해 영상에 접근하는 방식으로 보안성을 확보했다. CloudFront와 연동해 캐싱 및 저지연 스트리밍도 함께 구현했다.

## 인프라 및 DevOps

**IaC (Terraform)**

처음에는 콘솔에서 직접 리소스를 만들다 보니 실수가 잦고 재현도 어려웠다. Terraform으로 VPC, Subnet, EKS 클러스터 등 전체 인프라를 코드화했고, 개발이 없는 시간대에는 리소스를 내렸다가 다시 올리는 방식으로 비용도 줄였다. ExternalDNS를 적용해 서비스 배포 시 Route 53 레코드가 자동으로 연결되도록 했다.

**스토리지 성능 개선 (EFS → EBS)**

초기에는 EFS를 사용했는데, 파일 시스템 스캔 시간 편차가 커서 업로드 파이프라인이 불안정했다. EBS(StatefulSet)로 전환한 결과, Prometheus로 측정한 스캔 시간이 0.049초에서 0.009초로 약 81% 단축됐고 전송 속도도 안정화됐다.

**CI/CD**

GitHub Actions로 이미지를 빌드해 ECR에 푸시하고, Argo CD가 GitOps 방식으로 EKS에 자동 배포하는 파이프라인을 구축했다.

## 영상 전송 프로토콜 — SRT

![](https://velog.velcdn.com/images/paramad/post/a51d1b8c-9be8-4838-95f7-361e0373f140/image.png)

영상 전송 프로토콜로 SRT(Secure Reliable Transport)를 채택했다. RTMP는 안정적이지만 지연이 2~5초, WebRTC는 지연이 짧지만 패킷 손실에 취약하다. SRT는 UDP 기반으로 지연이 1초 내외이면서, 손실된 패킷만 선택적으로 재전송해 안정성도 확보할 수 있었다.

## 영상 재생 — CloudFront + Signed URL

![](https://velog.velcdn.com/images/paramad/post/64a8a4f6-295b-49b2-9ea0-55d7f79174d3/image.png)

S3 버킷을 직접 공개하지 않고, 재생 서버가 일정 시간 후 만료되는 Signed URL을 생성해 전달한다. CloudFront를 통해 정적 콘텐츠를 캐싱하여 속도와 보안성을 함께 확보했다.

## 서비스 메시 — Istio

![](https://velog.velcdn.com/images/paramad/post/09dafa4d-4335-4a8d-91bc-78548fc63195/image.png)

Istio의 사이드카 프록시(Envoy)를 모든 파드에 주입해 서비스 간 트래픽을 제어했다. 애플리케이션은 비즈니스 로직에만 집중하고, 트래픽 제어·인증·관측성은 Envoy가 담당한다. Kiali로 실시간 네트워크 트래픽을 시각화하고, Jaeger로 분산 추적을 수행했다.

# 4. 인프라 구축 및 성능 최적화

## 스토리지 개선 (EFS → EBS)

![](https://velog.velcdn.com/images/paramad/post/3a5e2560-9514-4921-a394-4bdd7502e900/image.png)

![](https://velog.velcdn.com/images/paramad/post/3e3abdc8-a394-488b-90d0-c6b928d905e2/image.png)

초기 EFS 구조에서는 파일 시스템 스캔 시간 편차가 크고 불안정했다. EBS로 전환한 후 Prometheus로 측정한 결과 스캔 시간이 0.049초에서 0.009초로 단축됐고, 측정값도 안정적으로 수렴했다.

![](https://velog.velcdn.com/images/paramad/post/12cdb095-9357-43c3-ae52-ea7fb3ecbb97/image.png)

![](https://velog.velcdn.com/images/paramad/post/8dc8514c-879d-4290-8a15-05e162d1df5e/image.png)

## 비용 최적화 — S3 수명 주기

7일이 지난 영상은 S3에서 Glacier로 자동 이동되도록 수명 주기 규칙을 설정했다. 자주 조회되지 않는 오래된 영상을 저가 스토리지로 내려 보관 비용을 줄였다.

## 로드 밸런서 이중화

로드 밸런서를 두 개로 분리해 운영했다. 블랙박스 기기에서 들어오는 SRT(UDP) 트래픽과 웹 클라이언트의 HTTPS(TCP) 트래픽은 특성이 달라 하나의 로드 밸런서로 처리하기 어렵기 때문이다.

# 5. 장애 대응

## 서킷 브레이커

![](https://velog.velcdn.com/images/paramad/post/4c1f0562-caa7-4bb9-85ff-cfbeb2a24ee2/image.png)

특정 서비스에서 3회 연속 5xx 에러가 발생하면 40초간 서킷을 개방(Open)해 해당 서비스로의 트래픽을 차단한다. 장애가 연쇄적으로 전파되는 것을 막고, 해당 서비스가 회복할 시간을 확보하는 방식이다.

적용 전에는 응답 시간이 5~7ms였지만, 적용 후에는 불필요한 요청을 차단해 90~100µs로 줄었다.

# 6. 문제 해결

## 메일 전송 오버헤드

![](https://velog.velcdn.com/images/paramad/post/935fbaa6-7b5f-4325-944f-323640ffa83c/image.png)
![](https://velog.velcdn.com/images/paramad/post/f6f7e913-a400-418e-9814-2469abed7745/image.png)

Jaeger로 API 처리 시간을 확인하다가 메일 전송에 비정상적으로 긴 시간이 걸리는 걸 발견했다. 원인은 메일을 보낼 때마다 SMTP SSL 연결과 로그인을 반복하는 구조였다. 이 중복 인증 로직을 최적화해 전송 시간을 3초대 초반에서 1초대 중반으로 줄였다.

## 세션 어피니티 (Session Affinity)

![](https://velog.velcdn.com/images/paramad/post/3c21138c-9a81-46ed-95af-54e429d26820/image.png)
![](https://velog.velcdn.com/images/paramad/post/44bf3392-4398-4d98-8a14-89f50c465a56/image.png)

파드를 스케일 아웃하자 이메일 인증이 간헐적으로 실패하기 시작했다. 사용자 요청이 로드 밸런서를 통해 랜덤 파드로 분산되면서, 인증 코드를 저장한 파드가 아닌 다른 파드로 요청이 들어와 세션을 찾지 못하는 게 문제였다. 동일 IP 요청은 항상 동일 파드로 라우팅되도록 Session Affinity를 적용해 해결했다.

# 7. DevOps 및 협업

## IaC (Terraform)

![](https://velog.velcdn.com/images/paramad/post/34ebe607-cc09-48fa-a253-7e9b7dbb9602/image.png)
![](https://velog.velcdn.com/images/paramad/post/85e8637f-a518-48c7-917f-67520363702a/image.png)

콘솔에서 직접 리소스를 생성하다 보니 실수가 반복됐다. Terraform으로 인프라 전체를 코드화하고, ExternalDNS로 서비스 배포 시 Route 53 도메인이 자동으로 연결되도록 구성했다. 24시간 가동할 필요가 없는 개발 환경은 작업이 없을 때 Destroy했다가 다시 올리는 방식으로 비용을 아꼈다.

# 8. 아쉬운 점

**Istio Sidecar OOM 문제**

파드마다 Envoy 사이드카를 주입하는 구조라 파드 수가 늘어날수록 메모리 오버헤드가 커졌고, 실제로 OOM이 발생했다. 사이드카 없이 노드 레벨에서 트래픽을 처리하는 Istio Ambient Mode로 전환했으면 더 나았을 것 같다.

**부하 테스트 부재**

JMeter나 nGrinder 같은 도구로 실제 한계점을 검증해보지 못했다. 서킷 브레이커 임계값 등 설정값들이 실측 데이터 없이 결정된 것이 아쉽다.
