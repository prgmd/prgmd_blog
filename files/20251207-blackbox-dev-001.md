# 1. 프로젝트 개요 및 배경

교통사고가 났을 때, 블랙박스 기기가 파손되거나 범인이 증거를 없애기 위해 기기를 가져가버리면 영상을 확보할 수 없습니다. 이 문제에서 프로젝트가 시작되었습니다.

만약 영상이 기기에 저장되는 동시에 클라우드에도 실시간으로 올라간다면 어떨까요? 기기가 파손되거나 분실되더라도 영상 데이터는 클라우드에 안전하게 남아 있고, 용량 걱정 없이 언제 어디서든 확인할 수 있습니다. **NEVES-BOX**는 그 아이디어를 실제 서비스로 구현한 결과물입니다.

- 실시간 저장으로 데이터 손실 방지
- 클라우드를 통해 어디서든 영상 재생 가능
- 영상 보관 기한 증가

# 2. 담당 역할 및 기여

> **Web App 팀 — 유저 서버 / 메일 서버 / 재생 서버 개발 + IaC·DevOps 환경 구축 담당**

## 담당 서버 개발

**유저 서버 (Django)**

회원가입, 로그인, JWT 발급·인증 로직을 담당했습니다. 개발 중 한 가지 까다로운 문제가 있었습니다. 서버 부하를 분산하기 위해 파드(Pod)를 여러 개로 늘렸더니(스케일 아웃), 이메일 인증이 간헐적으로 실패하기 시작한 것입니다.

원인을 분석해보니, 사용자 요청이 로드 밸런서를 통해 랜덤한 파드로 전달되면서 생기는 문제였습니다. 예를 들어 인증 코드를 A 파드에서 발급받았는데, 코드를 확인하는 요청이 B 파드로 가버리면 B 파드는 해당 세션 정보가 없어서 인증에 실패하게 됩니다. 이를 해결하기 위해 Session Affinity(세션 어피니티)를 적용했습니다. 같은 IP에서 오는 요청은 항상 같은 파드로 보내도록 고정하는 설정으로, 파드가 아무리 늘어나도 세션을 잃지 않게 되었습니다.

**메일 서버 (FastAPI)**

Gmail SMTP를 이용해 인증 메일과 사고 알림 메일을 발송하는 서버를 구현했습니다. 개발 완료 후 Jaeger(분산 추적 도구)로 API 처리 시간을 모니터링하던 중, 메일 전송에 비정상적으로 긴 시간이 걸린다는 것을 발견했습니다.

원인은 메일을 보낼 때마다 SMTP 서버와의 SSL 연결을 새로 맺고, 로그인까지 반복하는 구조에 있었습니다. 마치 편지를 한 통 보낼 때마다 우체국 문을 새로 열고, 신분증을 매번 다시 확인받는 것과 같은 비효율이었습니다. 이 중복 인증 로직을 최적화한 결과, 메일 전송 시간이 3초대 초반에서 1초대 중반으로 약 50% 단축되었습니다.

**재생 서버 (FastAPI)**

사용자가 영상을 볼 수 있도록 URL을 생성해주는 서버입니다. S3 버킷을 그냥 공개해버리면 누구나 영상에 접근할 수 있어 보안 문제가 생깁니다. 이를 막기 위해 Signed URL 방식을 사용했습니다. 재생 서버가 일정 시간(예: 1시간) 후 자동으로 만료되는 임시 접근 링크를 생성해 사용자에게 전달하는 방식입니다. 링크가 만료되면 더 이상 영상에 접근할 수 없어 보안성이 확보됩니다. 여기에 CloudFront를 연동해 영상을 캐싱함으로써 재생 속도도 함께 높였습니다.

## 인프라 및 DevOps

**IaC — Terraform**

초기에는 AWS 콘솔에서 직접 리소스를 만들었는데, 실수가 생겨도 어디서 잘못됐는지 추적하기 어렵고, 같은 환경을 다시 만들려면 처음부터 반복해야 한다는 문제가 있었습니다. Terraform을 도입해 VPC, Subnet, EKS 클러스터 등 전체 인프라를 코드로 관리했습니다. 코드만 있으면 동일한 환경을 언제든 다시 만들 수 있고, 변경 이력도 Git으로 추적할 수 있습니다.

또한 개발할 때만 인프라가 필요하므로, 작업이 없는 시간에는 Terraform으로 리소스를 내렸다가 필요할 때 다시 올리는 방식으로 비용을 절감했습니다. ExternalDNS도 함께 적용해, 새로운 서비스가 배포될 때 Route 53 DNS 레코드가 자동으로 연결되도록 구성했습니다.

**스토리지 성능 개선 — EFS → EBS**

영상 파일을 임시로 저장하는 스토리지로 처음에는 EFS(Elastic File System)를 사용했습니다. EFS는 여러 서버가 동시에 같은 파일에 접근할 수 있어 편리하지만, 파일 시스템을 스캔하는 시간의 편차가 크고 불안정하다는 문제가 있었습니다. 실제로 스캔 시간이 어떨 때는 2초, 어떨 때는 5초가 넘게 걸리는 등 들쭉날쭉해서 업로드 파이프라인 전체가 불안정해졌습니다.

EBS(Elastic Block Store)로 전환한 뒤 Prometheus로 스캔 시간을 측정했더니, 0.049초에서 0.009초로 약 81% 단축되었고 측정값도 안정적으로 수렴했습니다.

**CI/CD 파이프라인**

코드를 수정할 때마다 수동으로 빌드하고 배포하는 건 번거롭고 실수도 생깁니다. GitHub Actions로 이미지를 자동 빌드해 ECR(컨테이너 레지스트리)에 푸시하고, Argo CD가 변경사항을 감지해 EKS 클러스터에 자동 배포하는 GitOps 파이프라인을 구축했습니다. PR이 올라오면 Gemini CLI가 변경된 코드를 분석해 자동으로 코드 리뷰 코멘트를 남기는 시스템도 함께 적용했습니다.

# 3. 시스템 설계 및 아키텍처

## MSA 도입

![](https://velog.velcdn.com/images/paramad/post/d7b4ddc4-f621-4b91-b09e-f5ccdce445b7/image.png)

모든 기능을 하나의 단위로 묶어 배포하는 방식을 모놀리식(Monolithic)이라고 합니다. 개발 초기에는 빠르지만, 서비스가 커질수록 하나의 기능을 수정할 때 전체를 다시 배포해야 하고, 특정 서버에 장애가 생기면 전체가 영향을 받는 단점이 있습니다.

이 프로젝트에서는 MSA(마이크로서비스 아키텍처)를 채택했습니다. 기능별로 서버를 분리해 각각 독립적으로 배포하고 운영할 수 있도록 했습니다. 설계 단계에서는 이벤트 스토밍(Event Storming)을 활용해 서비스에서 발생하는 주요 사건들을 중심으로 구조를 정리하고 팀원 간 공유했습니다.

## 영상 전송 프로토콜 — SRT

![](https://velog.velcdn.com/images/paramad/post/a51d1b8c-9be8-4838-95f7-361e0373f140/image.png)

블랙박스에서 클라우드로 영상을 전송할 프로토콜을 선택하는 과정에서 세 가지 후보를 비교했습니다.

| 프로토콜 | 지연 시간 | 특징 |
|---|---|---|
| RTMP | 2~5초 | 안정적이나 지연이 김 |
| WebRTC | 0.5초 미만 | 초저지연이지만 패킷 손실에 취약 |
| **SRT** | **1초 내외** | **안정성과 저지연 모두 확보** |

SRT(Secure Reliable Transport)는 UDP 기반이라 지연이 짧으면서도, 패킷이 손실되면 해당 패킷만 선택적으로 재전송하는 ARQ 방식으로 안정성을 보완합니다. 블랙박스 영상처럼 실시간성과 신뢰성이 모두 중요한 상황에 적합해 SRT를 선택했습니다.

## 영상 재생 — CloudFront + Signed URL

![](https://velog.velcdn.com/images/paramad/post/64a8a4f6-295b-49b2-9ea0-55d7f79174d3/image.png)

영상 파일을 S3에 저장하지만, 버킷을 직접 공개하면 링크를 아는 누구나 영상에 접근할 수 있는 보안 문제가 생깁니다. 이를 막기 위해 재생 서버가 Signed URL(서명된 URL)을 생성해 전달하는 방식을 사용했습니다. 이 URL은 일정 시간이 지나면 자동으로 만료되어 더 이상 접근할 수 없습니다. CloudFront를 앞단에 두어 자주 요청되는 영상을 캐싱함으로써 재생 속도도 높였습니다.

## 서비스 메시 — Istio

![](https://velog.velcdn.com/images/paramad/post/09dafa4d-4335-4a8d-91bc-78548fc63195/image.png)

MSA 환경에서는 수많은 서비스가 서로 통신하는데, 각 서비스마다 인증·트래픽 제어·로깅 코드를 직접 넣으면 중복이 많아집니다. Istio는 이 문제를 사이드카 프록시(Envoy) 방식으로 해결합니다. 각 파드에 Envoy 프록시를 자동으로 주입해, 서비스 코드는 비즈니스 로직에만 집중하고 트래픽 제어·인증·관측성은 프록시가 담당하게 합니다.

Kiali로 서비스 간 트래픽 흐름을 실시간으로 시각화하고, Jaeger로 요청이 어떤 서비스를 거쳐 처리되는지 분산 추적을 수행했습니다.

# 4. 인프라 구축 및 성능 최적화

## 스토리지 개선 (EFS → EBS)

![](https://velog.velcdn.com/images/paramad/post/3a5e2560-9514-4921-a394-4bdd7502e900/image.png)

![](https://velog.velcdn.com/images/paramad/post/3e3abdc8-a394-488b-90d0-c6b928d905e2/image.png)

블랙박스에서 영상이 들어오면 MediaMTX 서버가 SRT 스트림을 수신해 mp4 파일로 변환한 뒤 파일 시스템에 저장합니다. DB 업로드 서버는 이 파일 시스템을 주기적으로 스캔해 새로운 파일을 S3로 올립니다.

초기에 EFS를 사용했을 때, 이 스캔 시간이 들쭉날쭉해서 파이프라인 전체 흐름이 불안정했습니다. EBS로 전환한 뒤 Prometheus로 측정한 결과, 스캔 시간이 0.049초에서 0.009초로 약 81% 단축되었고 편차도 크게 줄었습니다.

![](https://velog.velcdn.com/images/paramad/post/12cdb095-9357-43c3-ae52-ea7fb3ecbb97/image.png)

![](https://velog.velcdn.com/images/paramad/post/8dc8514c-879d-4290-8a15-05e162d1df5e/image.png)

## 비용 최적화 — S3 수명 주기

S3에 모든 영상을 무기한 보관하면 스토리지 비용이 계속 늘어납니다. 7일이 지난 영상은 S3 Standard에서 Glacier로 자동 이동되도록 수명 주기 규칙을 설정했습니다. Glacier는 자주 조회하지 않는 데이터를 장기 보관하는 데 특화된 저가 스토리지로, 비용을 크게 줄일 수 있습니다.

## 로드 밸런서 이중화

로드 밸런서를 두 개로 분리해 운영했습니다. 이유는 트래픽 유형이 근본적으로 다르기 때문입니다.

- **블랙박스 트래픽:** SRT 프로토콜 기반의 UDP 스트림 → NLB(Network Load Balancer)
- **웹 클라이언트 트래픽:** HTTPS 기반의 TCP 요청 → ALB/NLB

UDP와 TCP는 동작 방식이 달라 하나의 로드 밸런서로 함께 처리하기 어렵습니다. 역할에 따라 분리함으로써 각 트래픽 유형에 맞는 처리가 가능해졌습니다.

# 5. 장애 대응

## 서킷 브레이커

![](https://velog.velcdn.com/images/paramad/post/4c1f0562-caa7-4bb9-85ff-cfbeb2a24ee2/image.png)

MSA 환경에서는 한 서비스에 장애가 생겼을 때 그 서비스에 계속 요청을 보내면 에러가 전체 시스템으로 퍼질 수 있습니다. 서킷 브레이커(Circuit Breaker)는 이를 막는 안전장치입니다. 전기 회로의 차단기처럼, 특정 조건이 충족되면 해당 서비스로의 요청을 차단합니다.

이 프로젝트에서는 특정 서비스에서 3회 연속 5xx 에러가 발생하면 40초간 서킷을 열어(Open) 해당 서비스로의 트래픽을 차단했습니다. 장애 서비스가 회복할 시간을 벌어주고, 에러가 전체로 번지는 것을 방지합니다.

서킷 브레이커 적용 전에는 장애 서비스에 요청이 쌓이면서 응답 시간이 5~7ms였는데, 적용 후에는 요청 자체를 차단하므로 90~100µs로 줄었습니다.

![](https://velog.velcdn.com/images/paramad/post/aafae4e3-0a81-4b70-895c-3961a22c2bae/image.png)

# 6. 문제 해결

## 메일 전송 오버헤드

![](https://velog.velcdn.com/images/paramad/post/935fbaa6-7b5f-4325-944f-323640ffa83c/image.png)
![](https://velog.velcdn.com/images/paramad/post/f6f7e913-a400-418e-9814-2469abed7745/image.png)

Jaeger로 API 처리 흐름을 살펴보다가 메일 전송 구간에서 유독 긴 시간이 소요된다는 것을 발견했습니다. 코드를 분석해보니, 메일을 한 통 보낼 때마다 아래 과정을 매번 반복하고 있었습니다.

1. SMTP 서버에 SSL 연결
2. 로그인 인증
3. 메일 전송

연결을 한 번 맺어두고 재사용하면 될 것을, 매번 새로 연결하고 인증하는 구조였습니다. 이 중복 과정을 없애도록 로직을 최적화한 결과, 전송 시간이 3초대 초반에서 1초대 중반으로 단축되었습니다.

## 세션 어피니티 (Session Affinity)

![](https://velog.velcdn.com/images/paramad/post/3c21138c-9a81-46ed-95af-54e429d26820/image.png)
![](https://velog.velcdn.com/images/paramad/post/44bf3392-4398-4d98-8a14-89f50c465a56/image.png)

부하 분산을 위해 유저 서버 파드를 여러 개로 늘렸더니, 이메일 인증이 간헐적으로 실패하는 현상이 생겼습니다.

문제의 원인은 이렇습니다. 회원가입 시 인증 코드를 발급하는 요청이 A 파드로 가면, A 파드는 세션 스토리지에 인증 코드를 저장합니다. 그런데 사용자가 코드를 입력하는 요청이 로드 밸런서를 통해 B 파드로 전달되면, B 파드에는 해당 세션 정보가 없어서 인증에 실패합니다.

이를 Session Affinity(세션 어피니티)로 해결했습니다. 같은 IP에서 오는 요청은 항상 같은 파드로 보내도록 설정하면, 파드가 아무리 늘어나도 처음 세션을 만든 파드로 요청이 일관되게 전달됩니다.

![](https://velog.velcdn.com/images/paramad/post/34ebe607-cc09-48fa-a253-7e9b7dbb9602/image.png)
![](https://velog.velcdn.com/images/paramad/post/85e8637f-a518-48c7-917f-67520363702a/image.png)

콘솔에서 직접 리소스를 생성하면 어떤 설정으로 만들었는지 추적이 어렵고, 같은 환경을 다시 만들 때도 처음부터 반복해야 합니다. Terraform으로 인프라 전체를 코드화하면 Git으로 변경 이력을 관리할 수 있고, 코드만으로 동일한 환경을 재현할 수 있습니다.

ExternalDNS를 함께 적용해 새로운 서비스가 배포될 때 Route 53 DNS 레코드가 자동으로 연결되도록 했습니다. 또한 24시간 가동이 필요 없는 개발 환경은 작업이 없을 때 리소스를 내렸다가 필요할 때 다시 올리는 방식으로 비용을 절감했습니다.

## CI/CD 파이프라인

![](https://velog.velcdn.com/images/paramad/post/19b5ef2a-dfde-4310-aeb8-ced0d556b0a9/image.png)

코드를 수정할 때마다 수동으로 빌드하고 배포하는 것은 번거롭고 실수가 생기기 쉽습니다. 아래와 같은 자동화 파이프라인을 구성했습니다.

1. 코드를 GitHub에 푸시
2. GitHub Actions가 Docker 이미지를 빌드해 ECR에 업로드
3. Argo CD가 변경을 감지해 EKS 클러스터에 자동 배포 (GitOps)

PR이 올라오면 Gemini CLI가 변경된 코드(git diff)를 분석해 자동으로 코드 리뷰 코멘트를 남기는 시스템도 함께 적용했습니다.

# 8. 아쉬운 점

**Istio Sidecar OOM 문제**

Istio의 사이드카 방식은 파드마다 Envoy 프록시 컨테이너를 하나씩 추가로 주입합니다. 파드 수가 늘어날수록 Envoy 컨테이너도 그만큼 늘어나 메모리 사용량이 함께 증가합니다. 실제로 운영 중에 OOM(Out of Memory)이 발생하는 문제를 겪었습니다.

Istio Ambient Mode를 사용하면 사이드카 없이 노드 레벨에서 트래픽을 처리할 수 있어 오버헤드를 크게 줄일 수 있습니다. 처음부터 Ambient Mode로 설계했으면 더 나았을 것 같습니다.

**부하 테스트 부재**

JMeter나 nGrinder 같은 도구로 실제 한계 트래픽을 측정해보지 못했습니다. 서킷 브레이커의 임계값(3회 연속 에러, 40초 차단)도 실측 데이터 없이 경험적으로 결정한 것이라, 실제 운영 환경에서 최적값인지 검증하지 못한 점이 아쉽습니다.
