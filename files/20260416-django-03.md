# Model
## 1. Model
> DB와 Python 객체로 추상화된 형태로 상호작용

Django에서는 개발자가 DB에 대한 깊은 지식이 없어도 쉽게 데이터를 관리할 수 있도록 강력한 기능을 많이 제공한다. 

```
[ 사용자 요청 ]
      │
      ▼
  urls.py (사용자 요청이 어디로 갈지 정해줌)
      │
      ▼
  views.py (실행/로직) ◀───▶ models.py (데이터 정의 및 상호작용) ◀───▶ [ Database ]
      │
      ▼
  templates (받은 데이터를 화면으로 표시)
      │
      ▼
[ 사용자 응답 ]
```

`urls.py`에 사용자 요청이 들어오고, 들어온 요청이 `views.py`에서 처리된다면, `models.py`는 DB를 정의하고 상호작용하는 친구다. `templates`는 얻은 결과값을 사용자에게 보여줄 화면을 구성한다.

### 1.1 Model Class / Model Field
Aricles 앱에서 `models.py`에 다음과 같이 코드를 작성했다고 가정하자. 이게 곧 테이블 설계도가 되는 것.

``` python
class Article(models.Model):
	title = models.CharField(max_length=10)
    content = models.TextField()
```

잘 보면 `Model`이라는 부모 클래스를 **상속받는 걸 볼 수 있다**. `Model`은 **모델 관련 모든 코드가 이미 작성된 클래스**. 개발자는 다른 거 신경 안 쓰고, 테이블 구조 어떻게 설계할지만 고민하면 된다. 그 아래 줄들은 필드 이름, 데이터 유형, 제약 조건 등을 정의한 문장들로, 이 부분은 **Model Field**라고 부른다. 막상 만들고나면 `id` 속성도 생기는데, 이건 만든 적 없는데요? 하고 당황하지 말자. 편의상 Django가 알아서 만들어준 필드. `id`는 대체로 Primary Key로 활용하기 좋다.

※ 사실 Django는 SQLite를 기본 내장 DB로 사용하고 있고, SQLite는 문자열 컬럼 길이에 크게 제한을 안 둔다. 그래도 유효성 검사를 고려해서 명시적으로 `max_length` 같이 남기는 건 권장되는 사항.

#### Field Types
필드 유형은 상당히 많다. 공식 문서 참조할 것.

- CharField: 문자열
- TextField: 길이 제한 없는 대용량 텍스트 (무한은 아님)
- IntegerField, FloatField: 숫자 타입들
- FileField, ImageField: 파일 관련 타입들

#### Field Options
동작과 제약 조건 정의 파트. 

- null: NULL 값 허용 여부 (기본값 False)
- blank: 빈 값 허용 여부 (기본값 False)
- default: 기본값 설정

### 1.2 Migrations
Model Class의 변경사항을 DB에 최종 반영. 모든 변경사항이 코드로 관리되기 때문에 협업 시 모델 변경 내역에 대한 추적과 공유가 수월하다. 그리고 웬만해서는 이 파일들은 건드리지 말 것.

> 마이그레이션 파일 생성 명령어
``` bash
python manage.py makemigrations
```

이렇게 만들면 `0001_initial.py` 같이 일종의 최종 설계도 파일이 만들어진다. 마이그레이션 파일은 모델 변경사항을 기록한 Python 코드. DB 변경 내역을 순차적으로 저장해 추적 관리한다.

> 마이그레이션 파일 DB에 반영
```
python manage.py migrate
```

#### 추가 Migration
이미 생성된 테이블에 필드를 추가할 경우 → 모델 클래스 수정한 다음 `makemigrations` 명령어 재입력. 

```
created_at = models.DateTimeField(auto_now_add=True)
updated_at = models.DateTimeField(auto_now=True)
```

- auto_now: 데이터가 저장될 때마다 자동으로 현재 날짜시간 저장
- auto_now_add: 처음 생성될 때만 자동으로 현재 날짜시간 저장

이 때, 선택지가 두 개 뜰 것이다. 1번은 '현재 대화 유지 + 직접 기본 값 입력' / 2번은 '현재 대화에서 나간 뒤, `models.py`에서 기본 값 설정하는 법'

### 1.3 DB 초기화
`db.sqlite3` 파일을 삭제하면 된다.

### 1.4 추가 명령어
- `showmigrations`: migrations 파일들이 migrate 됐는지 안됐는지 여부 확인
- `sqlmigrate`: 해당 migration 파일이 SQL 언어로 어떻게 번역되어 DB에 전달되는지 확인
  - `python manage.py sqlmigrate 앱이름 마이그레이션이름` 문법.

※ 최초 migrate시 출력 내용이 많은 이유: Django 프로젝트가 동작하기 위해 미리 작성된 기본 내장 app들에 대한 miragtion 파일들이 함께 들어가기 때문. 걱정 ㄴㄴ

## 2. Admin Page
별다른 추가 없이 관리자 인터페이스를 누릴 수 있다. CRUD 작업을 간편하게 수행 가능. 

```
python manage.py createsuperuser
```

입력 정보는 다음과 같다.
- `username`: 로그인시 사용할 아이디
- `email address`: 선택사항
- `password`: 로그인시 사용할 비밀번호
- `password(again)`: 비밀번호 확인

### 2.1 관리
관리자 인터페이스 접속 하면 로그인 후 아무것도 보이지 않는 것이 정상. `admin.py`에 작성한 모델 클래스를 등록해야 사이트에서 확인이 가능하다.

```
from django.contrib import admin
from .models import Article

admin.site.register(Article)
```

이 경우 모델 클래스 등록 및 확인이 가능하다.

# ORM
## 1. ORM이란?
> Object-Relational-Mapping. 객체 지향 프로그래밍 언어의 객체와, 데이터베이스의 데이터를 매핑하는 기술.

기본적으로 Python과 DB는 서로 언어가 달라 소통이 불가능하다. 누군가 중간에서 번역을 수행해야 함. 이 때 ORM이 그 역할을 한다. ORM은 Django 개발자를 위해 'QuerySet API'라는 특별한 도구를 제공한다.

### 1.1 ORM을 쓰는 이유
- DB 추상화
	개발자는 특정 DB에 종속되지 않고 일관된 방식으로 데이터를 다룰 수 있게 된다.
- 객체 지향적 접근
  - DB 테이블을 Python 객체로 다룰 수 있어 객체 지향의 이점을 활용할 수 있다.

## 2. QuerySet API
DB의 복잡한 SQL 쿼리문을 직관적인 Python 코드로 다룰 수 있게 해주는 강력한 번역기. 

### 2.1 기본 구문 구조
```
모델클래스.매니저.쿼리셋API()
```

- 모델클래스: 주로 테이블의 스키마(필드, 데이터 타입)를 정의한다. 가장 기본적인 구조체.
- 매니저: 조회 작업을 위한 기본 인터페이스. 모델 클래스가 DB 쿼리 작업을 수행할 수 있도록 제공되는 진입점이다.
- 쿼리셋 API: 참고로 Django는 모든 모델에 objects 이름의 매니저를 자동으로 추가하는데, 이 매니저가 여러 쿼리 메서드를 가지고 있다.

### 2.2 QuerySet
#### `all()`
전체 데이터 조회

#### `filter()`
주어진 매개변수와 일치하는 개체를 포함하는 쿼리셋 반환. 예를 들어 `content=django!`

#### `get()`
주어진 매개변수와 일치하는 객체 반환. 쿼리셋을 반환하는게 아님.

### 2.3 정보 업데이트
인스턴스 변수를 변경한 뒤 `save` 메서드를 호출하면 된다

### 2.4 정보 삭제
삭제하려는 데이터를 조회한 뒤 `delete` 메서드 호출. 

``` python
article = Article.objects.get(pk=1)
article.delete()
```

### 2.3 Field Lookups
단순 동치 비교(=)를 넘어, 더 상세 조건으로 데이터를 조회할 수 있도록 Django ORM이 제공하는 기능.

#### 기본 문법
```
Article.objects.filter(모델필드명__조회조건='비교값')
```

모델의 필드 이름 뒤에 이중 밑줄을 붙이고 원하는 조회 유형을 명시하면 손쉽게 필터링 로직을 구성할 수 있다.

#### 조회 조건
- `exact/iexact`: (대소문자 구분 / 구분 없이) 정확히 일치하는 값 찾기
- `contains/icontains`: (대소문자 구분 / 구분 없이) 문자열 내 특정값 포함되어 있는지 확인
- `gt/gte/lt/lte`: 숫자, 날짜 필드에 대해 크고 작음 비교

## 3. ORM with view
### 3.1 Read
``` python
# articles/urls.py
urlpatterns = [
	path('<int:pk>/', views.detail, name='detail'),
]

# articles/views.py
def detail(request, pk):
	article = Article.objects.get(pk=pk)
    context = {
    	'article': article,
    }
  	return render(reqeust, 'articles/detail.html', context)
```

### 3.2 Crate
Create 로직을 구현하기 위해서는 view 함수가 두 개 필요하다 (사용자 입력 데이터를 받을 페이지를 렌더링할 new, 그 데이터를 받아 DB에 저장하는 create)

``` python
# articles/urls.py
urlpatterns = [
	path('new/', views.new, name='new'),
    path('create/', views.create, name='create'),
]

# articles/views.py
def new(request):
	return render(reqeust, 'articles/new.html')

def create(request):
	title = request.GET.get('title')
	content = request.GET.get('content')
    
    article = Article(title=title, content=content)
    article.save()
    
	return render(reqeust, 'articles/create.html')
```

``` html
<!-- templates/articles/index.html -->
<h1>Articles</h1>
<a href="{% url 'articles:new' %}">NEW</a>
<hr>

<!-- templates/articles/detail.html -->

<h1>NEW</h1>
<form action="{% url 'articles:create' %}" method="GET">
  <div>
    <label for="title">TITLE: </label>
    <input type="text" name="title" id="title">
  </div>

    <textarea name="content" id="content"></textarea>
  </div>
  <input type="submit">
</form>

<a href="{% url 'articles:index' %}">[back]</a>

<!-- templates/articles/create.html -->
<h1>게시글이 작성 되었습니다.</h1>
```

### 3.3 HTTP request methods
데이터에 대해 수행을 원하는 작업(행동)을 나타내는 것. 원하는 작업 종류를 알려주는 역할이다.

#### GET Method
서버로부터 데이터를 요청하고 받아오는 데 사용. 검색 쿼리 전송, 웹 페이지 요청, API에서 데이터를 조회하는 등...

- URL의 쿼리 문자열을 통해 데이터를 전송함
  - `http://127.0.0.1:8000/articles/create/?title=제목&content=내용`
- 다만 대량 데이터 전송은 적합하지 않음. URL 길이는 제한이 있기 때문.
- 또한 요청 URL이 브라우저 히스토리에도 남음.
- 브라우저는 GET 요청 응답을 로컬에 저장할 수 있음. 동일 URL로 다시 요청 시 서버에 접속하지 않고 저장된 결과를 사용해 페이지 로딩 시간을 크게 단축시킴 → **캐싱**

#### POST Method
서버에 데이터를 제출해 리소스를 변경(생성, 수정, 삭제)하는 데 사용. 로그인 정보 제출, 파일 업로드, 새 데이터 생성(게시글 생성 등), API에서 데이터 변경 요청 등...

- HTTP Body를 통해 데이터를 전송함 (GET에 비해 더 많은 데이터 전송 가능)
- 브라우저 히스토리에 남지 않음.
- 기본적으로 캐시할 수 없음. POST가 서버 상태를 변경하는 작업이기 때문. (캐시는 서버를 거치지 않고 저장된 결과를 반환하는 것)

### 3.4 HTTP reponse status code
서버가 클라이언트 요청에 대한 처리 결과를 나타내는 3자리 숫자.

#### 403 Forbidden
> 서버에 요청 전달 OK / 권한 때문에 거절

CSRF 토큰 누락 등이 대표적. Django는 CSRF 토큰을 필요로 한다. 모든 중요 요청마다 내가 직접 보낸게 맞다는 일회용 비밀 코드를 함께 보내도록 해 위조 요청을 막아준다. 어떻게 설정하는지? DTL의 태그를 이용. 또한 이 태그를 설정하면 더이상 Query String 형태로 보내던 데이터가 표기되지 않는 것을 볼 수 있다.

``` html
<form action="{% url 'articles:create' %}" method="POST">
  {% csrf_token %}
```

#### CSRF(Cross Site Request Forgery; 사이트 간 요청 위조)
사용자가 자신의 의지와 무관하게 공격자가 의도한 행동을 특정 웹사이트에 요청하게 만드는 해킹 방식. 위조된 인감도장이라 보면 된다. 

예를 들어 은행이 사용자를 신뢰하고 있다는 증표의 세션 쿠키를 브라우저를 통해 발급한다고 가정해보자. 해커는 미끼 링크를 사용자에게 보내고, 이 링크의 실제 내용은 '내 돈 100만원을 해커에게 송금하라'는 내용이 담긴 위조된 위임장이다. 만약 미끼 링크를 클릭하게 되면 브라우저는 자기도 모르게 은행에 위조된 위임장(송금 요청)을 보내게 되고, 이때부터 브라우저는 은행에 세션 쿠키를 자동으로 찍어 보낸다. 은행 입장에서는 이 요청이 진짜 요청이라 믿고 송금을 실행.

### 3.5 Redirect
사실 앞서 보여준 예시에서 POST 요청 후 완료 메시지 페이지를 직접 반환하는 것은 매우 좋지 않은 방식이다. 왜냐면 후속 행동(새로고침, 뒤로 가기 등)에서 예기치 않은 동작을 유발할 수 있기 때문. 즉, **서버는 데이터 저장 후 사용자를 적절한 기존 페이지로 보내야 한다.** 이때 쓰이는게 `redirect()` 함수. 클라이언트가 인자에 작성된 주소로 다시 요청을 보내도록 한다.

``` python
from django.shortcuts import render, redirect # redirect 추가

def create(request):
	title = request.GET.get('title')
	content = request.GET.get('content')
    
    article = Article(title=title, content=content)
    article.save()
    
    # redirect을 이용해 기존 페이지로 강제 이동
	return redirect('articles:detail', article.pk)
```
