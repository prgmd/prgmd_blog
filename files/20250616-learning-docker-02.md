# I. 도커 이미지(Docker Image)

[지난 게시글](https://prgmd-blog.vercel.app/#post/20250613-learning-docker-01)에서 도커 이미지의 특징인 '레이어' 개념을 배웠다.

> "**애플리케이션 실행에 필요한 환경을 담고 있는 읽기 전용(Read-only) 템플릿으로, 여러 개의 레이어가 차곡차곡 쌓인 형태**다. (중략) 여러 컨테이너가 똑같은 이미지를 기반으로 실행되고 있다면, 무거운 이미지 레이어들은 단 하나만 존재하며 **모든 컨테이너가 이를 공유해서 읽는 구조**다. 이게 저장 공간을 아끼는 핵심."

만약 10개 서비스가 모두 `Ubuntu` 기반이라면, 도커는 `Ubuntu` 레이어를 10번 저장하지 않고 단 1번만 저장한다. 서로 다른 이미지라도 베이스가 같은 **해당 레이어를 공유하고**, 이미지 업데이트시 **변경된 레이어만 새로 쌓으며**, 여러 레이러를 하나로 합쳐 사용자에게 마치 하나의 폴더처럼 보여준다. 

## 1. 도커 이미지 구조

이미지의 공식 명칭은 총 4개로 이뤄진다.

> `Registry_Address / Namespace / Repository_Name : Tag`

- Registry Address: 이미지가 저장된 서버 주소 (예: `docker.io`, `ghcr.io`). 생략 시 기본값은 Docker Hub.
- Namespace (네임스페이스): 이미지를 소유한 사용자나 단체의 이름.
  - 공식 이미지: 별도 지정이 없으면 library가 붙음. (예: `library/python`)
  - 사용자 이미지: 개발자 개인 ID. (예: `jang/my-app`)
- Repository Name: 실제 소프트웨어의 이름. (예: `mysql`, `nginx`)
- Tag (태그): 이미지 버전. (예: `3.8`, `latest`)

### 1.1 Tag와 Digest

| 구분      | 태그 (Tag)                            | 디지스트 (Digest)                 |
| ------- | ----------------------------------- | ----------------------------- |
| **특징**  | 사람이 읽기 쉬운 **별명** (v1.0, latest)     | 이미지 내용의 **지문**(SHA256 해시값)    |
| **가변성** | **가변적**. 같은 `latest`라도 내용이 바뀔 수 있음. | **불변적**. 내용이 1비트라도 다르면 값도 변함. |
| **용도**  | 편리한 버전 관리 및 배포                      | **무결성 검증** 및 운영 환경의 고정 배포     |
| **예시**  | `nginx:latest`                      | `nginx@sha256:4c0...`         |

참고로 도커를 이용하게 되면 `latest`를 자주 보게 될 텐데, 이 때 `latest`는 '최신 버전'이 아니라, 단지 가장 최근에 붙여진 이름일 뿐이다. **운영 환경에서 latest를 쓰는 것은 위험하다. 정확한 버전 태그나 Digest를 사용하는 것이 보안과 안정성의 핵심.**

### 1.2 이미지 확인 및 컨테이너 실행

지난 게시글에서 도커 이미지 관련 명령어들을 알아봤는데, 조금 더 자세하게 보자면 다음과 같다. 로컬 이미지 목록 확인 명령어를 쓰면 나오는 (`docker image`) 출력 정보는 다음과 같다.

- **REPOSITORY(이미지 이름)**: 이미지 이름(네임스페이스 포함)
- **TAG(버전)**: 버전 정보
- **IMAGE ID(고유 식별자)**: 로컬에서 이미지 식별하는 고유 ID (앞 12자리)
- **CREATED(생성 시점)**: 이미지 생성 시점
- **SIZE(가상 크기)**: 전체 레이어가 합쳐진 가상 크기

#### 출력 예시 및 해석 방법

```bash
REPOSITORY                TAG       IMAGE ID       CREATED        SIZE
nginx                     latest    605c77e624dd   2 weeks ago    141MB
mysql                     8.0       3218340d0d54   3 weeks ago    516MB
my-id/custom-python       v1.0      ae2a1234abcd   24 hours ago   850MB
<none>                    <none>    f92348572341   2 months ago   120MB
```

- **REPOSITORY(이미지 이름)**
  * nginx: 네임스페이스가 생략된 공식 이미지 (실제로는 library/nginx).
  * my-id/custom-python: 사용자(my-id)가 직접 만든 이미지.
  * <none>: **댕글링 이미지(Dangling Image)**라고 불리며, 이미지 빌드 중 오류가 났거나 새 버전이 나오면서 이름(Tag)을 뺏긴 유령 이미지다.
- **TAG(버전)**
  * latest: 가장 최근에 pull 하거나 빌드할 때 버전을 명시하지 않은 경우 붙는 기본값.
  * 8.0 / v1.0: 특정 시점의 버전을 명시한 경우.
- **IMAGE ID(고유 식별자)**
  * 605c77e624dd: 이미지의 주민등록번호 같은 존재입니다. 명령어 입력 시 605처럼 앞 3자리만 겹치지 않게 입력해도 도커가 인식한다.
- **CREATED(생성 시점)**
  * 다운로드한 날짜 X. 이 이미지가 **도커 허브에 처음 빌드되어 올라간 시점**. 2 weeks ago라면 2주 전에 만들어진 따끈따끈한 이미지라는 뜻.
- **SIZE(가상 크기)**
  * 해당 이미지가 차지하는 전체 레이어의 합계이므로, 만약 여러 이미지가 같은 베이스 레이어를 공유하고 있다면 실제 하드디스크 점유량은 이 수치들의 합보다 훨씬 적은 것.

## 3. 이미지 업로드 및 태그(Tag) 관리

수정된 컨테이너 환경은 **새로운 이미지로 생성**하거나, 기존 이미지에 식별 가능한 이름을 부여해 **원격 저장소에 공유**할 수 있습니다.

### 3.1 도커 로그인 및 로그아웃

원격 레지스트리에 접근하기 위한 인증 과정을 말한다.

- **로그인:** `docker login [레지스트리 주소]`
  * CLI 환경에서 `-u [계정명]` 옵션을 사용하면 계정명을 미리 입력할 수 있고, 패스워드는 보안상 별도로 입력할 것을 권함.
- **로그아웃:** `docker logout`

### 3.2 이미지 태그 부여

이 때, 원격 저장소에 이미지를 push하려면 반드시 이미지 이름이 **`[계정ID]/[레포지토리명]:[태그]`** 형식을 갖춰야 한다.

- **명령어:** `docker tag [원본_이미지명] [계정ID]/[레포지토리명]:[태그]`
  * **예시:** `docker tag my-app:v1 ssafy/my-app:1.0` (태그 생략시 기본값으로 `latest` 부여)

### 3.3 이미지 업로드

- **명령어:** `docker push [계정ID]/[레포지토리명]:[태그]`

팁이 있다면, 업로드 전 `docker images` 명령어를 사용해 태그가 올바르게 생성되었는지 먼저 확인한 다음 올리도록 하자.

### 3.4 이미지의 파일 관리(Save & Load)

> **만약 폐쇄망 환경(인터넷 불가)이나 보안상 네트워크 전송이 어렵다면, 이미지를 아카이브 파일(`.tar`)로 변환해 물리적으로 전달할 수도 있다.** 이때 사용하는게 `save`와 `load` 명령어.

- **명령어:** `docker image save -o [파일명.tar] [이미지명:태그]`
  * 로컬 도커 엔진에 있는 이미지를 레이어 구조 포함 단일 파일로 추출.
  * `>`(리다이렉션) 방식도 가능하지만, `-o` (output) 옵션을 사용하는 것이 더 표준에 가깝다.
- **명령어:** `docker image load -i [파일명.tar]`
  * `.tar` 파일을 도커 엔진 이미지 리스트에 등록하는 명령.
    * `-i` (input) 옵션을 사용한다.

#### 이미지와 컨테이너의 저장 목적의 차이

- 둘 다 `.tar` 파일로 저장되기 때문에 혹여나 착각할 수도 있으니 꼭 유의하도록 하자.
  * `save`는 이미지를 통째로 굽는 방식이고, `export`는 컨테이너를 통째로 굽는 방식이다. 쉽게 말하면 게임 CD 파일을 복사하는 것과 세이브 파일을 추출하는 개념이라 보면 된다.

| 구분     | **Save / Load**                                          | **Export / Import**                                  |
| ------ | -------------------------------------------------------- | ---------------------------------------------------- |
| **대상** | **이미지 (Image)**                                          | **컨테이너 (Container)**                                 |
| **특징** | 이미지의 메타데이터, 레이어 이력(History) 보존. 복구시 설치했던 기록(레이어)이 다 살아있다 | 컨테이너의 현재 상태(파일 시스템)만 스냅샷으로 저장. 복구하면 결과물 파일만 덩그러니 남는다 |
| **용도** | 이미지의 완벽하게 이전 및 복구하고 싶을 때                                 | 가벼운 배포용 혹은 백업용                                       |

# II. 레지스트리

사실 레지스트리 자체가 '무언가를 등록하고 관리하는 저장소'라는 광의의 용어. 우리가 자주 사용할 레지스트리는 Docker Hub나 Amazon ECR 같은 '컨테이너' 정보를 담는 레지스트리지만, 간략하게 어떤 저장소가 또 있는지만 가볍게 알아보도록 하자.

## 1. 컨테이너 레지스트리 (Container Registry)

도커 이미지와 같은 컨테이너 이미지들을 저장하고 관리하는 중앙 저장소. 개발자가 로컬에서 만든 이미지를 `docker push`해서 보관하고, 서버(EC2, EKS 등)에서 그 이미지가 필요할 때 `docker pull`해서 가져가는 도서관 같은 역할이다.

### 1.1 주요 기능

* 버전 관리(동일 소프트웨어라도 `v1.0`, `v1.1`, `latest` 등 태그 붙여 관리)
* 저장된 이미지에 보안 취약점 있는지 자동 검사
* 특정 사용자나 서버만 이미지를 가져갈 수 있도록 권한 제어

#### Amazon ECR

> AWS에서 제공하는 완전 관리형 도커 컨테이너 레지스트리 서비스. 개발자가 만든 컨테이너 이미지를 안전하게 보관하고, 필요할 때 언제든 꺼내 쓸 수 있게 해주는 AWS 전용 이미지 창고다.

* 완전 관리형이 뭐죠? = 서버 설치나 저장 용량 관리가 필요 없다는 뜻. AWS에서 자잘한 건 전부 관리해준다는 뜻이다.
* IAM으로 권한 제어가 가능하고, 일반적인 컨테이너 레지스트리와 비슷하게 이미지를 스캔해 취약점도 자동 검사해준다. 오래된 이미지는 자동 삭제하도록 수명 주기 설정도 가능.

## 2. 스키마 레지스트리

> 데이터 엔지니어링(Kafka 등)에서 사용하는 개념으로, 데이터 설계도를 저장하는 도서관. 데이터를 주고받을 때 메시징 정보, 그 데이터가 어떤 형식을 갖추고 있는지 정보를 저장한다. 데이터를 보내는 쪽(Producer)과 받는 쪽(Consumer)가 서로 동일 데이터 구조를 쓰는지 체크.

* 예시:  Confluent Schema Registry (Kafka 환경에서 주로 사용한다)

## 3. OS 레지스트리

> 윈도우 OS 내부에서 사용하는 설정값 보관소. OS와 설치 프로그램들이 작동할 때 필요한 모든 설정 정보(키/값)을 담고 있다. 

* 뭐 정말 자잘한 배경화면 설정부터 하드웨어 드라이버 정보, 프로그램 설치 경로까지 전부 저장된 대규모 저장소. `regedit`을 치면 나온다. 혹여나 잘못 건드렸다가 망가트리지 말자.
* 예시 : Windows Registry Editor
